# Версионирование

Этот документ — для тех, кто выпускает релизы, разворачивает MCP-сервер и интегрирует
его с порталом ModusBI. Он объясняет: по какой схеме нумеруется версия сервера, где она
задаётся, и как держать согласованными три движущиеся части — **фронтенд портала**,
**бэкенд портала** и **MCP-сервер**.

Если вы впервые видите проект: MCP-сервер — это программа, которая принимает команды от
ИИ-клиента (по протоколу JSON-RPC 2.0) и через эти команды создаёт и настраивает отчёты в
портале ModusBI. Сам сервер ничего не «рисует» — он формирует JSON-конфигурацию отчётов и
компонентов, а отображает её фронтенд портала в браузере. Из-за этого версия сервера всегда
связана с конкретной версией фронтенда: одно без другого не имеет смысла.

Базовые термины (слаг, рендер-контракт, JSON-RPC, режимы readonly/readwrite) собраны в
[словаре терминов](../../GLOSSARY.md).

---

## 1. Три версионируемых компонента

```
┌──────────────────────┐    читает слаги при рендере   ┌───────────────────────┐
│  Фронтенд портала    │◄──────────────────────────────│   Slug-схема MCP       │
│  (бандл, отображение) │      (рендер-контракт)         │  app/tools/config_schema.py │
└──────────┬───────────┘                                └───────────┬───────────┘
           │ HTTP action/command                                    │ HTTP action/command
           ▼                                                        ▼
              ┌─────────────────────────────────────────┐
              │   Бэкенд портала (POST /v1/api/...,      │
              │   команда — в теле запроса)              │
              └─────────────────────────────────────────┘
```

| Компонент | Что в нём версионируется | Где «живёт» его версия |
|---|---|---|
| **MCP-сервер** | контракт инструментов (tools/actions), slug-схема, генераторы конфигов (builders) | `__version__` в `app/__init__.py`, см. §3 |
| **Фронтенд портала** | что реально отображается в браузере: какие слаги, geokeys и типы компонентов | имя файла рендер-контракта `render_contract_<версия_фронта>.json` (каталог `docs/architecture/readiness/audit/`) |
| **Бэкенд портала** | HTTP-эндпоинты, поля датасетов и отчётов | согласуется с релизом портала (фиксируется в матрице, §4) |

**Ключевая зависимость.** MCP-сервер записывает JSON-конфигурацию, но отображает её
фронтенд. Поэтому slug-схема сервера действительна только против **конкретной** версии
фронт-бандла, описанной рендер-контрактом. Когда портал выкатывает новый фронт-бандл, часть
слагов может перестать давать видимый эффект, или их путь внутри JSON может измениться — это
надо пересверить заново (см. [рендер-контракт](../concepts/render-contract.md)).

## 2. Схема версии сервера (semver)

Версия MCP-сервера записывается в формате `MAJOR.MINOR.PATCH` (первый публичный релиз —
`1.0.0`). Каждый разряд отвечает за свой класс изменений:

- **MAJOR** — несовместимое изменение контракта инструментов: удалён или переименован
  action либо параметр, изменился формат ответа. После такого обновления клиентам
  (ИИ-агенту, интеграциям) скорее всего придётся менять свой код.
- **MINOR** — обратносовместимое расширение: добавлены новые инструменты, actions, слаги
  или генераторы конфигов; добавлена поддержка более нового фронт-бандла через новый
  рендер-контракт. Старые вызовы продолжают работать как раньше.
- **PATCH** — исправления без изменения контракта: починка пути слага внутри JSON,
  корректировка масштаба значения, правка логики генератора. Снаружи контракт тот же.

Внутри разработки допустимы пред-релизные суффиксы (например `-rc1`). **В публичный релиз
должен идти чистый `MAJOR.MINOR.PATCH` без суффиксов** — это проверяется в чек-листе релиза
(§6).

## 3. Где задаётся версия сервера

Каноничный источник версии один — `app/__init__.py` (`__version__`); тот же номер дублируется
в `pyproject.toml`, потому что упаковка требует статического значения. Собранный бинарник
сообщает версию сам, без окружения.

Переменная окружения `MCP_VERSION` — необязательный override для рантайма (например, штамп
конкретной сборки на стейджинге). Код читает `os.environ.get("MCP_VERSION") or __version__`
(см. `app/tools/token_metrics.py`): если переменная не задана, берётся `__version__`.

Дисциплина, чтобы версии не разъезжались:

1. **Версия сервера** — менять только `__version__` (`app/__init__.py`) и синхронно
   `pyproject.toml`. Не разносить номер по докстрингам и документации.
2. **Число слагов** — не писать конкретным числом в тексте. Оно вычисляется из самой
   slug-схемы как `len(SLUG_SCHEMA)` (`app/tools/config_schema.py`). В описаниях используется
   формулировка «N слагов (см. `config_schema.SLUG_SCHEMA`)», а не зафиксированный снимок.
   Так число всегда соответствует фактической схеме.
3. **Версия фронтенда** — только в имени файла `render_contract_<версия>.json` и в матрице
   совместимости (§4). Не зашивать номер бандла в код.
4. **Версия бэкенда** — фиксируется только в матрице (§4), не в коде.

---

## 4. Матрица совместимости: фронт ↔ бэк ↔ MCP

Совместимость связки ведётся таблицей и обновляется при каждом релизе. Источник правды по
фронтенду — файл рендер-контракта: его имя содержит проверенную версию бандла, против которой
сверена slug-схема.

| MCP-сервер | Фронтенд портала (проверенный) | Бэкенд портала | Рендер-контракт | Примечание |
|---|---|---|---|---|
| текущая совместимая ветка | проверенный бандл портала | совместимый с этим фронтом релиз | `render_contract_<версия>.json` | база, против которой сверена slug-схема |

Правила ведения матрицы:

- Не указывать «поддерживается» без **проверенного** рендер-контракта под эту версию фронта.
- Сначала пересверить рендер-контракт на новом фронте (см. §5), затем добавлять строку.
- Конкретные номера версий в этой публичной документации жёстко не фиксируются — актуальную
  проверенную связку смотрите в матрице вашего релиза и в имени файла рендер-контракта.

---

## 5. Порядок ведения версии (процесс)

### Сменился фронт-бандл портала

1. Пересверить рендер-контракт: какие слаги реально отображаются на новом бандле.
2. Обновить файл рендер-контракта `render_contract_<новая_версия>.json` (он лежит в
   `docs/architecture/readiness/audit/`) и статусы слагов в `config_schema.py` (что перестало
   отображаться, какие пути слагов изменились).
3. Поднять у сервера разряд **MINOR** (поддержка более нового фронта — это расширение
   совместимости) либо **PATCH** (если только починили пути слагов, контракт инструментов не
   менялся).
4. Добавить строку в матрицу совместимости (§4).
5. Поднять `__version__` (`app/__init__.py`) и синхронно `pyproject.toml`.

### Изменился только MCP-сервер (новый фронт не выходил)

- Новый функционал (новый инструмент, action, слаг, генератор) → **MINOR**.
- Исправление существующего поведения → **PATCH**.
- Матрицу §4 не трогать — фронт и бэк те же. Поднять `__version__` (и `pyproject.toml`).

### Изменился HTTP API бэкенда портала

- Сверить затронутые инструменты (работа с источниками данных, датасетами, отчётами,
  компонентами) против нового API.
- При несовместимости — **MAJOR**, иначе **MINOR** или **PATCH**. Обновить строку матрицы §4.

---

## 6. Чек-лист перед релизом

- [ ] `__version__` (`app/__init__.py`) и `version` в `pyproject.toml` совпадают, чистый `MAJOR.MINOR.PATCH` без суффиксов; `MCP_VERSION` (если задан) — тоже.
- [ ] В коде нет inline-чисел слагов и зашитых номеров версий фронта/бэка (см. §3).
- [ ] Матрица совместимости (§4) отражает реально проверенную связку фронт/бэк/MCP.
- [ ] Рендер-контракт соответствует текущему фронт-бандлу портала.

---

## Пример сценария обновления

Портал выкатил новый фронт-бандл. Действия релиз-инженера:

1. Прогнать сверку рендер-контракта против нового бандла. Допустим, выяснилось, что несколько
   слагов перестали давать видимый эффект, а у одного изменился путь внутри JSON.
2. Сохранить новый `render_contract_<новая_версия>.json` (в `docs/architecture/readiness/audit/`),
   обновить статусы этих слагов в `config_schema.py` (часть — как «не отображается на
   текущем фронте», у одного — новый путь).
3. Поскольку контракт инструментов наружу не менялся, а правились только пути слагов под новый
   фронт — поднять разряд **PATCH** (если же при этом добавили новые рабочие слаги под новый
   фронт — то **MINOR**).
4. Дописать строку в матрицу совместимости (§4) с новой версией фронта и проверенным
   рендер-контрактом.
5. Поднять `__version__` (`app/__init__.py`) и `pyproject.toml` (без суффиксов) и пройти
   чек-лист (§6).

После этого связка снова согласована: клиенты вызывают тот же контракт инструментов, а слаги,
которые пишет сервер, гарантированно отображаются проверенным фронт-бандлом.
