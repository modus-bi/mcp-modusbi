# Соглашения и код-стайл проекта

Документ для контрибьюторов. Описывает, как устроен код MCP-сервера, по каким
правилам он пишется и как запускать тесты. Цель — чтобы человек, впервые открывший
репозиторий, мог дописать новый инструмент или действие, не нарушив принятый стиль.

Базовые понятия (MCP, инструмент, действие, отчёт, компонент, датасет, портал) собраны
в [словаре терминов](../GLOSSARY.md). Если встретите незнакомое слово — загляните туда.

Пошаговые рецепты «как добавить слаг, билдер или инструмент» — в
[Механике расширения сервера](extending.md). Этот документ описывает правила и стиль,
тот — конкретные сценарии.

---

## 1. Что это за код

MCP-сервер на Python соединяет ИИ-ассистента с аналитическим порталом ModusBI.
Снаружи он говорит по протоколу MCP поверх JSON-RPC 2.0: ассистент отправляет вызов
RPC-метода с параметрами через стандартный поток ввода-вывода (stdio) и получает результат.
Каждый инструмент сервера — это такой RPC-метод, а не HTTP-эндпоинт.

Внутри, чтобы выполнить работу, сервер обращается к порталу по его HTTP-API. Это
деталь реализации сервера: на использование инструментов она не влияет. Запросы к порталу
идут методом POST, а конкретная операция кодируется в теле запроса (пара «объект + команда»),
то есть в стиле команд-действий (action/command поверх HTTP), а не как ресурсный REST.

- Язык и версия: Python 3.10+
- Протокол наружу: MCP через SDK FastMCP
- Связь с порталом: HTTP POST с командами в теле запроса

Подробнее про протокол — [Протокол и RPC](concepts/protocol-and-rpc.md),
про общую архитектуру — [Архитектура и потоки данных](concepts/architecture.md).

## 2. Структура кода

Весь сервер живёт в пакете `app/`. Три слоя, которые важно различать:

```
app/
├── __init__.py            # метаданные пакета (версия)
├── __main__.py            # точка входа: python -m app
├── server.py              # РЕГИСТРАЦИЯ инструментов как MCP-методов, запуск, чтение env
├── prompts.py             # готовые многошаговые сценарии (промпты)
│
├── core/                  # ИНФРАСТРУКТУРА (не про конкретные инструменты)
│   ├── instances.py       # подключение к порталу, HTTP-клиент, авторизация
│   ├── security.py        # режимы доступа (readonly/readwrite), проверка действий
│   ├── exceptions.py      # иерархия ошибок + помощники проверки параметров
│   └── validation.py      # очистка входных данных (например, санитизация HTML)
│
└── tools/                 # ДИСПЕТЧЕРЫ — по файлу на предметную область
    ├── report_operations.py      # операции над отчётами
    ├── dataset_operations.py     # операции над датасетами
    ├── datasource_operations.py  # операции над подключениями к данным
    ├── component_operations.py   # внутренний диспетчер операций над компонентами
    ├── component_crud.py         # реализация: добавление/изменение/удаление компонентов
    ├── component_filters.py      # реализация: фильтры компонентов
    ├── component_axes.py         # реализация: оси, расчётные поля, страницы
    ├── style_operations.py       # CSS-стили отчёта
    ├── batch_operations.py       # пакетные операции
    ├── action_types.py           # типы Literal[...] для параметра action
    ├── ...                       # прочие домены (полный список — в справочнике инструментов)
    │
    ├── builders.py        # вспомогательное: сборка конфигов компонентов
    ├── layout_helper.py   # вспомогательное: расчёт раскладки
    ├── config_schema.py   # справочник слагов конфигурации компонентов
    └── help_texts.py      # тексты подсказок и help-действий
```

Файлов в `tools/` заметно больше, чем в этом сокращённом снимке: помимо доменных
диспетчеров там лежат справочники, пресеты и вспомогательные модули. Снимок показывает
ключевые роли, а не полный список.

Три роли, которые важно запомнить:

- **`server.py` — регистрация.** Здесь каждый инструмент объявляется как MCP-метод
  (декоратор `@mcp.tool(...)`), получает клиента к порталу и делегирует работу диспетчеру
  из `tools/`. Бизнес-логики тут нет — только склейка.
- **`app/tools/*` — диспетчеры.** Как правило, один файл = одна предметная область (отчёты,
  датасеты, стили). Внутри файла — публичная функция-диспетчер и набор приватных функций
  под отдельные действия.
- **`app/core/*` — инфраструктура.** То, что не привязано к конкретному инструменту:
  HTTP-клиент к порталу, авторизация, режимы доступа, ошибки и помощники проверки
  параметров. Диспетчеры опираются на core.

### Особый случай: операции над компонентами

Компоненты — самая объёмная предметная область, поэтому она устроена не «один файл —
один диспетчер», а в два уровня:

- Один внутренний диспетчер (`component_operations.py`) принимает действие и маршрутизирует
  его в модули реализации.
- Модули реализации (`component_crud.py`, `component_filters.py`, `component_axes.py`,
  стилизация) содержат сами операции.

На уровне MCP это видно как несколько отдельных инструментов (CRUD компонентов, фильтры,
оси, визуальная стилизация), каждый из которых регистрируется в `server.py` и опирается на
этот внутренний диспетчер. Если вы добавляете действие над компонентами — реализуйте его в
соответствующем модуле реализации и подключите через `component_operations.py`.

Имена файлов и набор инструментов могут отличаться от снимка выше по мере развития —
актуальный список инструментов смотрите в [Справочнике инструментов](tools/README.md).

## 3. Паттерн инструмента

Каждый инструмент собран по одной схеме из трёх слоёв.

### Слой 1. Приватные функции под действия (`_verb_noun`)

Каждое отдельное действие — приватная асинхронная функция с префиксом `_`.

```python
async def _list_datasources(client) -> dict[str, Any]:
    """List all datasources."""
    response = await client.api_call("datasources", "list")
    ...
    return {"success": True, "count": len(items), "items": items}
```

### Слой 2. Публичный диспетчер (`{домен}_operations`)

Одна публичная асинхронная функция принимает первым смысловым аргументом `action` и
маршрутизирует вызов через `match action:` (структурное сопоставление Python 3.10).

Тип параметра `action` задаётся через `Literal[...]` (типы собраны в `tools/action_types.py`).
Это не просто аннотация: FastMCP превращает `Literal` в JSON Schema `enum`, и ассистент
заранее видит полный список допустимых действий, не угадывая их строками.

```python
from .action_types import DatasourceAction  # Literal["list", "get", ...]

async def datasource_operations(
    client,
    action: DatasourceAction,
    datasource_id: int | None = None,
    table_name: str | None = None,
    schema: str = "public",
) -> dict[str, Any]:
    """Datasource operations dispatcher."""
    match action:
        case "list":
            return await _list_datasources(client)
        case "get":
            err = require(
                {"datasource_id": datasource_id},
                tool="datasource_operations",
                action="get",
            )
            if err:
                return err
            return await _get_datasource(client, datasource_id)
        case _:
            return {"error": f"Unknown action: {action}"}
```

Ветка `case _:` обязательна: на неизвестное действие инструмент возвращает понятную
ошибку `Unknown action: ...`, а не падает.

Проверку обязательных параметров делают помощником `require(...)` из `app/core/exceptions.py`:
он осматривает все переданные значения сразу и возвращает структурированную ошибку со списком
недостающих полей. Это удобнее, чем ряд проверок `if not ...`, потому что ассистент исправляет
все пропуски за один повтор вызова, а не находит их по одному.

### Слой 3. Регистрация в `server.py`

Сервер импортирует функцию-диспетчер под алиасом с префиксом `_` и оборачивает её
в MCP-метод. Метод получает клиента к порталу и передаёт все параметры дальше.

```python
from .tools.report_operations import report_operations as _report_operations

@mcp.tool(annotations=...)
async def report_operations(...) -> dict[str, Any]:
    client = await _get_client()
    return await _report_operations(client, action=action, ...)
```

### Формат возвращаемого значения

Все инструменты возвращают `dict[str, Any]`. Две формы.

**Успех** — флаг `success: True` плюс полезная нагрузка:

```python
{"success": True, "count": N, "items": [...]}
{"success": True, "report": {...}}
```

**Ошибка** — человекочитаемое сообщение. В простом случае это короткая пара:

```python
{"success": False, "error": "..."}   # что не так
```

Когда ошибка связана с неверными или неполными параметрами, ответ дополняется
полями-подсказками, чтобы вызывающая сторона исправилась без обращения к исходникам:

```python
{
  "success": False,
  "error": "...",            # что не так
  "missing": [...],          # каких параметров не хватило
  "expected_types": {...},   # какие типы ожидались
  "hint": "...",             # как починить, словами
  "example": {...},          # пример корректного вызова
}
```

Расширенные поля (`missing`, `expected_types`, `hint`, `example`) добавляют именно при
недостающих или неверных параметрах — не к каждой ошибке. Для прочих сбоев (ресурс не
найден, ошибка API) хватает короткой формы с `error`.

Идея единого формата ошибки: ответ должен сам подсказывать следующий шаг. Поэтому к
ошибке про параметры прикладываются `hint` (что сделать) и при необходимости `example`
(готовый образец вызова). Например, ошибка про неизвестное поле оси отдаёт список доступных
полей и `hint`, объясняющий, что передавать имя поля, а не SQL-выражение.

### Три способа сообщить об ошибке

В коде встречаются три стиля, и важно выбирать осознанно:

1. **Короткий dict** — `{"success": False, "error": "..."}`. Подходит, когда подсказывать
   нечего: операция портала вернула отказ, ресурс не найден и т.п.
2. **Структурированный dict** — короткий плюс `missing`/`expected_types`/`hint`/`example`.
   Применяется к ошибкам параметров; обычно его собирает помощник `require(...)`.
3. **Исключение** — `raise ValidationError(...)` (и другие из иерархии § 5). Уместно в
   глубине логики, где удобнее прервать выполнение; на верхнем уровне такие исключения
   сериализуются в ответ методом `.to_dict()`.

Внутри одного инструмента старайтесь не смешивать стили без причины: для ответов о
параметрах — структурированный dict, для отказов портала — короткий.

### Защита операций записи

Действия, изменяющие данные (`create`, `update`, `delete` и т.п.), перед выполнением
вызывают проверку режима. Помощник `check_action(...)` **выбрасывает** `SecurityError`,
если в текущем режиме действие запрещено (по умолчанию сервер работает в режиме чтения):

```python
case "create":
    check_action("create")   # бросит SecurityError, если режим только чтение
    ...
```

Поскольку это исключение, его либо ловят на уровне инструмента и превращают в ответ-ошибку,
либо дают всплыть к верхнему слою, где оно сериализуется через `.to_dict()`. Главное — не
полагаться на то, что `check_action(...)` вернёт значение: он ничего не возвращает, а
прерывает выполнение.

Про режимы доступа подробно — [Режимы доступа и безопасность](security-model.md).

### Справочные действия

У мультидейственных инструментов принято поддерживать действие `help` (и где уместно —
`types_list`, `*_list`), которое возвращает список доступных действий и параметров.
Это позволяет ассистенту узнать возможности инструмента, не читая исходники.

## 4. Соглашения именования

| Элемент                     | Правило                  | Пример                                |
|-----------------------------|--------------------------|---------------------------------------|
| Модули                      | `snake_case`             | `report_operations.py`                |
| Публичные инструменты       | `{домен}_operations`     | `dataset_operations()`                |
| Приватные функции действий  | `_verb_noun`             | `_list_reports()`, `_get_dataset()`   |
| Классы                      | `PascalCase`             | `InstanceManager`, `SecurityMode`     |
| Исключения                  | `PascalCase` + `Error`   | `NotFoundError`, `APIError`           |
| Константы                   | `UPPER_SNAKE_CASE`       | `READONLY_ACTIONS`                    |
| Поля датаклассов            | `snake_case`             | `base_url`, `token`                   |
| Приватные поля              | `_snake_case`            | `_instances`, `_active`               |
| Имена действий (`action`)   | глагол в `snake_case`    | `"list"`, `"get"`, `"create"`, `"fields_list"` |
| Коды ошибок                 | `UPPER_SNAKE_CASE`       | `"NOT_FOUND"`, `"API_ERROR"`          |

Имена действий не только следуют `snake_case`, но и перечисляются в `Literal[...]`
(`tools/action_types.py`) — так список допустимых значений попадает в схему инструмента.

## 5. Ошибки

Все исключения наследуются от базового класса и образуют иерархию:

```
ModusBIError (база)
├── AuthenticationError   # проблемы авторизации (401)
├── APIError              # общие ошибки API (с кодом статуса)
├── NotFoundError         # ресурс не найден (404)
├── ValidationError       # некорректные входные данные (400)
├── SecurityError         # операция запрещена в текущем режиме (403)
└── InstanceError         # ошибки управления подключением
```

Правила:

- Каждый класс принимает `message: str` и необязательный `details: dict`.
- У каждого есть метод `.to_dict()` для сериализованного ответа об ошибке.
- Коды ошибок — `UPPER_SNAKE_CASE` (`AUTHENTICATION_ERROR`, `NOT_FOUND`, `VALIDATION_ERROR`).

## 6. Стиль Python-кода

- **Типы.** Современный синтаксис: объединения через `|` (`str | None`, не `Optional[str]`),
  встроенные дженерики (`dict[str, Any]`, `list[...]`, не `Dict`/`List` из `typing`).
  Для параметра `action` — `Literal[...]` (см. § 3), чтобы допустимые значения попадали в
  схему инструмента.
- **PEP 8.** Отступ 4 пробела (без табов), длина строки около 100 символов (мягкий лимит),
  две пустые строки между определениями верхнего уровня, импорты сгруппированы:
  стандартная библиотека, сторонние пакеты, локальные модули.
- **Документирующие строки.** У каждого модуля, класса и публичной функции есть docstring.
  Модуль инструмента в начале перечисляет назначение и список доступных действий.
- **Датаклассы.** Для контейнеров данных используется `@dataclass`, а не обычные классы.
- **Размер.** Вспомогательные и инфраструктурные модули стараемся держать компактными, а
  функции — короткими (ориентир — несколько десятков строк), вынося общую логику в помощники
  (`builders.py`, `layout_helper.py` и т.п.) без дублирования. Файлы доменных диспетчеров
  бывают заметно крупнее из-за большого числа действий — это допустимо: главное, чтобы
  отдельные функции оставались небольшими и читаемыми.

### Язык в коде

| Контекст                       | Язык     |
|--------------------------------|----------|
| Docstring модулей и функций    | English  |
| Комментарии в коде             | English  |
| Описания инструментов          | English  |
| Сообщения об ошибках для пользователя | Русский |

То есть внутренняя документация кода — на английском, а тексты, которые видит конечный
пользователь (сообщения об ошибках), — на русском.

## 8. Тесты

### Где лежат и чем гоняются

- Тесты — в каталоге `app/tests/`.
- Фреймворк — `pytest` с `pytest-asyncio` в режиме `asyncio_mode = "auto"` (асинхронные
  тесты не требуют отдельного маркера). Конфигурация — в `pyproject.toml`.

Запуск всего набора:

```bash
pytest
```

Запуск одного файла или одного теста:

```bash
pytest app/tests/test_config_schema.py
pytest app/tests/test_config_schema.py::test_some_case
```

### Тесты только-чтения по живому порталу

Часть тестов выполняется против реального портала, но вызывает только операции чтения
(`list`/`get`/`summary`), поэтому безопасна. Они подтверждают, что инструменты корректно
общаются с порталом, ничего не изменяя.

```bash
# интеграционные тесты только-чтения
python -m app.tests.test_readonly_smoke --verbose

# с явным указанием режима доступа
python -m app.tests.test_readonly_smoke --security-mode readonly
```

Подключение к порталу берётся из переменных окружения (см. ниже). Для запуска таких
тестов нужен доступ к порталу; для запуска обычных юнит-тестов он не требуется.

## 9. Конфигурация и запуск

Сервер читает параметры подключения к порталу из переменных окружения при старте —
отдельного файла с учётными данными нет. Минимальный набор:

```bash
MODUSBI_URL=https://<ваш-портал>
MODUSBI_USERNAME=<пользователь>
MODUSBI_PASSWORD=<пароль>
```

Шаблон всех переменных — в `.env.example`. Файлы с реальными секретами
(`.env`, клиентский `.mcp.json`) не попадают в репозиторий (перечислены в `.gitignore`).

Один процесс сервера обслуживает один портал; для нескольких порталов заводят несколько
записей в клиентской конфигурации MCP. Запуск и режимы (`readonly` по умолчанию,
`readwrite` для операций записи) описаны в [Режимах запуска сервера](../start/server-modes.md).

## 10. Git

- Рабочая ветка-основа — `master`. Изменения ведём в отдельных ветках и сливаем в `master`.
- Сообщения коммитов — в стиле [Conventional Commits](https://www.conventionalcommits.org/):
  `<type>(<scope>): <описание>`. `type` — категория изменения, `scope` (необязательный) —
  затронутая область (например, `tools`, `security`, `docs`).

| Тип        | Когда применять                                            |
|------------|-----------------------------------------------------------|
| `feat`     | новая возможность (инструмент, действие, слаг)            |
| `fix`      | исправление ошибки                                        |
| `refactor` | изменение кода без смены поведения                        |
| `test`     | добавление или правка тестов                              |
| `docs`     | изменения только в документации                           |
| `chore`    | служебное (зависимости, конфиги, мелкая инфраструктура)   |

```
feat(tools): add relationship_operations tool
fix(security): guard write actions in readonly mode
docs: update conventions
```

- `.gitignore` исключает артефакты Python (`__pycache__/`, `*.py[cod]`, `dist/`, `build/`),
  виртуальные окружения, секреты (`.env`, `.mcp.json`), служебные файлы IDE и выгрузки.
