# Эксплуатация сервера

Этот документ — для тех, кто разворачивает и сопровождает MCP-сервер ModusBI в
работе: как подключить один или несколько порталов, что происходит с токеном при
его истечении; где смотреть логи и как разграничивать доступ к секретам.

Если вы ещё не знаете, что это за сервер и как он встроен в связку «ИИ — сервер —
портал», начните с [обзорного README](../README.md) и
[словаря терминов](../GLOSSARY.md). Установка из исходников и первый запуск
описаны в [Установке и запуске (DevOps)](../start/for-devops.md). Здесь —
эксплуатационная сторона.

Два интерфейса сервера, важные при эксплуатации:

- наружу, к ИИ-клиенту, сервер общается по протоколу **MCP поверх JSON-RPC 2.0**
  (не REST); транспорт — стандартный поток ввода-вывода (stdio). Каждый
  инструмент — это RPC-метод;
- внутрь, к **порталу** ModusBI, сервер обращается по его HTTP-API: запросы идут
  методом POST, а конкретная операция кодируется в теле запроса (объект и
  команда), а не маршрутом ресурса.

---

## Модель «один сервер — один портал»

Один процесс сервера обслуживает **ровно один портал**. Адрес портала и
учётные данные задаются переменными окружения при старте процесса:
`MODUSBI_URL`, `MODUSBI_USERNAME`, `MODUSBI_PASSWORD`; опционально
`MODUSBI_INSTANCE_NAME` (человекочитаемое имя инстанса для логов). Внутри
процесса нет понятия «активный портал» и нет переключения между порталами на
лету: связь с порталом фиксируется на старте и не меняется до перезапуска.

Практические следствия для эксплуатации:

- сменить портал, его адрес или учётную запись можно только перезапуском
  процесса с другими переменными окружения;
- состояние авторизации (токен, факт подключения) живёт в памяти процесса;
  после перезапуска сервер авторизуется заново.

## Мультипортал

Несколько порталов поднимаются как **несколько отдельных записей в конфигурации
MCP-клиента** — по одному процессу сервера на портал. Каждая запись несёт свой
набор переменных `MODUSBI_*`, поэтому процессы изолированы друг от друга и не
делят ни токен, ни соединения.

Пример: две именованные записи в блоке `mcpServers` конфигурации клиента
(`.mcp.json` или `claude_desktop_config.json`) — у каждой свой `MODUSBI_URL`:

```jsonc
{
  "mcpServers": {
    "modusbi-prod":  {
      "command": "/путь/.venv/bin/python",
      "args": ["-m", "app.server", "--readonly"],
      "env": { "MODUSBI_URL": "https://portal-a.example.com", "MODUSBI_USERNAME": "<логин>", "MODUSBI_PASSWORD": "<пароль>" }
    },
    "modusbi-stage": {
      "command": "/путь/.venv/bin/python",
      "args": ["-m", "app.server", "--readwrite"],
      "env": { "MODUSBI_URL": "https://portal-b.example.com", "MODUSBI_USERNAME": "<логин>", "MODUSBI_PASSWORD": "<пароль>" }
    }
  }
}
```

Имена записей (`modusbi-prod`, `modusbi-stage`) — произвольные; по ним ИИ-клиент
и человек различают порталы. Режим доступа задаётся для каждой записи независимо:
в примере один портал поднят только на чтение, а другой — на запись.

Инструмент `instance_operations` показывает, к какому порталу подключён процесс:
он отдаёт сведения о текущем подключении — адрес, имя инстанса, статус
авторизации. Пароль он не возвращает.

## Аутентификация и обновление токена

При старте сервер пытается авторизоваться на портале сразу — выполняет вход
(POST на эндпоинт логина портала с логином и паролем из окружения) и при успехе
получает токен доступа (JWT). Если вход на старте не удался (портал недоступен,
неверные учётные данные), это не критично: сервер пишет в лог предупреждение и
продолжает работу. Срок действия токена сервер вычисляет из самого токена и
хранит вместе с ним в памяти процесса.

Дальше сервер поддерживает токен автоматически:

- **перед запросом** сервер проверяет валидность токена. Если токен истёк или его
  ещё нет (вход на старте не удался), выполняется вход ещё до отправки запроса к
  порталу;
- **если портал ответил `401`** (токен отозван или признан недействительным
  раньше срока), сервер сбрасывает токен, выполняет повторный вход и **один раз**
  повторяет тот же запрос с новым токеном. Для вызвавшего инструмента это
  происходит прозрачно — он получает результат, а не ошибку;
- при параллельных вызовах повторный вход выполняется один раз: первый вызов
  обновляет токен, остальные дожидаются его и используют уже свежий, без
  лишних входов.

Если вход не удался (портал недоступен, неверные учётные данные), инструмент
возвращает ошибку авторизации с указанием инстанса. Типичные причины, которые
стоит проверить оператору: недоступность портала по сети, смена пароля
API-пользователя без обновления переменных окружения, блокировка учётной записи
на стороне портала.

## Логирование

Сервер пишет диагностику в **`stderr`**. Поток `stdout` при этом остаётся
чистым — он занят протоколом stdio (JSON-RPC), и любой посторонний вывод в него
сломал бы обмен с ИИ-клиентом. Куда физически осядут строки из `stderr`,
определяет MCP-клиент, который поднял процесс: как правило, они попадают в журнал
клиента.

Поведение логирования настраивается двумя параметрами запуска:

| Параметр | Где задаётся | Назначение |
|---|---|---|
| `--log-level` | флаг запуска | уровень детализации: `DEBUG`, `INFO` (по умолчанию), `WARNING`, `ERROR` |
| `--log-format` | флаг запуска или переменная `MODUSBI_LOG_FORMAT` | формат строки: `text` (по умолчанию, для чтения человеком) или `json` |

В формате `json` каждая строка лога — один JSON-объект с полями времени,
уровня, имени логгера и сообщения; при ошибке с трассировкой добавляется поле с
исключением. Такой вывод удобно скармливать системам сбора логов. Действия,
изменяющие состояние портала, помечаются в сообщении маркером `audit:` (например,
`audit:report_create`); в `json`-формате такие записи дополнительно несут признак
аудита, по которому их можно отфильтровать в системе сбора логов.

При успешном старте сервер пишет в лог итоговый режим доступа, например
`Server started in READONLY mode`. Это первое, что стоит проверить при разборе
поведения: режим определяет, какие операции вообще разрешены (подробнее —
[Режимы работы сервера](../start/server-modes.md)).

Для ручной диагностики удобно поднять сервер с подробным логом:

```bash
python -m app.server --readonly --log-level DEBUG
```

А для прогона через систему сбора логов — переключить формат:

```bash
python -m app.server --readonly --log-format json
```

## Секреты

Все чувствительные значения сервер получает **из окружения процесса**, а не из
файлов в репозитории и не из аргументов командной строки. Это касается прежде
всего учётных данных портала (`MODUSBI_URL`, `MODUSBI_USERNAME`,
`MODUSBI_PASSWORD`). Хранить и доставлять их можно так, как принято в вашей
инфраструктуре: блок `env` в записи сервера у MCP-клиента, локальный файл `.env`
(шаблон — `.env.example`), либо механизм секретов вашей платформы развёртывания.

Правила обращения с секретами:

- **не коммитьте секреты в git.** Файлы `.env` и `.mcp.json`, в которых обычно
  лежат реальные значения, исключены из репозитория через `.gitignore`. В
  репозитории остаются только шаблоны-примеры с плейсхолдерами;
- **пароль не печатается** ни в выводе инструментов, ни в логах — чувствительные
  фрагменты сообщений маскируются перед записью;
- **подключения к базам данных** (источники данных портала) сервер при чтении
  отдаёт уже без чувствительных полей: адрес хоста, порт, имя базы, схема,
  пользователь и строка подключения в публичный ответ не попадают. Управление
  этими подключениями выполняется инструментом `datasource_operations`.

При мультипортальной конфигурации у каждой записи сервера — свой набор секретов
в её собственном блоке `env`; процессы не делят учётные данные между собой.
