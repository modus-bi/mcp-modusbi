# Что такое MCP и роль этого сервера

> ⚠️ **Перед практической работой** прочитайте [../../../DISCLAIMER.md](../../../DISCLAIMER.md): изменения на портале необратимы (нет отмены/истории), безопасность доступов при работе с LLM — на стороне пользователя.

## Коротко

Этот проект — **MCP-сервер для управления отчётами портала ModusBI**. Он стоит между
ИИ-ассистентом и порталом: ИИ описывает на естественном языке, что нужно построить, а сервер
превращает это в конкретные операции над отчётами, компонентами и данными портала.

Документ объясняет, что такое MCP, кто участвует в работе и какую роль играет этот сервер.
Детали самого протокола вынесены в [protocol-and-rpc.md](protocol-and-rpc.md). Все термины
определены в [../../GLOSSARY.md](../../GLOSSARY.md) — используйте его для уточнений.

## Что такое MCP

**MCP (Model Context Protocol)** — открытый протокол, по которому ИИ-ассистент вызывает
внешние «инструменты». Идея простая: у ИИ есть набор функций, которые он может вызвать по
имени с аргументами, получить структурированный ответ и продолжить работу. MCP стандартизирует,
как такие функции описываются и как они вызываются.

Сама по себе языковая модель умеет только генерировать текст — она не может напрямую сходить в
базу данных или изменить отчёт. MCP даёт ей канал к реальным действиям: вместо того чтобы выдать
пользователю «вот код, выполните сами», ИИ вызывает инструмент, сервер выполняет работу и
возвращает результат.

Как это выглядит на практике. ИИ вызывает инструмент (RPC-метод) с аргументами, а сервер
возвращает структурированный результат:

```
вызов:  component_crud(action="add", component_type="HsBarAMchartsChart", dataset_id=5)
ответ:  { "success": true, "component_idx": 3 }
```

Базовые понятия:

- **MCP-клиент** — программа, в которой работает ИИ (например, среда разработки или десктоп-приложение с ассистентом).
- **MCP-сервер** — отдельный процесс, который предоставляет инструменты. **Этот проект — такой сервер.**
- **Tool (инструмент)** — имя RPC-метода, который ИИ может вызвать (например, `component_crud`).
- **Action (действие)** — у большинства инструментов это первый параметр, задающий, что именно
  сделать: `component_crud` с `action="add"`, `action="update"`, `action="delete"`. Так один
  инструмент покрывает целый набор связанных операций.
- **Prompt (промпт)** — готовый многошаговый сценарий, который ИИ может развернуть (например, «создай дашборд из шаблона»).

Важно: наружный интерфейс между ИИ и MCP-сервером — это **не REST**. ИИ не дёргает HTTP-эндпоинты
по URL. Вместо этого клиент и сервер обмениваются сообщениями по **JSON-RPC 2.0**: ИИ вызывает
именованный RPC-метод (`tools/call`) и передаёт аргументы, а сервер отвечает структурированным
результатом. Транспорт по умолчанию — **stdio**: обмен идёт через стандартный ввод/вывод процесса
(потоки stdin/stdout), то есть через «трубу» между клиентом и сервером, а не по сети. Подробности —
в [protocol-and-rpc.md](protocol-and-rpc.md).

## Кто участвует в работе

| Участник | Роль |
|---|---|
| **ИИ-ассистент** | Решает, что построить, и вызывает инструменты сервера |
| **MCP-сервер (этот проект)** | Принимает RPC-вызовы, валидирует входные данные, собирает корректные запросы и обращается к API портала |
| **HTTP-API портала** | Обрабатывает запросы от MCP-сервера, выполняет операции над отчётами, датасетами и источниками, отдаёт результат в JSON |
| **БД портала** | Хранит отчёты, датасеты, конфигурации компонентов и источники данных |
| **Фронтенд портала** | Получает JSON-конфиг компонента от портала и рендерит его как интерактивный виджет в браузере |

Поток выглядит так:

```
ИИ-ассистент
   │  JSON-RPC 2.0 (вызов инструмента), транспорт stdio
   ▼
MCP-сервер (этот проект)
   │  HTTP-вызовы к API портала
   ▼
HTTP-API портала ──► БД портала (хранение)
                 └─► Фронтенд портала (рендер отчёта в браузере)
```

Поток данных одного конфига такой: **MCP-сервер создаёт или изменяет JSON-конфиг → портал хранит
его в БД → фронтенд читает этот JSON и рисует виджет в браузере**. Именно поэтому сервер знает,
какие ключи конфигурации читает рендер: без правильных ключей собранный JSON не отрисуется.

### Чем общение MCP-сервера с порталом отличается от обычного REST

Ниже уровня MCP сервер обращается к **HTTP-API портала**, но это не чистый ресурсный REST.
Почти все обращения идут через `POST /v1/api/...`, а сама операция указывается **в теле запроса**:
например, поле `command` со значением `"create"` или `"update"`, либо передача целевого объекта и
метода. То есть это диспетчеризация по действию (action/command dispatch) поверх HTTP, а не
маршрутизация по URL и HTTP-глаголам, как в классическом REST.

## Что сервер даёт ИИ

Теоретически ИИ мог бы обращаться к API портала напрямую. Но «сырые» вызовы портала требуют
точных идентификаторов, полных JSON-тел и знания внутренних форматов — на этом легко ошибиться.
ИИ нужен **семантический** слой: «добавь столбчатую диаграмму по полю X» вместо «собери вот такой
JSON на сотни строк и отправь его».

Поэтому MCP-сервер — это **прослойка с доменными знаниями**. Она:

- предоставляет **высокоуровневые инструменты** вместо сырых вызовов портала;
- **валидирует** входные данные и подсказывает, чего не хватает (в ответе об ошибке приходят недостающие параметры, ожидаемые типы и пример вызова);
- **собирает корректную конфигурацию** компонентов из простых параметров;
- знает соответствие «дружелюбная настройка → реальный ключ конфигурации, который читает рендер»;
- по умолчанию работает в безопасном **readonly**-режиме: доступны только чтение и проверка
  (список, получение, валидация, экспорт). Создание, изменение и удаление включаются явным
  запуском сервера в режиме записи (флаг `--readwrite`). Подробнее о режимах — в
  [../../GLOSSARY.md](../../GLOSSARY.md).

Инструменты сгруппированы по доменам — отдельно операции над отчётами, над компонентами, над
фильтрами, над датасетами, над источниками данных, над стилями и так далее. Большинство
инструментов принимает параметр действия (`action`): один вызываемый метод покрывает набор
связанных операций (`add`, `update`, `delete`, `list` и т. д.). Некоторые специализированные
инструменты (например, запрос к данным `dataset_query` или проверка SQL `sql_query_validate`)
параметра `action` не имеют — у них собственный набор параметров под свою задачу.

## Доменная модель портала

Чтобы пользоваться инструментами MCP-сервера, нужно понимать структуру данных портала ModusBI —
именно этими сущностями оперируют все инструменты. Достаточно знать четыре:

```
Report (отчёт = дашборд)
 ├─ Component[]  — список виджетов (график, таблица, карта, KPI, фильтр, текст…)
 │    └─ config: { … }   ← JSON-конфиг виджета; влияет на визуальные настройки
 ├─ Layout       — координаты, ширина и высота каждого виджета
 └─ CSS          — стили уровня отчёта

Dataset (семантический слой = сохранённый запрос, отдающий таблицу данных)
 └─ ПРИВЯЗЫВАЕТСЯ к компонентам: поля датасета → оси и значения виджета

Datasource (подключение к внешней БД-источнику)
 └─ на нём строятся датасеты
```

- **Report** = отчёт, он же **дашборд** — контейнер виджетов. См. [../../GLOSSARY.md](../../GLOSSARY.md).
- **Component** = **виджет**. У каждого есть тип (график, таблица, карта, KPI, фильтр, текст и т. д.) и конфигурация. См. [../../GLOSSARY.md](../../GLOSSARY.md).
- **Dataset** = **семантический слой**: сохранённый запрос, который отдаёт таблицу данных для виджетов. См. [../../GLOSSARY.md](../../GLOSSARY.md).
- **Datasource** = подключение к внешней базе данных, на котором строятся датасеты. См. [../../GLOSSARY.md](../../GLOSSARY.md).

Типичный сценарий «с нуля»: создать отчёт → создать датасет → добавить компонент → добавить
фильтр → применить стили. Порядок здесь не случаен: **датасет должен существовать до компонента**,
потому что компонент привязывается к датасету и берёт из него данные для визуализации. Если
добавить компонент к несуществующему датасету, отображать ему будет нечего.

Для частых случаев есть готовые шаблоны дашбордов, которые разворачиваются одним вызовом.
