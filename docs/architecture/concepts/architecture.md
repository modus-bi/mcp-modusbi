# Архитектура: слои системы и уровни визуальной настройки

Этот документ даёт обзор того, как устроена система целиком: какие в ней слои, кто за что
отвечает, что именно делает MCP-сервер, и какими тремя способами настраивается внешний вид
компонента отчёта. Детали обмена сообщениями между слоями вынесены в отдельный документ —
[protocol-and-rpc.md](protocol-and-rpc.md).

Аудитория — разработчик, аналитик или интегратор, которому нужна общая карта системы перед
погружением в конкретные инструменты.

---

## 1. Четыре слоя

Запрос проходит сверху вниз через четыре слоя. Каждый слой решает свою задачу и общается
только с соседними.

```
┌─────────────────────────────────────────────────────────────────┐
│ 1. ИИ-КЛИЕНТ (ассистент)                                          │
│    Решает, что построить. Вызывает инструменты сервера.           │
└───────────────────────────┬─────────────────────────────────────┘
                            │ JSON-RPC 2.0 поверх stdio
┌───────────────────────────▼─────────────────────────────────────┐
│ 2. MCP-СЕРВЕР (этот проект)                                       │
│    Принимает вызовы инструментов, проверяет аргументы,            │
│    собирает JSON-конфигурацию отчёта, обращается к порталу.       │
└───────────────────────────┬─────────────────────────────────────┘
                            │ HTTP, операция в теле запроса
┌───────────────────────────▼─────────────────────────────────────┐
│ 3. HTTP-API ПОРТАЛА                                               │
│    Хранит отчёты, датасеты, подключения. Принимает и отдаёт JSON. │
│    Это «источник истины» для конфигов отчётов.                    │
└───────────────────────────┬─────────────────────────────────────┘
                            │ тот же JSON отчёта
┌───────────────────────────▼─────────────────────────────────────┐
│ 4. БАЗА ДАННЫХ И ОТРИСОВКА (рендер)                               │
│    Портал хранит данные в БД, а его интерфейс читает JSON-конфиг  │
│    компонентов и рисует их в браузере.                            │
└─────────────────────────────────────────────────────────────────┘
```

Коротко о каждом слое:

- **ИИ-клиент** — ассистент, который принимает решение, какой отчёт или компонент нужен,
  и вызывает инструменты сервера. Он не знает ни про HTTP портала, ни про устройство БД —
  только про набор инструментов, которые ему отдал сервер.
- **MCP-сервер** — этот проект. Принимает вызовы от ассистента, проверяет аргументы,
  собирает корректную JSON-конфигурацию отчёта и передаёт её порталу. Подробнее — в разделе 2.
- **HTTP-API портала** — серверное приложение, где хранятся отчёты, датасеты и подключения
  к данным. Для MCP-сервера это «источник истины»: отчёт целиком хранится на портале.
- **База данных и отрисовка** — портал держит данные в БД, а его веб-интерфейс читает
  JSON-конфигурацию компонентов и превращает её в видимое изображение (графики, таблицы,
  карты). Этот шаг отрисовки называется **рендером**.

Граница ответственности этого проекта проходит между слоями 2 и 3: MCP-сервер записывает
корректный JSON и кладёт его в портал. Как именно этот JSON выглядит на экране, решает
отрисовка на слое 4. Поэтому «значение записано в конфиг» и «значение видно на экране» —
два разных факта: бывает, что настройка сохранена верно, но для данного типа компонента
не имеет видимого эффекта либо игнорируется отрисовкой. Это и есть **рендер-контракт** —
проверка результата по тому, что реально нарисовано в браузере, а не только по содержимому
конфига (см. [../../GLOSSARY.md](../../GLOSSARY.md)).

### Чем отличаются протоколы между слоями

Две стрелки на схеме — это два разных протокола, и путать их не нужно:

- **ИИ-клиент → MCP-сервер** — это **JSON-RPC 2.0** поверх стандартного ввода-вывода (stdio).
  Здесь нет URL-адресов и HTTP-глаголов; инструменты вызываются как удалённые процедуры по имени.
- **MCP-сервер → портал** — это **HTTP**, но не классический ресурсный REST: операция
  кодируется не HTTP-глаголом и URL-путём, а полем в теле запроса (диспетчеризация по имени
  команды). Почти все вызовы идут методом `POST`.

Полный разбор обоих протоколов с примерами сообщений — в [protocol-and-rpc.md](protocol-and-rpc.md).

## 2. Что делает MCP-сервер

MCP-сервер — это посредник между ассистентом и порталом. Его задача — превратить
высокоуровневый вызов инструмента (например, «добавь столбчатую диаграмму по такому-то
полю») в корректную JSON-конфигурацию отчёта и сохранить её на портале.

### Инструменты и действия

Сервер отдаёт ассистенту набор **инструментов** (tools). Каждый инструмент покрывает целую
группу операций над одной сущностью и принимает первым аргументом `action`, который выбирает
конкретную операцию. Например, `component_crud(action="add", ...)` добавляет компонент, а
`component_crud(action="delete", ...)` удаляет. Такой инструмент с диспетчеризацией по `action`
маршрутизирует вызов во внутренний обработчик нужного действия.

Сущности, с которыми работают инструменты:

- **отчёты** — контейнеры компонентов с их раскладкой и оформлением;
- **датасеты** — сохранённые запросы к данным (семантический слой), к которым привязываются
  компоненты;
- **компоненты** — отдельные виджеты внутри отчёта: графики, таблицы, карты, KPI-блоки,
  фильтры, текстовые блоки.

Определения этих терминов — в [../../GLOSSARY.md](../../GLOSSARY.md).

Жизненный цикл компонента не ограничивается добавлением и удалением: дополнительные операции
над компонентами вынесены в отдельные инструменты — `component_filters` (фильтры и каскадные
связи между компонентами), `component_axes` (оси, вычисляемые поля, привязки) и
`component_styling` (визуальное оформление). Все они устроены по тому же принципу
диспетчеризации по `action`, что и `component_crud`.

### Сборка JSON-конфигурации компонента

Когда ассистент добавляет компонент, сервер собирает его JSON-конфигурацию (config) в два этапа:

1. **Сборка «скелета».** По типу компонента и переданным полям данных сервер строит стартовую
   конфигурацию: оси, привязку полей к значениям и категориям, агрегацию, дефолты, характерные
   для этого типа.
2. **Точечная доводка.** Поверх скелета применяются переопределения из `config_overrides` —
   словаря вида `{слаг: значение}`. Сервер раскладывает каждый слаг по нужному адресу внутри
   config и проверяет значение.

После этого сервер сохраняет результат на портале. Поскольку портал хранит отчёт целиком,
запись обычно устроена как «прочитать актуальный отчёт → внести правку → записать отчёт
обратно». Именно поэтому операции читают текущее состояние перед записью.

## 3. Три уровня визуальной настройки компонента

Внешний вид компонента настраивается тремя способами — от самого простого к самому гибкому.
Их можно комбинировать.

### Уровень 1. Атомарные параметры

Отдельные именованные аргументы инструмента, например `legend_visible` или `bg_color`. Это
самый простой способ: покрывает частые случаи и не требует знать внутреннее устройство config.

```
component_crud(action="add",
               report_id=...,
               component_type="HsBarAMchartsChart",
               dataset_id=...,
               category_field="region",
               value_field="dead_count",
               aggregation="sum",
               legend_visible=True)
```

### Уровень 2. config_overrides (слаги)

Словарь `{слаг: значение}`, передаваемый в инструмент. Слаг — это короткое плоское имя одной
настройки; сервер сам раскладывает его в нужный адрес внутри config. Это основной способ
точечной кастомизации: он даёт доступ к большому набору настроек, недоступных через атомарные
параметры.

```
component_crud(action="update",
               report_id=...,
               component_idx=0,
               config_overrides={"legend.position": "bottom"})
```

Здесь слаг `legend.position` сервер записывает в соответствующее место config компонента.

### Уровень 3. Пресеты

Именованные наборы слагов, которые применяют пачку настроек разом: `minimal`, `presentation`,
`dashboard`, `dark`, `print`, `kpi`. Пресет удобен, когда нужно быстро привести компонент к
типовому виду, не перечисляя слаги по отдельности.

Соотношение уровней простое: пресет задаёт основу, поверх неё ложатся атомарные параметры и
слаги, и при совпадении выигрывает более точечная настройка. То есть явно переданные
`config_overrides` имеют приоритет над тем, что задал пресет.

## 4. Один процесс — один портал

MCP-сервер обслуживает **один** портал на процесс. Адрес портала и учётные данные сервер
берёт из переменных окружения при запуске. Чтобы работать с несколькими порталами, заводят
несколько записей в конфигурации MCP-клиента — по одной на портал, каждая со своими
переменными окружения. Параллельные процессы сервера не делят между собой состояние и
подключение.

Режимы запуска сервера (`readonly` по умолчанию и `readwrite` для операций изменения) описаны
в [../../start/server-modes.md](../../start/server-modes.md).
