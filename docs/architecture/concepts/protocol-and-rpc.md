# Протокол: MCP — это JSON-RPC, а не REST

Этот документ объясняет, по какому протоколу ИИ-ассистент общается с MCP-сервером ModusBI, и почему этот протокол — **не REST**. Дополнительно разбирается, что происходит «этажом ниже»: как MCP-сервер вызывает HTTP-API портала ModusBI, и почему этот HTTP-API тоже нельзя называть «чистым ресурсным REST».

Аудитория — разработчик или интегратор, которому нужно понимать, какие сообщения реально летают между слоями.

---

## 1. Три слоя, которые легко спутать

Когда говорят «протокол», обычно смешивают три разные вещи. Разнесём их сразу — дальше весь документ опирается на это разделение.

```
┌──────────────────────────────────────────────────────────────┐
│  Прикладной слой: MCP                                         │
│  (определяет конкретные методы: tools/list, tools/call, …)   │
├──────────────────────────────────────────────────────────────┤
│  Формат сообщений: JSON-RPC 2.0                              │
│  (определяет конверт: jsonrpc, id, method, params)           │
├──────────────────────────────────────────────────────────────┤
│  Транспорт: stdio (стандартный ввод/вывод процесса)          │
│  (доставляет байты между процессами)                         │
└──────────────────────────────────────────────────────────────┘

  ИИ-ассистент ──────────► MCP-сервер ──────────► Портал ModusBI
  (JSON-RPC / stdio)       (HTTP / action-command)
```

- **Транспорт** — это то, что физически переносит байты. У MCP-сервера ModusBI это **stdio**: клиент запускает сервер как дочерний процесс и обменивается с ним строками через стандартный ввод/вывод. Транспорт ничего не знает о содержимом — он только доставляет.
- **Формат сообщений** — это **JSON-RPC 2.0**. Он задаёт форму каждого сообщения (конверт), но сам ничего не доставляет и не знает, что внутри.
- **Прикладной слой** — это **MCP**. Он определяет, какие именно методы существуют (`initialize`, `tools/list`, `tools/call`, `prompts/list`, `prompts/get`) и что они означают.

Ключевая мысль: **наружный интерфейс MCP-сервера к ИИ — это JSON-RPC 2.0, а не REST**. Здесь нет URL-путей, нет HTTP-глаголов `GET`/`POST`/`PUT`/`DELETE`, нет ресурсов по адресам. Есть только именованные удалённые вызовы процедур (RPC).

## 2. JSON-RPC 2.0 на пальцах

Вся спецификация JSON-RPC 2.0 умещается в пару страниц. Она описывает **только форму сообщений** — четыре типа.

### 2.1. Request — запрос с ожиданием ответа

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": { "name": "report_operations", "arguments": { "action": "list" } }
}
```

> `tools/call` — это имя RPC-метода для вызова инструмента; что такое «инструмент» и откуда берётся этот метод, подробно разбирается в разделе 3.

Поля конверта:
- `jsonrpc` — всегда строка `"2.0"` (версия формата).
- `method` — имя вызываемой процедуры (строка).
- `id` — идентификатор для сопоставления запроса с ответом (число или строка).
- `params` — аргументы. Для JSON-RPC это «чёрный ящик»: любой допустимый JSON. Что внутри — решает прикладной слой.

### 2.2. Response — успешный ответ

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": { "content": [ { "type": "text", "text": "{...}" } ], "isError": false }
}
```

Ответ возвращается с тем же `id`, что и запрос, — так клиент понимает, на что именно пришёл ответ. Поля `content` и `isError` внутри `result` — это уже оформление прикладного слоя MCP (см. раздел 3.1), а не часть самого JSON-RPC.

### 2.3. Error — ответ с ошибкой

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": { "code": -32602, "message": "Invalid params", "data": { "details": "..." } }
}
```

В одном ответе бывает либо `result`, либо `error` — никогда оба сразу. Коды ошибок — единственная семантика, которую вводит сам JSON-RPC:

| Код    | Что значит        |
|--------|-------------------|
| -32700 | Parse error (битый JSON) |
| -32600 | Invalid Request (нет `method` и т. п.) |
| -32601 | Method not found |
| -32602 | Invalid params (не прошла валидация аргументов) |
| -32603 | Internal error |

### 2.4. Notification — сообщение без ответа

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/initialized"
}
```

Отличие от Request — **нет поля `id`**. Сервер на такое сообщение не отвечает. Используется для уведомлений (например, клиент сообщает, что закончил инициализацию).

И это всё. Других типов сообщений в JSON-RPC 2.0 нет: ни сессий, ни подписок, ни механизма обнаружения методов. Всё остальное — надстройки прикладного слоя.

## 3. MCP — прикладной слой поверх JSON-RPC

JSON-RPC сам по себе не знает ни про какие «инструменты» или «промпты». Это просто формат обмена сообщениями — конверт, доставляемый транспортом. Смысл вкладывает **MCP (Model Context Protocol)** — прикладной протокол, который определяет, какие именно методы существуют (например, `tools/list`, `tools/call`) и что они означают в контексте работы ИИ.

В контексте MCP **инструмент (tool)** — это функция, доступная ИИ-ассистенту для вызова. У инструмента есть имя, описание и набор параметров со схемой. Ассистент сначала получает список инструментов через метод `tools/list`, а затем вызывает нужный через `tools/call`.

**Tool — это RPC-метод, а не HTTP-эндпоинт.** Когда ИИ хочет что-то сделать на портале ModusBI, он не делает HTTP-запрос на URL. Он отправляет JSON-RPC сообщение с `method: "tools/call"` и указывает имя инструмента в `params.name`. То есть все инструменты вызываются через **один** JSON-RPC метод `tools/call`, а конкретный инструмент выбирается по имени внутри `params`.

Как клиент узнаёт, какие инструменты вообще есть и какие у них параметры? Через встроенный в MCP механизм обнаружения — метод `tools/list`. Сервер обязан на него ответить списком инструментов, у каждого из которых есть имя, описание и JSON Schema параметров.

### 3.1. Живая сессия с MCP-сервером ModusBI

**Шаг 1. Рукопожатие (handshake).** Клиент представляется и узнаёт возможности сервера:

```json
→ {"jsonrpc":"2.0","id":1,"method":"initialize",
   "params":{"protocolVersion":"2024-11-05","capabilities":{"tools":{}},
             "clientInfo":{"name":"<имя-клиента>","version":"1.0"}}}

← {"jsonrpc":"2.0","id":1,"result":{
    "protocolVersion":"2024-11-05",
    "serverInfo":{"name":"modusbi","version":"1.0"},
    "capabilities":{"tools":{"listChanged":true},"prompts":{"listChanged":true}}}}
```

**Шаг 2. Клиент подтверждает готовность (notification, без `id`):**

```json
→ {"jsonrpc":"2.0","method":"notifications/initialized"}
```

**Шаг 3. Клиент запрашивает список инструментов со схемами:**

```json
→ {"jsonrpc":"2.0","id":2,"method":"tools/list"}

← {"jsonrpc":"2.0","id":2,"result":{
    "tools":[
      {
        "name":"report_operations",
        "description":"Manage reports (list/get/create/update/delete/...)",
        "inputSchema":{
          "type":"object",
          "properties":{
            "action":{"type":"string","title":"Action"},
            "report_id":{"anyOf":[{"type":"integer"},{"type":"null"}],"default":null}
          },
          "required":["action"]
        }
      }
    ]}}
```

Поле `inputSchema` в ответе содержит **JSON Schema** параметров инструмента — стандартный формат описания структуры данных. Его содержимое — это описание, по которому ИИ узнаёт, какие аргументы принимает инструмент. Для самого JSON-RPC это просто произвольный JSON внутри `result`; смысл ему придаёт прикладной слой MCP.

**Шаг 4. ИИ вызывает инструмент.** Перед отправкой он сверяется со схемой (видит `required: ["action"]`, подставляет строку):

```json
→ {"jsonrpc":"2.0","id":3,"method":"tools/call",
   "params":{"name":"report_operations","arguments":{"action":"list"}}}

← {"jsonrpc":"2.0","id":3,"result":{
    "content":[{"type":"text","text":"{\"success\":true,\"count\":604,\"items\":[...]}"}],
    "isError":false}}
```

Результат инструмента приходит как текст внутри `result.content` — это контракт MCP, а не «тело HTTP-ответа». Обёртку `content`/`isError` MCP-сервер формирует автоматически: код инструмента возвращает обычный объект, а оформление результата в этот вид добавляет фреймворк (см. раздел 4).

### 3.2. Что именно едет по транспорту stdio

Для stdio-транспорта одно JSON-RPC сообщение — это одна строка JSON, завершённая переводом строки. Когда ИИ зовёт `report_operations(action="list")`, серверу на стандартный ввод приходит одна строка:

```
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"report_operations","arguments":{"action":"list"}}}
```

А сервер отвечает одной строкой на стандартный вывод. Вот и весь «транспорт»: строка JSON = одно сообщение, разделитель — перевод строки. Никакого HTTP здесь нет.

## 4. Откуда берётся JSON Schema инструментов

Схемы параметров не пишутся вручную. Сервер ModusBI построен на **FastMCP** (фреймворк для создания MCP-серверов на Python), и схема каждого инструмента генерируется автоматически из сигнатуры обычной Python-функции.

Каждый инструмент — это асинхронная функция (в Python-коде сервера; MCP-клиент этого не видит), помеченная декоратором. Например:

```python
@mcp.tool()
async def instance_operations(
    action: InstanceAction,
) -> dict[str, Any]:
    """Get information about the configured portal instance..."""
```

Здесь `InstanceAction` — это `Literal["list", "get_active"]`: строгий перечень допустимых значений, который FastMCP превратит в JSON Schema с `enum`. Многие инструменты сервера устроены богаче — у них, помимо `action`, есть набор опциональных параметров. Например, упрощённая сигнатура `report_operations`:

```python
@mcp.tool()
async def report_operations(
    action: str,
    report_id: int | None = None,
    name: str | None = None,
    ...
) -> dict[str, Any]:
    """Manage reports (list/get/create/update/delete/...)."""
```

Что FastMCP делает с такой функцией:

1. **Имя функции** становится именем инструмента (`name` в `tools/list`).
2. **Docstring** становится описанием инструмента (`description`).
3. **Сигнатура** превращается в JSON Schema параметров (`inputSchema`).

Правила превращения типов в схему простые:

| Python                          | JSON Schema |
|---------------------------------|-------------|
| `action: str` (без значения по умолчанию) | `{"type":"string"}` + попадает в `required` |
| `name: str \| None = None`      | `{"anyOf":[{"type":"string"},{"type":"null"}],"default":null}` |
| `report_id: int \| None = None` | `{"anyOf":[{"type":"integer"},{"type":"null"}],"default":null}` |
| `aggregation: str = ""`         | `{"type":"string","default":""}` |
| параметр **без** значения по умолчанию | попадает в массив `required` |
| параметр **со** значением по умолчанию  | не в `required`, значение кладётся в `default` |

Отсюда характерный для этого сервера приём: у инструмента один обязательный параметр `action` (без значения по умолчанию) и много опциональных. В схеме это даёт `required: ["action"]`, а конкретное действие (`list`, `get`, `create`, …) ИИ выбирает строкой.

Одно ограничение стоит держать в голове: параметр типа `dict` превращается в `{"type":"object","additionalProperties":true}` — то есть «любой объект». Структуру вложенного словаря из одной только схемы ИИ не узнает — JSON Schema здесь не описывает поля произвольного объекта на уровне параметра; её приходится описывать словами в docstring инструмента и в промптах MCP (готовых многошаговых сценариях для ассистента).

## 5. Слой ниже: MCP вызывает HTTP-API портала

Когда инструмент выполняется, MCP-сервер не работает с базой данных напрямую. Он обращается к **HTTP-API портала ModusBI** — тому же API, что использует веб-интерфейс портала. То есть полная картина потока выглядит так:

```
ИИ ──JSON-RPC / MCP (stdio)──► MCP-сервер ──HTTP (action/command)──► портал ModusBI ──► БД
```

Левая стрелка (ИИ → MCP-сервер) — это JSON-RPC, разобранный выше. Правая стрелка (MCP-сервер → портал) — это HTTP. И вот тут важная деталь: **HTTP-API портала — не чистый ресурсный REST.** Всё, что описано ниже в этом разделе, относится к **внутреннему HTTP-API портала**, а не к интерфейсу MCP к ИИ — со стороны ассистента эти детали скрыты (см. раздел 5.2).

### 5.1. Почему это не «чистый REST»

В каноническом ресурсном REST операция кодируется HTTP-глаголом, а объект — URL-путём: `GET /reports/35`, `PUT /reports/35`, `DELETE /reports/35`. У портала ModusBI устроено иначе: почти всё — это `POST /v1/api/...`, а сама операция указывается **в теле запроса**. Это паттерн «действие/команда поверх HTTP» — то есть диспетчеризация по имени действия (action/command-dispatch): операция выбирается не по HTTP-глаголу или URL-пути, а по значению поля в теле запроса.

Тело стандартного вызова имеет фиксированную форму: объект, над которым работаем, команда и данные.

```json
POST /v1/api/datasets
{
  "object":  { "name": "datasets" },
  "command": { "name": "create" },
  "data":    [ { "name": "...", "parentID": 27 } ]
}
```

```json
POST /v1/api/datasets
{
  "object":  { "name": "datasets" },
  "command": { "name": "update" },
  "data":    [ { "id": 500, "query": "SELECT ...", "fields": [ ... ] } ]
}
```

То есть `create` и `update` — это не разные HTTP-глаголы (`POST` vs `PUT`), а один и тот же `POST /v1/api/datasets` с разным значением `command.name`. Имя объекта (`datasets`, `datasources`, `reports`, `recordsets`) в `object.name` указывает, над чем работаем; идентификатор экземпляра передаётся в `object.id` или внутри `data`.

Конкретные примеры реальных вызовов, которые делает MCP-сервер:

**1. Запрос данных — параметры выборки в теле, не в URL.**
Получить данные из набора данных нельзя через `GET /datasets/241/rows`. Выборка делается через объект `recordsets`: параметры (`select`, `where`, `group`, `order`, `limit`) кладутся в тело. Прямой SQL к источнику данных порталом не поддерживается вовсе — данные доступны только через этот механизм по `dataset_id`. Внутри MCP это абстрагировано инструментом `dataset_query`, у которого уже есть параметры `select`, `where`, `group`, `order`, `limit`.

**2. Операция как имя команды.**
В коде MCP вызовы к порталу строятся как «объект + команда», например `api_call("datasources", "check.conn")` (проверка соединения) или `api_call("datasets", "create")`. Значение команды (`check.conn`, `create`, `update`) попадает в поле `command.name` стандартного тела — это и есть операция; она не выражается через URL-путь к ресурсу.

**3. Особый случай — `recordsets.create`.**
Команда `recordsets.create` — единственное исключение из стандартной структуры `{object, command, data}`: параметры выборки кладутся в тело **напрямую** (без обёртки `object`/`command`), а сам объект и его идентификатор кодируются в URL-пути (`POST /v1/api/recordsets/{dataset_id}`). Это сделано под формат API выборки данных; во всех остальных вызовах действует стандартная структура с обёрткой.

Заметна аналогия: «объект + команда» в HTTP-вызовах портала по духу близко к «`method` + `params`» в JSON-RPC. Это тоже диспетчеризация по имени действия, просто доставляется поверх HTTP, а не как JSON-RPC сообщение.

### 5.2. Что это значит для интегратора

- **Не ищите REST-семантику в API портала.** Не рассчитывайте, что `GET` на URL вернёт ресурс, а `DELETE` его удалит. Операция почти всегда в поле `command.name` тела запроса.
- **Идемпотентность и кэширование по HTTP-глаголу не работают.** Раз почти всё — это `POST`, привычные REST-гарантии (безопасность `GET`, кэшируемость) к этому API неприменимы.
- **MCP-сервер скрывает эту разницу.** Как интегратор поверх MCP вы работаете не с URL портала, а с инструментами через `tools/call`. MCP-сервер автоматически собирает корректные тела запросов за вас (структуру `{object, command, data}`, формат `recordsets` и поля `datasets`). Знать её полезно для отладки и понимания ограничений.
- **Многое — один эндпоинт с разными командами.** Если в логах или трассировке вы видите много `POST /v1/api/datasets` или `POST /v1/api/reports` — это нормально: разные действия идут на один путь, различаясь полем `command.name`.

## 6. Сравнение трёх моделей

| Аспект | Ресурсный REST | HTTP-API портала ModusBI (action/command) | JSON-RPC / MCP (к ИИ) |
|--------|----------------|-------------------------------------------|------------------------|
| Где живёт операция | в HTTP-глаголе (`GET`/`POST`/`PUT`/`DELETE`) | в теле запроса (`command.name = "create"` / `"update"` / `"check.conn"`) | в поле `method` сообщения |
| Где живёт объект | в URL-пути (`/reports/35`) | в `object.name` (`datasets`, `recordsets`, `reports`) + id в `object.id` или `data` | в `params` (`name` инструмента + `arguments`) |
| Транспорт | HTTP | HTTP | stdio (между процессами) |
| HTTP-глаголы | по смыслу операции | почти всегда `POST` | не используются |
| Обнаружение возможностей | вне протокола (OpenAPI и т. п.) | вне протокола | встроено: `tools/list`, `prompts/list` |
| Описание параметров | OpenAPI/JSON Schema (отдельно) | формат полей тела (по документации) | JSON Schema в `inputSchema` (часть ответа) |
| Корреляция запрос↔ответ | по HTTP-соединению | по HTTP-соединению | по полю `id` |
| Главный потребитель | веб- и мобильные клиенты | веб-интерфейс портала и MCP-сервер | ИИ-ассистент (вызов инструментов) |

Резюме одной фразой: **наружу MCP-сервер говорит на JSON-RPC (вызовы процедур по имени), внутрь — обращается к HTTP-API портала, где операция закодирована в поле `command.name` тела; ни тот, ни другой интерфейс не является чистым ресурсным REST.**

## 7. Краткий итог

- Интерфейс между ИИ и MCP-сервером ModusBI — это **JSON-RPC 2.0** поверх транспорта **stdio**, а не REST.
- JSON-RPC описывает только **конверт сообщения** (`jsonrpc`, `id`, `method`, `params` / `result` / `error`) и набор кодов ошибок. Содержимое `params` для него — чёрный ящик.
- **MCP** — прикладной слой поверх JSON-RPC. Инструменты (tools) — это **RPC-методы**, вызываемые через `tools/call`, а не HTTP-эндпоинты. Список инструментов и их схемы клиент получает через `tools/list`.
- Схемы параметров инструментов **FastMCP генерирует автоматически** из сигнатур Python-функций: имя функции → имя инструмента, docstring → описание, типы аргументов → JSON Schema.
- Ниже MCP-сервер вызывает **HTTP-API портала ModusBI** — но это **не чистый ресурсный REST**: операция кодируется в теле запроса (`command.name = "create"/"update"/"check.conn"`) в рамках стандартной структуры `{object, command, data}`, почти всё идёт через `POST /v1/api/...`.

Дополнительные материалы по архитектуре сервера и работе с данными — в соседних документах раздела `concepts/`.
