# Слаги компонентов: три имени одной настройки

У каждого компонента отчёта (графика, таблицы, KPI-блока, карты, фильтра) есть набор
настроек: положение легенды, толщина столбца, цвет фона, угол подписей осей и так далее.
Одна и та же настройка в проекте встречается под **тремя разными именами** — в зависимости
от того, кто на неё смотрит:

- **UI-контрол** — как настройка подписана в панели настроек портала (русское название);
- **слаг (slug)** — короткое плоское имя, которым настройку задаёт ассистент;
- **JSON-путь** — адрес, по которому значение реально лежит в конфигурации компонента.

Этот документ объясняет, что такое слаг, почему имён три, как ассистент применяет настройки
через `config_overrides` и почему иногда настройка «применилась», но на экране ничего не
изменилось. Здесь — концепция; механика кода (как именно сервер раскладывает слаг в JSON)
живёт в модуле описания слагов сервера (`app/tools/config_schema.py`) и в обработчиках
операций над компонентами.

Перед чтением полезно знать базовые термины — `config`, `компонент`, `слаг`,
`config_overrides`, `рендер` — они определены в [../../GLOSSARY.md](../../GLOSSARY.md).

---

## 1. config — это «истина» настроек

У каждого компонента есть **config** — вложенный JSON-объект, в котором хранятся все его
настройки: цвета, легенда, оси, подписи, привязки полей данных. Портал отдаёт этот config
браузеру, и именно по нему компонент рисуется на экране. То есть config — это «истина»: что
записано в config, то и определяет, как выглядит компонент.

Внутри config сгруппирован в разделы, а в разделах лежат конкретные ключи:

```json
{
  "type": "barChart",
  "legend":       { "position": "bottom-center", "visible": true },
  "styleCommons": { "columnWidth": 0.4 },
  "axes": [
    { "type": "categories", "tickangle": 45 },
    { "type": "values",     "showgrid": true }
  ]
}
```

Реальные пути внутри config бывают длинными и называются неочевидно
(`styleCommons.columnWidth`, `axes[categories].tickangle`). Запоминать и писать их вручную —
больно и легко ошибиться. Поэтому ассистент работает не с сырым JSON, а со **слагами**.

---

## 2. Слаг — короткое имя настройки

**Слаг** — это плоское строковое имя одной настройки, например `legend.position` или
`visuals.columnWidth`. Ассистент не кликает мышкой в браузере: он передаёт серверу словарь
`{слаг: значение}`, а сервер кладёт значение в нужное место config. Так ассистент задаёт
настройки, не зная длинных JSON-путей.

У каждого слага в сервере есть «паспорт»: тип значения (`bool`/`int`/`float`/`str`/`color`/
`enum`), границы для чисел, список допустимых значений для перечислений, адрес записи в config
и к каким типам компонентов слаг применим. Благодаря этому сервер при применении слага
**проверяет** значение (тип, диапазон, перечисление) — чего сырой JSON-путь сам по себе не
делает.

## 3. Три имени одной настройки

Возьмём одну настройку — положение легенды — и посмотрим на её три имени:

```
        ПОРТАЛ                  АССИСТЕНТ                  БРАУЗЕР (рендер)
   ┌──────────────┐        ┌──────────────┐         ┌──────────────────┐
   │  UI-контрол  │        │     слаг     │         │    JSON-путь     │
   │ «Положение   │   ≈    │ legend.      │    ≈    │ config.legend.   │
   │  легенды»    │        │ position     │         │ position         │
   │ (секция      │        │              │         │                  │
   │  «Легенда»)  │        │              │         │                  │
   └──────┬───────┘        └──────┬───────┘         └────────▲─────────┘
          │ человек кликает       │ сервер применяет         │
          └───────────────────────┴──────────────────────────┘
                        всё пишет в ОДИН config
```

- **UI-контрол** — что задаёт человек в панели настроек портала: «поставь легенду снизу».
  Подписан по-русски и сгруппирован в секцию («Легенда», «Столбцы», «Подписи»).
- **Слаг** — чем оперирует ассистент: `legend.position`.
- **JSON-путь** — куда значение реально ложится: `config.legend.position`.

И панель настроек портала (когда человек кликает), и ассистент (когда применяет слаг) пишут в
**один и тот же config**. Браузер рисует компонент, читая только config — ему всё равно, кто
туда записал значение.

### Совпадают ли три имени

В простом случае все три имени совпадают по «хвосту»: UI-контрол «Положение легенды», слаг
`legend.position`, JSON-путь `config.legend.position`. Но часто слаг назван иначе, чем
JSON-ключ. Пример — толщина столбца:

```
UI «Толщина столбца»  →  слаг visuals.columnWidth  →  JSON config.styleCommons.columnWidth
                                   └──────────── имена разные ──────────────┘
```

Здесь слаг и JSON-путь называются по-разному, но это **не ошибка**: сервер знает соответствие
и пишет значение туда, куда нужно. Важно лишь помнить: если искать настройку в сыром JSON по
имени слага, её можно не найти — она лежит под другим ключом.

Бывает и так, что отличаются не только имена, но и единицы измерения. Для `visuals.columnWidth`
ассистент задаёт толщину в процентах (целое 10..100), а в config значение попадает уже долей
(0..1): сервер при записи делит на 100, то есть `40` превращается в `0.4`. Это ещё одна
причина не сверять config с тем, что вы передали слагу, «в лоб».

## 4. Как ассистент применяет настройки: config_overrides

Чтобы изменить настройки компонента, ассистент передаёт инструменту редактирования словарь
**`config_overrides`** вида `{слаг: значение}`. Сервер проходит по словарю, проверяет каждое
значение и записывает его в соответствующее место config.

> Примеры ниже даны в псевдокоде Python — для наглядности. На самом деле ассистент не
> вызывает функции напрямую: он отправляет серверу JSON-RPC-запросы (как именно — см.
> [protocol-and-rpc.md](protocol-and-rpc.md)). Имена инструментов и параметров при этом те же.

Применить слаги можно как при добавлении компонента, так и на уже существующем:

```python
# при добавлении компонента
component_crud(action="add", report_id=669, component_type="HsBarAMchartsChart",
               dataset_id=531, category_field="region", value_field="dead_count",
               config_overrides={"legend.position": "bottom-center",
                                 "axes.categoryLabelAngle": 45})

# на существующем компоненте (component_idx — порядковый номер виджета, считается с нуля)
component_crud(action="update", report_id=669, component_idx=2,
               config_overrides={"visuals.columnWidth": 40})
```

Сквозной пример — «поставить легенду снизу» — даёт один и тот же результат двумя путями:

- **Человек в браузере:** настройки → секция «Легенда» → Положение: «Снизу» → Сохранить.
  Портал записывает `config.legend.position = "bottom-center"`.
- **Ассистент через слаг:** `config_overrides={"legend.position": "bottom-center"}`.
  Сервер кладёт то же самое в `config.legend.position`.

Оба пути дают одинаковый config, и браузер рисует легенду снизу.

> В UI написано «Снизу», но в config это `"bottom-center"` — не «снизу» и не «bottom».
> Поэтому ассистенту мало знать имя слага: нужно знать и **допустимые значения**. Их сервер
> хранит в «паспорте» слага и проверяет при применении.

Список доступных слагов и их допустимые значения ассистент получает у самого сервера через
действие листинга слагов инструмента `component_crud`.

## 5. Почему бывает рассинхрон: слаг применился, а рендер не изменился

Частая ситуация: ассистент задал слаг, сервер ответил «успех», но компонент на экране **не
изменился**. Ключевая мысль: **«значение записано в config» ≠ «пользователь увидел эффект».**
«Успех» означает только, что сервер положил значение в config; нарисует ли его браузер — это
отдельный вопрос.

Причины рассинхрона:

- **Слаг пишет не в тот ключ.** Сервер кладёт значение в один ключ config, а браузер при
  отрисовке читает другой. Значение «легло» в config, но визуально ничего не меняется — браузер
  его просто не видит. Простыми словами: настройка тихо проигнорирована.
- **Слага для настройки нет.** Контрол есть в панели портала, но соответствующего слага в
  сервере не сделали. Через `config_overrides` такую настройку не задать — только вручную в
  браузере.
- **Настройке нужны подходящие данные.** Некоторые контролы «оживают» только при определённой
  форме данных. Например, диаграмма-дерево требует числовой идентификатор; со строковым она не
  строится. Это не ошибка, а требование к форме данных.
- **Сервер заблокировал опасное значение.** Часть комбинаций настроек способна сломать
  отрисовку всей страницы отчёта. Сервер ставит защиту и не записывает заведомо ломающие
  значения — слаг при этом не применяется намеренно.

Из-за того, что запись в config и видимый результат — разные вещи, итог настройки проверяют не
по факту записи, а по тому, что реально нарисовано в браузере. Этот принцип — что источник
истины для проверки настройки именно отрисовка, а не содержимое config — называется
**рендер-контракт**; его краткое определение есть в [../../GLOSSARY.md](../../GLOSSARY.md), а
подробный разбор с примерами — в [render-contract.md](render-contract.md).

## 6. Шпаргалка «кто есть кто»

```
СЛОЙ            ЧТО ЭТО                          ПРИМЕР
─────────────────────────────────────────────────────────────────────────
Человек         кликает в браузере               двигает «Толщина столбца» = 40
UI-контрол      русское имя + секция             «Толщина столбца» / секция «Столбцы»
       │
Ассистент       команда серверу                  config_overrides={"visuals.columnWidth": 40}
Слаг            короткое имя настройки            visuals.columnWidth
       │
Сервер          слаг → JSON-путь (+ проверка)     знает адрес записи и допустимые значения
       │
config (JSON)   истина настроек                  config.styleCommons.columnWidth = 0.4
       │
Браузер         читает config и рисует           столбцы стали нужной ширины
```

(Толщина задаётся слагом в процентах — `40`, а в config попадает долей — `0.4`; см. раздел 3.)
