# Фильтры в отчётах: рабочие паттерны и критичные правила

Документ для аналитика, который собирает дашборд и хочет, чтобы фильтры
действительно ограничивали данные на всех виджетах. Здесь описаны два проверенных
способа разместить фильтры, обязательное правило их привязки к данным, каскадные
(зависимые) фильтры и обход одной частой визуальной проблемы — наложения
выпадающих списков.

Базовые термины (отчёт, компонент, датасет, фильтр, alias) — в
[словаре терминов](../../GLOSSARY.md). Общий рабочий процесс сборки дашборда —
в [руководстве аналитика](../../start/analyst.md).

---

## Из чего состоит фильтр

Фильтр на дашборде — это отдельный компонент типа «Контейнер с фильтрами».
В системе он называется типом `HsFilterControlPanel` (именно это значение
передаётся в `component_crud(action="add", component_type="HsFilterControlPanel")`),
а внутри его конфигурации поле `config.chartType` имеет значение
`FilterControlPanel`. Внутри у компонента есть ось `filters`, на которую
добавляются одно или несколько полей датасета. Каждое поле описывается,
в частности, парой:

- `name` — техническое имя поля в датасете (используется в запросах к данным);
- `alias` — человекочитаемое имя (например, `Регион`, `Период`). Именно `alias`
  служит ключом, по которому фильтр связывается с общим состоянием отчёта.

Все поля контейнера фильтров автоматически становятся **общими фильтрами отчёта**
(в конфигурации это объект `globalFilters` на уровне отчёта; ключ записи —
тот самый `alias` поля). Общий фильтр — это «единое выбранное значение», которое
видит весь отчёт.

Локально сам компонент-фильтр хранит свой выбор в `config.selectedValue`, но для
синхронизации со всеми остальными виджетами фронтенд читает выбранное значение
из общего состояния отчёта (`globalFilters[alias].selected`). Поэтому ключом
связи везде выступает `alias` — он должен быть одинаковым во всех местах, где
фильтр используется.

Главная мысль, из которой следует всё остальное: фильтр-компонент сам по себе
только показывает выпадающий список и хранит выбор. Чтобы выбор повлиял на
конкретный график или таблицу, это же поле должно быть добавлено и в фильтруемый
компонент (см. раздел «Критичное правило» ниже).

## Добавление поля в фильтр

Поле на ось фильтра добавляется инструментом `component_filters`, действие
`filter_field_add`. Минимально нужны:

```text
component_filters(
  action="filter_field_add",
  report_id=<id отчёта>,
  component_idx=<индекс компонента-фильтра>,
  field_name="region",        # техническое имя поля в датасете (параметр так и
                              #   называется — field_name, не name и не value_field)
  alias="Регион",             # человекочитаемое имя (ключ общего фильтра)
  field_type="string",        # "string" | "number" | "date" | "datetime" | "boolean"
  dataset_id=<id датасета>
)
```

Правила, которые экономят время:

- **Всегда передавайте `dataset_id` явно.** Без него инструмент пытается вывести
  датасет из самого компонента, и на data-компонентах это не всегда срабатывает.
- **Всегда задавайте русский `alias`.** Если `alias` не передать, в списке фильтра
  пользователь увидит техническое имя поля (`region`) вместо «Регион». `alias`
  ещё и служит ключом связи с общими фильтрами отчёта, поэтому он должен быть
  осмысленным и одинаковым везде, где этот фильтр используется.
- `field_type` определяет вид виджета: `string` — список значений, `number` —
  числовой фильтр, `date` / `datetime` — выбор даты или периода, `boolean` —
  переключатель «да/нет».

Вид отображения фильтра (выпадающий список, чекбоксы, кнопки, слайдер, выбор
периода) и режимы фильтрации детально описаны в справочнике компонента
«Контейнер с фильтрами» (тип `HsFilterControlPanel`; см. [reference/filter-panel.md](reference/filter-panel.md)).

## Паттерн A: раздельные фильтры (1 фильтр = 1 компонент)

Самый распространённый и предсказуемый способ. Каждый фильтр — это отдельный
компонент «Контейнер с фильтрами» с одним полем на оси `filters`. Компоненты
выстраиваются горизонтально в ряд над содержимым отчёта.

```text
┌──────────────────────────────────────────────────────────┐
│ [Период ▼]   [Регион ▼]   [Категория ▼]   [Менеджер ▼]   │  ← ряд фильтров
├──────────────────────────────────────────────────────────┤
│  KPI   KPI   KPI   KPI                                    │
├──────────────────────────────────────────────────────────┤
│            Графики и таблицы                              │
└──────────────────────────────────────────────────────────┘
```

Когда применять:

- Фильтров немного и они часто используются. На практике в один ряд комфортно
  помещается 4–6 фильтров — точное число зависит от ширины экрана и длины
  подписей; технического ограничения на количество фильтров нет.
- Нужно визуально выделить ключевые фильтры в шапке дашборда.
- Каждый фильтр должен иметь собственную ширину и оформление.

Раскладка (значения ширины зависят от ширины сетки отчёта — числа ниже даны для
наглядности): на N фильтров делят доступную ширину поровну, каждый фильтр ставят
в верхний ряд (`y=0`) с небольшой высотой. Типовое оформление одного фильтра:

- тонкая рамка: `outline.enabled=true`, `outline.width=1`,
  `outline.color="rgba(179,179,179,1)"`;
- белый фон: `bgColor="rgba(255,255,255,1)"`;
- небольшие боковые отступы: `margin.l=5`, `margin.r=5`.

Эти параметры задаются как обычные настройки компонента через MCP-слаги
`config_overrides` (см. [../concepts/components-json-slugs.md](../concepts/components-json-slugs.md)).
Слаг — это удобное короткое имя для вложенного пути в JSON-конфигурации: например,
слаги `outline.enabled`, `outline.width`, `outline.color` соответствуют JSON-пути
`config.outline.{enabled, width, color}`.

## Паттерн B: единый компонент с несколькими полями

Здесь все фильтры живут в одном компоненте «Контейнер с фильтрами»: на его ось
`filters` добавляется несколько полей (несколько вызовов `filter_field_add` с тем
же `component_idx`).

```text
┌───────────────────────────────────────┐
│  Фильтры                              │
│   Период:    [ ▼ ]                    │
│   Регион:    [ ▼ ]                    │
│   Категория: [ ▼ ]                    │
│   Менеджер:  [ ▼ ]                    │
├───────────────────────────────────────┤
│            Содержимое отчёта           │
└───────────────────────────────────────┘
```

Когда применять:

- Фильтры логически образуют один блок «параметры отбора».
- Удобно иметь одну общую рамку и (при необходимости) одну кнопку «Применить»
  на весь набор.

Практическое замечание по высоте: для четырёх и более полей компоненту нужна
увеличенная высота (ориентировочно `h≥9`), иначе поля не помещаются. Для паттерна A
такой проблемы нет — каждый фильтр невысокий.

Какой паттерн выбрать: если фильтры самостоятельные и их немного — берите
паттерн A (раздельные); он гибче по раскладке и оформлению. Если это единый блок
параметров отбора — паттерн B.

## Критичное правило: привязать поле и к фильтру, и к каждому виджету

Это самая частая причина ситуации «фильтр показывает значения, а данные не
меняются».

Контейнер фильтров отвечает только за выбор значения и хранение его в общих
фильтрах отчёта. Чтобы выбор реально ограничил данные конкретного виджета, **то же
самое поле должно быть добавлено на ось `filters` этого виджета**. Иначе виджет
просто не знает, что по нему нужно фильтровать.

Поэтому `filter_field_add` вызывают:

1. один раз — на компоненте-фильтре (`HsFilterControlPanel`);
2. **и отдельно — на каждом data-компоненте**, который должен фильтроваться:
   на каждом графике, таблице, KPI-блоке, карте.

Используйте один и тот же `alias` во всех вызовах — именно совпадение `alias`
связывает выбор в фильтре с фильтрацией виджетов через общие фильтры отчёта.

```text
# 1) поле в самом фильтре
component_filters(action="filter_field_add", report_id=R, component_idx=<фильтр>,
                  field_name="region", alias="Регион", field_type="string", dataset_id=D)

# 2) то же поле на КАЖДОМ фильтруемом виджете
component_filters(action="filter_field_add", report_id=R, component_idx=<график>,
                  field_name="region", alias="Регион", field_type="string", dataset_id=D)
component_filters(action="filter_field_add", report_id=R, component_idx=<таблица>,
                  field_name="region", alias="Регион", field_type="string", dataset_id=D)
component_filters(action="filter_field_add", report_id=R, component_idx=<KPI>,
                  field_name="region", alias="Регион", field_type="string", dataset_id=D)
# ... и так для карты и остальных data-компонентов
```

Симптом нарушения этого правила: в выпадающем списке фильтра значения есть и
выбираются, но цифры на графиках и в таблицах не реагируют. Проверьте, что поле
добавлено на ось `filters` всех нужных виджетов, а `alias` везде одинаковый.

## Каскадные (зависимые) фильтры

Каскад — это цепочка, где выбор в родительском фильтре сужает список значений в
дочернем (и обновляет зависимые виджеты). Типичный пример:

```text
Регион  →  Город  →  Точка продаж
```

При выборе региона дочерний фильтр «Город» показывает только города этого региона,
а «Точка продаж» — только точки выбранного города.

Зависимость задаётся при добавлении поля параметром `depends_on`, в который
передаётся `alias` родительского фильтра. Родительский фильтр должен уже
существовать в отчёте (быть добавленным раньше).

```text
# Родитель
component_filters(action="filter_field_add", report_id=R, component_idx=<фильтр1>,
                  field_name="region", alias="Регион", field_type="string", dataset_id=D)

# Дочерний фильтр зависит от "Регион"
component_filters(action="filter_field_add", report_id=R, component_idx=<фильтр2>,
                  field_name="city", alias="Город", field_type="string",
                  dataset_id=D, depends_on="Регион")
```

Что происходит под капотом: в записи дочернего фильтра в общих фильтрах отчёта
появляется зависимость (поле `filterBy`), указывающая на родителя. После этого
портал при смене значения родителя перезапрашивает список значений дочернего
фильтра с учётом выбора родителя.

Как проверить результат: при успешной настройке каскада вызов возвращает
`cascade_set: true`. Если родитель не найден в отчёте или зависимость некорректна
(например, фильтр ссылается сам на себя), вернётся `success: false` с пояснением
в поле `error` — тогда каскад не настроен.

Замечания:

- Фильтр не может зависеть сам от себя — `depends_on` должен ссылаться на другой
  `alias`.
- Каскад настраивает только связь между фильтрами. Чтобы выбранные значения
  ограничивали данные виджетов, по-прежнему действует критичное правило выше:
  поля должны быть добавлены и на data-компоненты.

## Наложение выпадающих списков и его исправление

Раскладка дашборда устроена так, что каждый компонент помещается в свою ячейку
сетки, и эта ячейка визуально «изолирована» от соседних (технически — браузер
создаёт для неё отдельный контекст наложения слоёв из-за CSS-трансформаций
раскладки). Из-за этого выпадающий список фильтра, который должен раскрываться
поверх соседних виджетов, может оказаться обрезанным нижестоящим компонентом или
спрятанным под ним. Настройка «слоя» через позицию компонента (`zIndex`) эту
ситуацию не решает: она не превращается в нужное CSS-правило.

Рабочее исправление — поднять слой именно тех ячеек сетки, в которых находится
контейнер фильтров, добавив отчёту правило CSS:

```text
style_operations(
  action="update",
  report_id=<id отчёта>,
  css=".react-grid-item:has(.hsFilterControlPanel) { z-index: 100 !important; }"
)
```

Селектор использует современный CSS-псевдокласс `:has()` (поддерживается
актуальными версиями браузеров) — он выбирает ячейки сетки, внутри которых лежит
контейнер фильтров. Рекомендуется добавлять это правило **в каждый отчёт, где
есть контейнеры фильтров** — тогда списки гарантированно раскрываются поверх
содержимого.

Важная особенность инструмента: действие `update` у `style_operations`
**заменяет весь CSS отчёта целиком**, а не дописывает к существующему. Если в
отчёте уже есть свой CSS (например, оформление темы), сначала получите текущий
стиль действием `get`, затем объедините его с правилом z-index и отправьте
объединённый текст одним вызовом `update`. Иначе ранее заданное оформление будет
затёрто.

## Короткий чек-лист

- Поле фильтра добавлено через `filter_field_add` с явными `dataset_id` и русским
  `alias`.
- То же поле (с тем же `alias`) добавлено на КАЖДЫЙ фильтруемый виджет: график,
  таблицу, KPI, карту.
- Раздельные фильтры (паттерн A) выстроены горизонтально; единый блок (паттерн B)
  имеет достаточную высоту под все поля.
- Для зависимых фильтров задан `depends_on` с `alias` родителя, родитель добавлен
  раньше, а ответ вернул `cascade_set: true`.
- В отчёт добавлено CSS-правило z-index для контейнеров фильтров; при наличии
  своего CSS он сначала получен через `get` и объединён, а не перезаписан.
