# Форматы данных для специальных возможностей компонентов

Большинство компонентов рисуется по простой раскладке датасета: одно строковое поле
для категорий, одно числовое поле для значений, агрегация суммой. Но у ряда компонентов
есть возможности, которые **оживают только при особой форме данных**. Если данные
поданы обычной таблицей, такая возможность остаётся пустой: цвет не появляется, шкала
рисует значения по умолчанию, граф не строится.

Этот файл собирает такие случаи. Для каждого — какой формат датасета нужен, почему
именно такой, и как выглядит структура строк. Конкретные имена полей здесь условные:
подставляйте свои.

Базовые термины (`датасет`, `компонент`, `config`, `слаг`, `рендер`) определены в
[словаре терминов](../../GLOSSARY.md). Каталог типов компонентов и матрица выбора —
в [каталоге типов компонентов](README.md). Принцип слагов и привязки полей —
в [концепции слагов](../concepts/components-json-slugs.md).

> Стандартная раскладка по умолчанию: `category_field` — строковое поле,
> `value_field` — числовое поле, агрегация `sum`. Рецепты ниже отступают от неё там,
> где это необходимо для конкретной возможности.

## Сводная таблица

| Возможность | Компонент | Что нужно в данных | Зачем |
|---|---|---|---|
| Цвет и размер пузырьков | Пузырьковая (`HsBubbleAMchartsChart`) | две числовые метрики + отдельное числовое поле размера | без второй метрики и поля размера пузырьки не позиционируются и не масштабируются |
| Цветовые зоны (отсечки) | Спидометр (`HsSpeedometerV2AMcharts`) | значение + поля-границы зон | без границ шкала рисует две зоны по умолчанию |
| Подсветка плиток | Плиточная карта (`HsTilemapChart`) | канонические имена субъектов РФ | плитки сопоставляются с встроенным справочником субъектов по точному имени |
| Граф «родитель → потомок» | Дерево связей (`HsTreeGraph`) | числовой идентификатор узла и числовой идентификатор родителя | строковый идентификатор ломает построение графа |
| Сравнение объектов | Сравнительная (`HsComparisonChart`) | «длинный» формат: объект, название показателя, значение | компонент ожидает по строке на пару «объект + показатель» |
| Несколько серий | Столбчатая, линейная, area | поле серии (≥2 значений) | без поля серии данные образуют один ряд — стек, многоцветная легенда и пер-серийная стилизация не работают |

## Пузырьковая диаграмма: цвет и размер

Пузырьковая диаграмма показывает три измерения одновременно: положение по X,
положение по Y и размер пузырька. Это значит, что одной метрики недостаточно —
нужны как минимум две числовые метрики для координат и отдельное числовое поле
для размера.

**Зачем такой формат.** Первая числовая метрика задаёт вертикальную координату,
вторая — горизонтальную. Поле размера управляет диаметром пузырька. Если подать
только одну метрику, пузырькам некуда встать по второй оси и нечем задать размер —
диаграмма не отрисуется.

**Структура данных.** Каждая строка — один пузырёк:

| объект | метрика_y | метрика_x | размер |
|---|---|---|---|
| Объект A | 1200 | 340 | 56 |
| Объект B | 870 | 510 | 23 |
| Объект C | 1540 | 290 | 81 |

**Привязка.** Две числовые метрики передают в значения (`value_field` с двумя полями
через запятую: первое идёт на ось Y, второе — на ось X), поле размера — отдельным
параметром размера (одно поле, без запятой).

> Цветовое кодирование пузырьков по данным (отдельная числовая шкала, окрашивающая
> пузырьки) — возможность отрисовки, которую средствами добавления компонента через
> сервер пока не выставить. Поля для координат и размера задаются штатно.

## Спидометр: значение и отсечки зон

Спидометр рисует одно значение на круговой шкале «минимум — максимум» и может
делить шкалу на цветовые зоны (например, «низко / норма / высоко»). Границы этих
зон берутся из данных.

**Зачем такой формат.** Без полей-границ спидометр показывает шкалу с двумя зонами
по умолчанию — он не знает, где проходят пороги. Чтобы появились собственные
цветовые зоны, в значения добавляют дополнительные числовые поля, помеченные как
границы зон. В интерфейсе компонента это пометка типа поля «Отсечка» в полке значений:
такое поле подаётся не как обычная метрика, а как граница цветовой зоны.

**Структура данных.** Одна строка с основным значением и порогами:

| значение | порог_1 | порог_2 |
|---|---|---|
| 73 | 40 | 80 |

Здесь `значение` — стрелка спидометра, `порог_1` и `порог_2` — границы цветовых зон.

> «Отсечка» — это настройка типа поля в полке значений компонента (интерфейс портала).
> На уровне данных порог остаётся обычным числом; тип «граница зоны» назначается полю
> при настройке компонента.

## Плиточная карта: канонические имена субъектов

Плиточная карта (`HsTilemapChart`) раскладывает регионы России плитками и красит
их по числовой шкале. Чтобы плитка подсветилась, значение категории должно **точно
совпасть с каноническим именем субъекта РФ** из встроенного справочника карты.

**Зачем такой формат.** Соответствие «плитка → субъект» зашито в компонент. Он ищет
совпадение по полному имени субъекта. Если в данных имена районов, городов или
сокращённые/неточные написания, совпадений со справочником не будет — и все плитки
останутся серыми (нераскрашенными).

**Структура данных.** Категория — полное имя субъекта, значение — число для шкалы:

| субъект | показатель |
|---|---|
| Краснодарский край | 1820 |
| Республика Татарстан (Татарстан) | 1530 |
| г. Севастополь | 210 |

Имена должны соответствовать справочнику субъектов целиком, включая тип
(«край», «Республика …», «г. …»). Цветовая шкала интерполируется между минимумом
и максимумом показателя по всем плиткам.

## Древовидный граф: числовой идентификатор

Дерево связей (`HsTreeGraph`) строит граф «родитель → потомок». Каждый узел должен
иметь **числовой идентификатор**, и ссылка на родителя тоже должна быть числовой.

**Зачем такой формат.** Компонент обрабатывает идентификатор узла как число.
Строковый идентификатор приводит к ошибке преобразования и граф не строится. Поэтому
идентификаторы генерируют числами — например, нумерацией строк, а корень помечают
фиксированным числом с пустым родителем.

**Структура данных.** Корень — с пустым родителем; потомки ссылаются на идентификатор
родителя:

| id | parent_id | название | показатель |
|---|---|---|---|
| 0 | (пусто) | Все регионы | 9400 |
| 1 | 0 | Регион A | 5200 |
| 2 | 0 | Регион B | 4200 |

Пример запроса с числовой нумерацией строк для идентификаторов:

```sql
SELECT 0 AS id, NULL::int AS parent_id, 'Все регионы' AS name, SUM(value) AS metric
FROM source_table
UNION ALL
SELECT ROW_NUMBER() OVER (ORDER BY region) AS id,  -- числовой идентификатор узла
       0 AS parent_id,                              -- числовая ссылка на корень
       region AS name,
       SUM(value) AS metric
FROM source_table
GROUP BY region;
```

**Привязка.** Идентификатор узла идёт в категорию (`category_field`); ссылка на
родителя и числовой показатель — в значения (`value_field` с двумя и более полями
через запятую: первое — `parent_id`, остальные — показатели); агрегация — `none`.

## Сравнительная диаграмма: «длинный» формат (UNPIVOT)

Сравнительная диаграмма (`HsComparisonChart`) сопоставляет несколько объектов по
набору показателей. Она ожидает данные в «длинном» формате (UNPIVOT): **одна строка =
один объект + название одного показателя + его значение**.

**Зачем такой формат.** Обычная «широкая» таблица держит показатели в отдельных
колонках. Сравнительной диаграмме нужно, чтобы и объект, и название показателя были
значениями в строках — тогда она может перебрать пары «объект × показатель». Поэтому
широкую таблицу разворачивают в длинную через `UNION ALL`.

**Структура данных.** По строке на каждую пару «объект + показатель»:

| объект | показатель | значение |
|---|---|---|
| Регион A | Количество | 1200 |
| Регион A | Сумма | 340 |
| Регион B | Количество | 870 |
| Регион B | Сумма | 510 |

Пример разворота широкой таблицы в длинную:

```sql
SELECT region AS object, 'Количество' AS metric_name, SUM(count_value) AS metric_value
FROM source_table GROUP BY region
UNION ALL
SELECT region AS object, 'Сумма'      AS metric_name, SUM(sum_value)   AS metric_value
FROM source_table GROUP BY region;
```

**Привязка.** Поле объекта — в категорию (`category_field`); поле с названиями
показателей — в показатели (`column_fields`). Это **одно** строковое поле датасета,
значения которого — названия показателей («Количество», «Сумма»). Поле значений —
в значения (`value_field`, числовое). Два сравниваемых объекта выбираются как два
значения поля объекта.

## Мультисерийная линия (и стек на других графиках): поле серии

Линейная, столбчатая и area-диаграммы рисуют **несколько серий** только когда
в данных есть отдельное поле серии. Стекирование, многоцветная легенда и стилизация
отдельной серии опираются именно на это поле.

**Зачем такой формат.** Без поля серии данные образуют один ряд: одна линия, один
цвет в легенде, нечего складывать в стек и нечего адресовать при пер-серийной
стилизации. Чтобы получить несколько линий/серий, добавляют категориальное поле,
которое делит значения на серии, и подают данные в «длинном» виде — по строке на пару
«точка оси × серия».

**Структура данных (long-format).** По строке на каждую точку оси и каждую серию:

| период | серия | значение |
|---|---|---|
| 2023 | Регион A | 1200 |
| 2023 | Регион B | 870 |
| 2024 | Регион A | 1310 |
| 2024 | Регион B | 940 |

Здесь `период` — ось, `серия` — поле, разбивающее данные на отдельные линии,
`значение` — число. Каждое уникальное значение поля `серия` даёт свою серию на графике.

**Привязка.** Поле оси — в категорию (`category_field`); поле серии — в поле серии
(`series_field`); числовое поле — в значения (`value_field`).

> Поле серии (`series_field`) поддерживают столбчатая, линейная и area-диаграммы.
> На других типах оно игнорируется — для них применяют свои механизмы группировки
> (например, показатели сравнительной диаграммы).

> Пер-серийная стилизация (цвет, толщина линии, заливка для конкретной серии) через
> слаги адресует серию по точному значению поля серии — указанное значение должно
> совпадать со значением в данных буква в букву.
