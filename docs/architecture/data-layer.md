# Слой данных: датасеты, запросы, батчинг

Этот документ описывает, как MCP-сервер ModusBI работает с данными портала: что
такое датасет, как из него извлекаются строки, как проверяется SQL до создания
датасета и как несколько выборок объединяются в один вызов.

Аудитория — разработчик или аналитик, которому нужно понимать, откуда берутся
данные в отчёте и какими инструментами их получать. Термины (`датасет`,
`портал`, `Tool`, `Action`) определены в [словаре терминов](../GLOSSARY.md).

---

## 1. Где находится слой данных

Данные в ModusBI проходят через цепочку из четырёх уровней. Сверху — физическое
подключение к базе, снизу — конкретный график на дашборде.

```
Источник данных (подключение к СУБД)
    └── Датасет (SQL-запрос + описание полей = семантический слой)
            └── Выборка (запрос данных: фильтры, агрегация, сортировка)
                    └── Отчёт
                            └── Компонент (график, таблица, KPI)
```

- **Источник данных** — настроенное на портале подключение к конкретной СУБД
  (PostgreSQL, ClickHouse, MS SQL и другие). У него есть хост, порт, база, права.
- **Датасет** — именованный SQL-запрос поверх источника плюс описание полей
  (имя, тип, человекочитаемое название). Это и есть семантический слой.
- **Выборка** — конкретный запрос данных из датасета с фильтрами, группировкой и
  сортировкой. Отдельной сущности для хранения у выборки нет: это запрос, а не
  таблица. Каждый визуальный компонент внутренне формирует свою выборку.
- **Компонент** показывает результат выборки на дашборде.

Один датасет может питать множество компонентов; компонент привязывается к
датасету в момент создания.

---

## 2. Датасет как семантический слой

Датасет хранит две вещи: SQL-запрос для извлечения данных и список полей с их
типами и подписями. Технические имена колонок (`region`, `accident_count`)
приходят из SQL, а человекочитаемые названия (`Район`, `Количество ДТП`)
задаются отдельно — это и есть семантика поверх «сырых» колонок.

Каждое поле датасета имеет тип. Базовые типы:

| Тип | Назначение | Типичная агрегация |
|-----|------------|--------------------|
| `string` | строки: район, ФИО, категория | без агрегации (для категорий), `count` |
| `number` | числа: сумма, количество, цена | `sum`, `avg`, `min`, `max`, `count` |
| `date` | даты | `min`, `max` |
| `datetime` | дата со временем | `min`, `max` |
| `boolean` | логическое значение (да/нет) | `count` |

Тип поля определяет, как поле ведёт себя в компоненте: строковые поля идут в
категории, числовые — в значения с агрегацией, даты — в фильтры по периоду.

Обратите внимание: `file` и `image` — это **не типы полей**, а типы компонентов
рендеринга (ячейка показывает ссылку на файл или изображение). На уровне датасета
URL такого ресурса хранится в обычном поле типа `string`.

### Связь датасета с источником

Датасет ссылается на источник двумя разными значениями, которые легко спутать:

- идентификатор **подключения** — какое именно настроенное соединение использовать;
- идентификатор **типа драйвера** СУБД — он определяет SQL-диалект (PostgreSQL,
  ClickHouse, MS SQL и т.д.).

При создании датасета указывается только подключение (`datasource_id`); тип
драйвера сервер подставляет автоматически. Путать эти два значения не нужно — но
полезно знать, что они различны, потому что диалект SQL зависит именно от драйвера
источника.

### Инструменты для датасетов

Управление датасетами собрано в одном инструменте `dataset_operations`, где
конкретная операция выбирается параметром `action`. Чтение доступно всегда;
создание, изменение и удаление требуют запуска сервера в режиме `readwrite`
(см. [security-model.md](security-model.md)).

| Action | Что делает |
|--------|------------|
| `list` | список всех датасетов |
| `get` | полная информация: SQL-запрос и все поля |
| `fields_list` | только список полей с типами и подписями |
| `create` | создание «пустого» датасета без проверки SQL |
| `update` | изменение SQL, подписей полей, источника, RLS |
| `delete` | удаление датасета |

Точные имена действий и их параметры всегда можно уточнить прямо у инструмента
(`dataset_operations(action="help")`), не полагаясь на эту таблицу как на
исчерпывающую.

### Подписи полей: порядок имеет значение

Человекочитаемые названия полей задаются через параметр `field_aliases` действия
`update` — словарём вида «техническое имя → подпись и описание».

Важная особенность: подписи полей нужно задавать **до** того, как датасет
привязан к компонентам. Если поле уже используется в отчёте, портал возвращает
ошибку при попытке изменить его подпись или тип. Рабочий порядок такой:

1. создать датасет из SQL;
2. задать подписи полей (`field_aliases`);
3. только потом добавлять компоненты.

Если подписи нужно поправить на уже привязанном датасете — обычно проще создать
новый датасет с правильными подписями и перепривязать компоненты.

## 3. Создание датасета из SQL

Рекомендуемый способ создать датасет — инструмент `dataset_create_from_sql`. В
отличие от «пустого» `create`, он сам проверяет SQL и определяет структуру полей.
Внутри происходит четыре шага:

1. по указанному подключению определяется тип драйвера СУБД;
2. SQL проверяется без сохранения, из него извлекаются имена и типы полей;
3. создаётся датасет;
4. датасет дополняется SQL-запросом и набором полей.

После создания все поля имеют пустые подписи — их задают отдельным вызовом
`dataset_operations(action="update", field_aliases=...)`.

Несколько практических правил для SQL датасета:

- использовать `ORDER BY`, чтобы порядок категорий на графике был предсказуем
  (часы 0–23, месяцы 1–12, топ-N по убыванию);
- приводить результат `EXTRACT(...)` к целому, иначе часы и месяцы выводятся
  дробными;
- округлять проценты и средние значения;
- давать колонкам **латинские** имена в `AS`, а русские названия задавать потом
  через `field_aliases`. Русские имена прямо в SQL ломают техническое имя поля.

Подробные SQL-шаблоны (топ-N, динамика по месяцам, сравнение периодов) и формы
данных под конкретные возможности компонентов собраны в
[рецептах форматов данных](components/data-recipes.md).

## 4. Запрос данных из датасета

Получить строки из датасета можно только через выборку по идентификатору
датасета. **Прямой SQL к источнику данных через MCP не выполняется** — это
сознательное ограничение: единственная точка доступа к данным — датасет с его
проверенным SQL и описанными полями.

Основной инструмент — `dataset_query`. Он принимает идентификатор датасета и
необязательные параметры выборки:

- `select` — какие поля выбрать, с опциональной агрегацией;
- `where` — условия фильтрации;
- `group` — поля группировки;
- `order` — сортировка;
- `limit` — максимум строк (по умолчанию — порядка тысячи).

Пример агрегированного запроса: суммарное количество по менеджерам, отсортировать
по убыванию, взять верхние пять:

```python
dataset_query(
    dataset_id=241,
    select=[
        {"name": "ФИО менеджера"},
        {"name": "Количество (шт.)", "aggr": "sum"}
    ],
    group=[{"name": "ФИО менеджера"}],
    order=[{"name": "Количество (шт.)", "dir": "desc"}],
    limit=5
)
```

Пример с фильтром (`where` поддерживает упрощённый вид `op`/`value`):

```python
dataset_query(
    dataset_id=241,
    select=[
        {"name": "Наименование продукта"},
        {"name": "Количество (шт.)", "aggr": "sum"}
    ],
    where=[{"name": "ФИО менеджера", "op": "=", "value": "CEO"}],
    group=[{"name": "Наименование продукта"}],
    limit=10
)
```

### Функции агрегации

| Агрегация | Смысл |
|-----------|-------|
| `""` (пусто) | без агрегации — для категорий и группировок |
| `sum` | сумма |
| `avg` | среднее |
| `min` / `max` | минимум / максимум |
| `count` | количество строк |

### Операторы фильтрации

В `where` поддерживаются операторы `=`, `>=`, `<=`, `>`, `<`, `!=`, `like`,
`is null`, `is not null`. Для простых условий достаточно полей `op` и `value`; для
сложных (несколько значений, инверсия, логика AND/OR) есть полный формат с
`values`, `operators`, `not` и признаком объединения условий.

### Особенности результата, о которых стоит знать

- При агрегированных запросах портал может вернуть поля с внутренними именами
  вида `[values][0]`, `[values][1]` вместо исходных. Это штатное поведение;
  опознавать поля удобнее по их порядку в `select`.
- Сортировка `order` надёжно работает для простых выборок без агрегации. При
  агрегированных запросах фактический порядок строк может не совпадать с заданным
  — он зависит от СУБД источника. Если порядок критичен, закладывайте его в `ORDER
  BY` самого датасета.
- В ответе выборки тип полей не определяется (приходит как «неизвестно»). Чтобы
  узнать типы полей, используйте `dataset_operations(action="get"/"fields_list")`.

## 5. Батч-запросы

Когда дашборду нужно сразу несколько метрик из одного датасета (например, набор
KPI-карточек), эффективнее запросить их одним вызовом, а не серией отдельных.
Для этого есть инструмент `query_batch`: он принимает идентификатор датасета и
массив запросов, у каждого — свой `id` (для сопоставления результатов) и `params`
(те же `select` / `where` / `group` / `order` / `limit`).

```python
query_batch(
    dataset_id=241,
    queries=[
        {"id": "total_qty",
         "params": {"select": [{"name": "Количество (шт.)", "aggr": "sum"}]}},
        {"id": "by_manager",
         "params": {
             "select": [
                 {"name": "ФИО менеджера"},
                 {"name": "Количество (шт.)", "aggr": "sum"}
             ],
             "group": [{"name": "ФИО менеджера"}],
             "order": [{"name": "Количество (шт.)", "dir": "desc"}],
             "limit": 3
         }}
    ]
)
```

Ограничения и нюансы батча:

- все запросы выполняются к **одному** датасету;
- у каждого запроса обязателен уникальный `id`;
- число запросов за раз ограничено (в обычном режиме — порядка десятка, в
  демо-режиме меньше); точный предел сервер сообщает в ошибке при превышении;
- в отличие от `dataset_query`, `query_batch` передаёт `params` в портал как есть,
  без преобразования упрощённого формата. Если нужен упрощённый вид полей —
  используйте `dataset_query`.

## 6. Проверка источника и SQL до создания датасета

Перед тем как создавать датасет, полезно убедиться, что источник доступен и SQL
корректен. Для этого есть два инструмента.

`preflight_check_datasource` проверяет источник на двух уровнях: есть ли
соединение и проходит ли пробный запрос. Это помогает заранее отличить «нет сети /
неверные права» от «база отвечает, но запрос падает».

`sql_query_validate` проверяет конкретный SQL-запрос и возвращает структуру полей
(имена и типы) **без создания датасета**. Удобно, чтобы заранее увидеть, какие
поля даст запрос, и поймать синтаксическую ошибку.

```python
sql_query_validate(
    sql_query="SELECT id, name, amount FROM sales WHERE status = 'active' LIMIT 10",
    datasource_id=27
)
```

**Важно для безопасности.** Проверка не выполняется в песочнице: портал
валидирует SQL, **исполняя** его на «живом» источнике данных. Поэтому
MCP-сервер пропускает на портал только один SELECT-запрос (или
`WITH ... SELECT`): любые изменяющие данные конструкции (INSERT, UPDATE, DELETE,
DROP, ALTER, CREATE, TRUNCATE и т.п.), как и несколько инструкций сразу,
отклоняются ещё на стороне MCP-сервера — до того, как запрос дойдёт до базы. Это
защищает источник от случайной мутации данных при «проверке». Если имя колонки
совпадает с SQL-ключевым словом — заключите его в двойные кавычки.

Внутри и `sql_query_validate`, и preflight-проверка обращаются к порталу через
вызов `POST /v1/api/query`, передавая SQL и идентификатор источника в теле
запроса. Это обращение в стиле команды-действия поверх HTTP, а не отдельный
REST-ресурс на каждый запрос. Как именно устроено общение между MCP-сервером и
порталом, описано в [концепции протокола](concepts/protocol-and-rpc.md).

## 7. Безопасность данных (RLS)

Этот раздел описывает только ограничение видимости строк на уровне датасета.
Общая модель доступа MCP-сервера (режимы запуска, права, демо-лимиты) разобрана
в отдельном документе — [security-model.md](security-model.md).

У датасета можно включить ограничение видимости строк (Row Level Security): тогда
к каждому запросу автоматически добавляется заданное WHERE-условие. В условии
доступна подстановка идентификатора текущего пользователя, так что каждый
пользователь видит только свои строки. Включается это через `update` датасета
(параметры `rls` и `query_rls`). Подробнее о модели доступа — в
[security-model.md](security-model.md).

## 8. Типовой цикл подготовки данных

Собирая всё вместе, обычный путь от пустого места до данных в дашборде выглядит
так:

1. **Проверить источник** — `preflight_check_datasource`.
2. **Проверить SQL** (по желанию) — `sql_query_validate`.
3. **Создать датасет** — `dataset_create_from_sql`.
4. **Задать подписи полей** — `dataset_operations(action="update", field_aliases=...)`.
5. **Проверить данные** — `dataset_query` с небольшим `limit`.
6. **Привязать компоненты** — после того как подписи уже на месте.

После этого данные готовы к визуализации. Как разложить их под конкретные
возможности компонентов — см. [рецепты форматов данных](components/data-recipes.md).
