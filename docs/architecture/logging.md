# Логирование

Сервер ведёт операционный лог через стандартный модуль Python `logging`. Лог нужен для диагностики
(что сервер делал, где возникла ошибка) и для аудиторского следа операций записи.

## Куда пишутся логи

**Всё в `stderr`.** `stdout` зарезервирован под протокол MCP (JSON-RPC 2.0), поэтому любой посторонний
вывод в stdout сломал бы обмен с клиентом. Отсюда два правила в коде:

- все логгеры пишут в `sys.stderr`;
- во время инициализации stdout временно перенаправляется в stderr (`contextlib.redirect_stdout`),
  чтобы случайный `print()` при старте не попал в протокол.

Своих файлов лога сервер не создаёт — он пишет в stderr, а дальше поток подхватывает **MCP-клиент**:
например, Claude Desktop сохраняет stderr подключённых серверов в свои лог-файлы; в Claude Code (CLI) он
виден в выводе/логах клиента; при запуске из терминала — прямо в консоли.

## Уровень и формат

Задаются флагами при запуске сервера:

| Флаг | Значения | По умолчанию | Назначение |
|---|---|---|---|
| `--log-level` | `DEBUG` / `INFO` / `WARNING` / `ERROR` | `INFO` | Подробность лога. |
| `--log-format` | `text` / `json` | `text` (или env `MODUSBI_LOG_FORMAT`) | Формат строки лога. |

- **text** (по умолчанию) — человекочитаемо: `<время> [INFO] app.tools.dataset_operations: <сообщение>`.
- **json** — одна JSON-строка на запись, для production-агрегации (ELK / Loki / Datadog): поля
  `ts`, `level`, `logger`, `msg`, при ошибке — `exc`, для аудиторских записей — `audit`.

Имя логгера совпадает с модулем (`logging.getLogger(__name__)`), например `app.tools.report_operations`
— по нему видно, какой инструмент сделал запись.

## Что логируется

- **Старт сервера**: выбранный режим безопасности (`readwrite` — `WARNING`, `demo`/`readonly` —
  `INFO`), переопределение режима потолком `--security-ceiling`, проблемы аутентификации к порталу.
- **Предупреждения и ошибки инструментов**: например, отказ валидации или недоступность портала.
- **Аудиторский след операций записи**: ключевые create-события помечаются префиксом `audit:` в
  тексте сообщения — `audit:report_create`, `audit:dataset_create`. В формате `json` такие записи
  дополнительно получают поле `"audit": true`, что удобно для фильтрации аудиторского следа в системе
  сбора логов. Это **не** журнал отмены (откатить операцию нельзя, см. [../../DISCLAIMER.md](../../DISCLAIMER.md)),
  но даёт трассируемость: что и когда было создано.

## Чего нет «из коробки»

- Отдельного файла лога, ротации и отправки во внешний сервис — это делается средствами платформы
  развёртывания поверх stderr (перенаправление в файл, `journald`, сборщик логов клиента).
- Подробной трассировки каждого вызова инструмента на уровне `INFO` — обычный поток компактный; для
  детальной диагностики запускайте с `--log-level DEBUG`.
