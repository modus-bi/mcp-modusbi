# Расширение сервера: слаг, билдер, инструмент, промпт

Этот документ — практическая «механика» для контрибьюторов: как добавить новый слаг,
билдер компонента, инструмент (tool) или промпт, как заново сгенерировать справочные
таблицы и что проверить локально перед коммитом.

Документ предполагает, что вы уже понимаете базовые понятия проекта. Концепция слагов
и того, как плоское имя настройки превращается в путь внутри JSON-конфигурации, разобрана
в [concepts/components-json-slugs.md](concepts/components-json-slugs.md). Термины
(слаг, config, рендер, отчёт, компонент) — в [../GLOSSARY.md](../GLOSSARY.md).

Общий принцип работы: вносите маленькое проверяемое изменение, затем сразу прогоняйте
относящийся к нему тест. Не копите крупные правки без проверки.

---

## Где что лежит

| Файл | За что отвечает |
|---|---|
| `app/tools/config_schema.py` | словарь слагов `SLUG_SCHEMA` и функция применения слагов к конфигу |
| `app/tools/builders.py` | функции-билдеры, собирающие стартовый `config` каждого типа компонента; множество `NO_DATASET_TYPES` |
| `app/tools/component_crud.py` | добавление/обновление/удаление компонентов, диспетчер типов |
| `app/server.py` | объявление инструментов (`@mcp.tool`) и промптов (`@mcp.prompt`) |
| `app/prompts.py` | тексты промптов и диспетчер их сборки |
| `scripts/` | генераторы справочных таблиц (`gen_slug_json_table.py` и др.) и сверки с фронтендом |
| `app/tests/` | тесты (`pytest`) |

## Рецепт A. Добавить слаг (настройку компонента)

Слаг — короткое плоское имя одной настройки. Все слаги описаны в одном месте: словарь
`SLUG_SCHEMA` в `app/tools/config_schema.py`.

### Шаг 1. Понять, какой ключ конфига читает отрисовка

Слаг имеет смысл только тогда, когда фронтенд портала действительно читает тот ключ
`config`, куда слаг пишет значение. Поэтому сначала определите точный путь внутри
`config`, который влияет на картинку (а не просто сохраняется). Это и есть «адрес назначения»
слага.

Здесь работает понятие рендер-контракта (подробно —
[concepts/render-contract.md](concepts/render-contract.md)). Коротко: сервер может
корректно записать значение в `config`, но фронтенд при отрисовке способен его не
использовать — тогда настройка для данного типа компонента не даёт видимого эффекта, и
такой слаг бесполезен. Окончательную проверку даёт только браузер.

### Шаг 2. Добавить запись в `SLUG_SCHEMA`

Запись слага — это его «паспорт»: тип значения, границы, целевой путь в `config` и при
необходимости преобразования. Пример:

```python
"section.niceName": {
    "type": "int",                        # тип значения
    "default": 10,                        # значение по умолчанию
    "min": 0, "max": 100,                 # границы для чисел
    "json_path": "styleCommons.realKey",  # куда реально пишется значение в config
    "path_write": True,                   # предпочтительный универсальный способ записи
    # "value_map": {...},                 # дружелюбное значение → значение фронта
    # "invert": True,                     # фронт хранит обратный смысл
    "applies_to": ["lineChart"],          # если настройка только для отдельных типов
},
```

Поля паспорта (в том же порядке, что и в примере):

| Поле | Значение |
|---|---|
| `type` | тип значения: `bool` / `int` / `float` / `str` / `color` / `enum` / `any` |
| `default` | значение по умолчанию |
| `min` / `max` | границы для чисел (проверяются при валидации) |
| `values` | список допустимых значений для `enum` |
| `json_path` | куда писать внутри `config` |
| `path_write` | `True` ⇒ писать строго по `json_path` универсальным механизмом |
| `value_map` | словарь «дружелюбное значение → значение, ожидаемое фронтом» |
| `invert` | `True` ⇒ фронт хранит обратный смысл (записывается `not value`) |
| `applies_to` | список типов компонентов, к которым слаг применим (пусто = общий) |
| `deprecated` | строка-причина; такой слаг при применении пропускается |

#### Когда нужны `value_map` и `invert`

Это два независимых преобразования значения перед записью. Применяйте их, когда
«дружелюбное» значение, удобное ассистенту, не совпадает с тем, что хранит фронтенд.

`value_map` — перевод значения по словарю. Нужен, когда ассистенту удобнее передавать
понятный вариант, а фронт ожидает технический:

```python
"colors.theme": {
    "type": "enum",
    "values": ["светлая", "тёмная"],
    "value_map": {"светлая": "light", "тёмная": "dark"},  # фронт ожидает "light"/"dark"
    "json_path": "colorScheme",
    "path_write": True,
},
```

`invert` — логическая инверсия булева значения. Нужен, когда смысл слага и смысл ключа
конфига противоположны (например, слаг говорит «показывать сетку», а ключ хранит
«скрывать сетку»):

```python
"axes.showGrid": {
    "type": "bool",
    "invert": True,                # ассистент передаёт True → в config пишется False
    "json_path": "axes[categories].hideGrid",
    "path_write": True,
},
```

### Шаг 3. Как слаг применяется к JSON: `apply_slug_overrides`

Функция `apply_slug_overrides(config, overrides, component_type)` в `config_schema.py`
принимает словарь `{слаг: значение}` и раскладывает значения по `config`. Она возвращает
**новый** `config` и не мутирует вход. Порядок обработки каждого слага (упрощённо):

```
для каждого (slug, value):
  1) слаг помечен deprecated      → пропустить
  2) у слага есть path_write      → записать строго по json_path:
       value = not value          (если invert)
       value = value_map[value]    (если задан value_map и значение подходит)
       _write_config_path(config, json_path, value)
     и на этом всё (короткое замыкание — секционные обработчики не вызываются)
  3) слаг вида columns.* / rules.* → специальные обработчики
                                      (настройки колонок таблиц / условное форматирование)
  4) иначе                        → обработка по первой секции имени слага
                                      (margin / outline / legend / labels / axes / visuals / …)
```

Ключевой момент: `path_write: True` — универсальный и предпочтительный способ. Когда он
задан, слаг пишется строго туда, куда указывает `json_path`, минуя секционную логику.

Вспомогательная функция `_write_config_path(cfg, path, value)` понимает три формы пути:

```python
_write_config_path(cfg, "roundLimits", v)                 # верхний уровень: cfg["roundLimits"] = v
_write_config_path(cfg, "grid.palette", v)                # вложенный путь: cfg["grid"]["palette"] = v
_write_config_path(cfg, "grid.palette.gradeCount", v)     # вложенность по точкам (любая глубина)
_write_config_path(cfg, "axes[categories].tickangle", v)  # ось по типу: элемент axes[].type=="categories"
```

Точечная форма работает для любой глубины вложения, а не только для показанных уровней:
недостающие промежуточные словари функция создаёт сама. Для формы `axes[type].key`
функция ищет в массиве `cfg["axes"]` элемент с нужным `type` и пишет в него; если такой
оси у компонента нет — запись молча пропускается.

### Шаг 4. Проверить запись слага (smoke-тест)

```python
from tools.config_schema import apply_slug_overrides

cfg = apply_slug_overrides({}, {"section.niceName": 42}, "lineChart")
assert cfg["styleCommons"]["realKey"] == 42
```

Этот тест подтверждает, что значение легло в правильный путь конфига. Для визуальных
настроек одного теста записи мало: убедитесь по рендеру в браузере, что эффект действительно
виден — это и есть проверка по рендер-контракту
([concepts/render-contract.md](concepts/render-contract.md)).

### Шаг 5. Перегенерировать справочные таблицы

После изменения схемы обновите производные таблицы. Если изменился целевой путь слага,
прогоните генератор таблицы «слаг → путь»:

```bash
cd scripts && python gen_slug_json_table.py   # изменился json_path слага
```

Полный перечень генераторов и того, какой когда запускать, — в разделе
[«Регенерация справочных таблиц»](#регенерация-справочных-таблиц).

## Рецепт B. Добавить тип компонента (билдер)

Билдер — функция, которая собирает стартовый `config` для нового компонента из переданных
параметров (тип, поля, агрегация, дефолты). Билдеры живут в `app/tools/builders.py` и
называются `_build_<type>_config(...)` (например, `_build_chart_config`, `_build_table_config`,
`_build_map_config`).

Шаги:

1. В `app/tools/builders.py` добавить функцию-билдер `_build_<type>_config(...)`, которая
   собирает стартовый `config` из параметров.
2. Зарегистрировать тип в логике добавления компонента (`app/tools/component_crud.py`):
   - если компонент **без данных** — добавить его имя в множество `NO_DATASET_TYPES`
     (см. ниже), тогда используется путь добавления без привязки датасета и валидации полей;
   - иначе — стандартный путь с привязкой полей к осям.
3. Если у типа есть особые ключи верхнего уровня, специфичные для него, — учесть их в
   словаре `_TOP_LEVEL_PER_TYPE` (в `config_schema.py`).
4. Проверить: создать компонент этого типа и убедиться, что `config` корректен и
   сериализуется в JSON.

### Что такое `NO_DATASET_TYPES`

`NO_DATASET_TYPES` — неизменяемое множество (`frozenset`) в `app/tools/builders.py`,
перечисляющее типы компонентов, которые не привязываются к датасету: текстовый блок, iframe,
изображение, панель вкладок и подобные. Для них нет полей данных и осей, поэтому стандартная
валидация привязки полей к ним не применяется.

```python
NO_DATASET_TYPES = frozenset({
    "HsImagePanel", "HsIframe", "HsTabsPanel",
    "HsPageContainer", "HsSubheaderComponent",
    "HsTextBlock", "HsAudioplayer",
})
```

Если вы добавляете новый компонент без данных (условно `HsCustomPanel`), добавьте его имя
прямо в литерал (множество неизменяемое — `.add()` к нему неприменим):

```python
NO_DATASET_TYPES = frozenset({
    ..., "HsCustomPanel",
})
```

Список уже зарегистрированных типов можно получить инструментом
`component_crud(action="types_list")`.

## Рецепт C. Добавить инструмент (tool)

Инструмент — публичная функция сервера, доступная ассистенту как RPC-метод по протоколу MCP.
Снаружи это вызов JSON-RPC 2.0 поверх стандартного потока ввода-вывода (stdio), а не HTTP-эндпоинт.

Шаги:

1. В `app/server.py` написать функцию и пометить её декоратором `@mcp.tool`. У инструмента
   указывается режим доступа: для операций чтения используется аннотация только для чтения,
   для операций записи — аннотация чтения-записи (по образцу существующих `@mcp.tool`).
   Это влияет на то, доступен ли инструмент в режиме `readonly`.
2. Бизнес-логику вынести в отдельный модуль `app/tools/<name>_operations.py` — обёртку над
   HTTP-API портала. К порталу обращение идёт методом POST: конкретная операция кодируется
   в теле запроса (например, полем `command` либо парой «объект + метод»). То есть портальный
   API устроен в стиле команд-действий поверх HTTP, а не как чистый ресурсный REST.
3. Использовать мультидейственный паттерн: первый аргумент `action`, внутри — диспетчер по
   значению `action`, и обязательно ветка `action="help"`, описывающая доступные действия.
4. Ошибки возвращать единым конвертом:
   `{success: False, error, missing, hint, example}`. Это контракт, по которому ассистент
   сам исправляет свой вызов и повторяет его.
5. Защитить операции записи: для действий, меняющих портал (`create`, `update`, `delete`),
   перед выполнением вызвать проверку режима (`check_action("действие")`). В режиме
   `readonly` такой вызов будет отклонён. Подробно — в
   [conventions.md#защита-операций-записи](conventions.md#защита-операций-записи).

## Рецепт D. Добавить промпт (сценарий)

Промпт — готовый многошаговый сценарий (например, «создай дашборд из шаблона»), который
ассистент разворачивает по запросу.

Шаги:

1. В `app/prompts.py` добавить функцию-генератор текста промпта (по образцу существующих,
   например `create_dashboard_prompt`). Затем подключить её в диспетчере `get_prompt_messages`,
   добавив ветку с именем промпта.
2. В `app/server.py` объявить точку входа промпта: функцию с декоратором `@mcp.prompt`,
   которая делегирует сборку сообщений в `get_prompt_messages(name, arguments)`.

После этого новый промпт становится доступен ассистенту наравне с остальными.

## Регенерация справочных таблиц

Справочные таблицы (карта «слаг → JSON-путь», сводки статуса и т.п.) генерируются из кода,
а не пишутся вручную. После изменения схемы или билдеров перегенерируйте затронутые таблицы
скриптами из каталога `scripts/`:

| Скрипт | Что делает | Когда запускать |
|---|---|---|
| `scripts/gen_slug_json_table.py` | таблица соответствия «слаг → фактический JSON-путь» | изменился `json_path` слага |
| `scripts/gen_slug_reference.py` | справочник слагов | добавили/изменили слаг |
| `scripts/gen_slug_ui_matrix.py` | матрица «слаг × статус готовности» | изменился набор или статус слагов |
| `scripts/gen_component_status.py` | сводка статусов по компонентам | добавили тип компонента |
| `scripts/gen_render_manifest_from_source.py` | перечень ключей конфига, которые читает отрисовка | сверка с исходниками фронтенда |
| `scripts/frontend_version_sync.py` | сверка слагов с исходниками версии фронтенда | обновление фронтенда |
| `scripts/recheck_render_dead.py` | пере-проверка слагов без видимого эффекта | ревизия слагов без эффекта |

Запуск — из каталога `scripts/`:

```bash
cd scripts && python gen_slug_json_table.py    # изменился json_path слага
cd scripts && python gen_component_status.py   # добавлен новый тип компонента
```

Если изменился целевой ключ слага — обязательно прогоните генератор таблицы «слаг → путь»,
чтобы публичная справка не разошлась с кодом.

## Локальные проверки перед коммитом

Прогоняйте тесты через `pytest` из каталога `app/`. Запускайте сначала тот тест, который
относится к вашему изменению, затем весь набор:

```bash
cd app && pytest tests/test_config_schema.py -q   # изменили слаг/схему
cd app && pytest tests/test_builders.py -q        # изменили билдер
cd app && pytest -q                                # полный прогон перед коммитом
```

Чек-лист перед коммитом:

- [ ] Слаг / билдер / инструмент / промпт добавлен, относящийся к нему тест зелёный.
- [ ] Для визуального слага эффект подтверждён по рендеру: открыть отчёт в браузере,
      применить `config_overrides` через сервер, убедиться, что эффект виден (или явно
      задокументировать причину отсутствия эффекта).
- [ ] Справочные таблицы перегенерированы соответствующими скриптами:
      `gen_slug_json_table.py` при смене `json_path`, `gen_component_status.py` при
      добавлении типа компонента.
- [ ] Полный `pytest` зелёный (`cd app && pytest -q`).
- [ ] Секреты и локальные настройки (например, `.env`, `.mcp.json`) не попали в коммит.
