# Подробный справочник инструментов

Детальное описание 19 инструментов MCP-сервера ModusBI: назначение, режим
(`readonly` / `--readwrite`), все действия (`action`) с пояснениями, ключевые
параметры, примеры и типичные ошибки.

Краткая карта инструментов с полными списками действий и параметров — в
[tool-reference.md](tool-reference.md). Что такое инструмент и почему диспетчеризация
по `action` — в [README.md](README.md). Термины — в [../../GLOSSARY.md](../../GLOSSARY.md).

> ⚠️ Запись на портал (`create` / `update` / `delete` / …) **необратима** — см.
> [../../../DISCLAIMER.md](../../../DISCLAIMER.md). По умолчанию сервер в `readonly`.

## `report_operations`

**Назначение:** Полный жизненный цикл отчёта (дашборда): создание, чтение, изменение, удаление, а также сопутствующие операции — состав и сводка отчёта, экспорт в файл, клонирование, управление глобальными фильтрами, переменными, категориями и опциями сетки. Применяйте всегда, когда нужно что-либо сделать с отчётом как с целым (а не с отдельным компонентом внутри него).

**Режим:** В `readonly` доступны только операции чтения и выгрузки готового отчёта: `help`, `list`, `get`, `summary`, `components_list`, `groups_list`, `export`, `export_info`, `variables_list`, `categories_list`, `get_options`, `global_filters_list`. Требуют `--readwrite`: `create`, `clone` (через проверку `create`); `update`, `update_options`, `variable_add`, `variable_update`, `variable_delete`, `category_add`, `category_update`, `category_delete`, `global_filter_delete` (через проверку `update`); `delete` (через проверку `delete`).

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
|---|---|---|
| `help` | Возвращает список действий инструмента; с именем действия — его описание и пример. | `name` (имя интересующего действия) |
| `list` | Перечисляет отчёты постранично, можно сузить до одной группы. | `group_id` (опц.), `limit`, `offset` |
| `get` | Полная информация об отчёте: состав компонентов с позициями, датасеты, глобальные фильтры/переменные/категории. | `report_id` |
| `summary` | Текстовая сводка отчёта (markdown): состав компонентов и поля. | `report_id` |
| `components_list` | Перечень компонентов отчёта с типами и позициями (без полной конфигурации). | `report_id` |
| `groups_list` | Перечень групп (папок) отчётов постранично. | `limit`, `offset` |
| `create` | Создаёт пустой отчёт в указанной группе. | `name`, `caption`, `group_id`; опц. `parent_id`, `description`, `ord`, `remark` |
| `update` | Обновляет указанные поля отчёта; переданные значения перезаписывают прежние. | `report_id`; опц. `name`, `caption`, `group_id`, `remark`, `description`, `ord`, `global_filters` |
| `delete` | Безвозвратно удаляет отчёт со всеми компонентами, фильтрами, раскладками и переменными. | `report_id` |
| `clone` | Глубокая копия отчёта: переносит сетку, компоненты, фильтры, переменные, категории, опции. | `report_id`; опц. `name`, `group_id` |
| `export` | Рендерит отчёт в файл (PDF/PNG/PPTX), при необходимости сохраняет на диск. | `report_id`; опц. `format`, `page_size`, `page_orientation`, `output_dir`, `filename`, `timeout` |
| `export_info` | Сообщает текущий каталог экспорта и его источник (переменная окружения / Downloads / cwd). | — |
| `variables_list` | Перечень глобальных переменных отчёта (`globalVariables`). | `report_id` |
| `variable_add` | Добавляет новую переменную; ошибка, если переменная с таким именем уже есть. | `report_id`, `variable_name`, `variable_value` |
| `variable_update` | Меняет значение существующей переменной; ошибка, если её нет. | `report_id`, `variable_name`, `variable_value` |
| `variable_delete` | Удаляет переменную по имени. | `report_id`, `variable_name` |
| `categories_list` | Перечень глобальных категорий отчёта (`globalCategories`). | `report_id` |
| `category_add` | Добавляет категорию с выбранным значением и списком вариантов. | `report_id`, `category_name`, `category_selected`, `category_options` |
| `category_update` | Обновляет выбранное значение и/или варианты категории. | `report_id`, `category_name`; опц. `category_selected`, `category_options` |
| `category_delete` | Удаляет категорию по имени. | `report_id`, `category_name` |
| `get_options` | Возвращает опции сетки отчёта (режим ячеек, наложение, свободное перемещение и т. д.). | `report_id` |
| `update_options` | Обновляет опции сетки; меняются только переданные (не `None`) поля. | `report_id`; опц. `cell_mode`, `allow_overlap_mode`, `free_pane_movement`, `no_gap_mode`, `recalculated_cell_mode`, `grouping_mode` |
| `global_filters_list` | Перечень глобальных фильтров отчёта (`globalFilters`). | `report_id` |
| `global_filter_delete` | Удаляет глобальный фильтр по его алиасу; имя фильтра передаётся в `variable_name`. | `report_id`, `variable_name` |

**Ключевые параметры:**
- `report_id` (`int`) — числовой идентификатор отчёта; узнать через `report_operations(action="list")`.
- `name` / `caption` (`str`) — `name` это короткий технический идентификатор (латиница), `caption` — человекочитаемая подпись в интерфейсе (поддерживает кириллицу).
- `group_id` (`int`) — группа (папка), в которой создаётся или размещается отчёт; список — через `reportgroup_operations(action="list")`.
- `format` (`str`) — формат экспорта: `pdf` / `png` / `pptx`.
- `global_filters` (`dict`) — при `update` карта вида «алиас → {"enabled": True, "selected": [...]}»; передаётся для сквозной фильтрации; значения сливаются с уже имеющимися.
- `variable_value` (`str | list[str]`) — значение(я) переменной; одиночная строка автоматически оборачивается в список.
- `cell_mode` (`str`) — режим размера ячеек сетки; допустимые значения проверяются (`compact` / `standard` / `large`).

**Пример:**
```
report_operations(
    action="clone",
    report_id=35,            # отчёт-источник
    name="Продажи (копия)",  # имя новой копии (опционально)
    group_id=20              # целевая группа (опционально; по умолчанию — группа источника)
)
```

**Подсказки/типичные ошибки:**
- `delete` необратимо: каскадом удаляются все компоненты, фильтры, раскладки и переменные отчёта. Перед удалением полезно сохранить конфигурацию через `action="get"`.
- `update`, `update_options` перезаписывают только переданные поля, но прежние их значения теряются; `global_filters` при `update` сливаются с существующими, остальные поля — заменяются.
- Не помните набор действий или их параметры — вызовите `report_operations(action="help")` (список) или `report_operations(action="help", name="clone")` (по конкретному действию). Параметр действия для справки здесь — `name`.
- При ошибке «требует режим: readwrite» сервер запущен в `readonly` — запишущие действия (`create`, `update`, `delete`, `clone`, `variable_*`, `category_*`, `global_filter_delete`, `update_options`) недоступны.

## `reportgroup_operations`

**Назначение:** Управление группами (папками) отчётов — иерархическими контейнерами, по которым отчёты раскладываются в навигации портала. Применяйте для организации структуры разделов: создать папку, переименовать, переместить в другую родительскую группу, удалить.

**Режим:** В `readonly` доступны `list` и `get`. Требуют `--readwrite`: `create` (проверка `create`), `update` (проверка `update`), `delete` (проверка `delete`), `move` (проверка `move`). Действия `help` у этого инструмента нет — справку по действиям смотрите в самом перечне ниже.

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
|---|---|---|
| `list` | Перечисляет все группы отчётов постранично, с флагами (в меню, расширенная, есть ли отчёты, пустая). | `limit`, `offset` |
| `get` | Информация об одной группе по ID: имя, подпись, родитель, флаги, опции, иконка. | `group_id` |
| `create` | Создаёт новую группу; при `parent_id=0` группа создаётся в корне. | `name`; опц. `caption`, `parent_id`, `menu`, `is_extended`, `options`, `image` |
| `update` | Обновляет поля группы; меняются только переданные значения, флаг «по умолчанию» сохраняется. | `group_id`; опц. `name`, `caption`, `parent_id`, `menu`, `is_extended`, `options`, `image` |
| `delete` | Безвозвратно удаляет группу; вложенные группы и отчёты, ссылающиеся на неё через `parent_id`, остаются без родителя. | `group_id` |
| `move` | Перемещает группу под нового родителя; опционально задаёт позицию среди соседей. | `group_id`, `parent_id`; опц. `previous_group_id` |

**Ключевые параметры:**
- `group_id` (`int`) — идентификатор группы; список — через `reportgroup_operations(action="list")`.
- `name` (`str`) — короткий технический идентификатор группы (латиница); при создании, если не задан `caption`, используется как подпись.
- `caption` (`str`) — человекочитаемое название группы в интерфейсе (поддерживает кириллицу).
- `parent_id` (`int`) — родительская группа; `0` означает корень (на уровне API транслируется в «нет родителя»).
- `menu` (`bool`) — показывать ли группу в главном навигационном меню портала.
- `previous_group_id` (`int`) — при `move` идентификатор группы, после которой разместить перемещаемую (для упорядочивания соседей).

**Пример:**
```
reportgroup_operations(
    action="create",
    name="sales",                       # технический идентификатор (латиница)
    caption="Отчёты отдела продаж",     # подпись в интерфейсе
    parent_id=1,                        # вложить в группу с ID=1
    menu=True                           # показать в навигационном меню
)
```

**Подсказки/типичные ошибки:**
- `delete` необратимо: вложенные группы и отчёты, привязанные к удалённой группе через `parent_id`, теряют родителя и могут стать недоступными через дерево папок портала.
- Для корневого уровня используйте `parent_id=0` (либо не передавайте его) — внутри инструмент превращает `0` в «нет родителя»; передавать сырой `0` напрямую в API не нужно.
- У инструмента нет `action="help"`: перечень действий и обязательных параметров берите из этого справочника или из самой схемы инструмента.

## `report_template`

**Назначение:** Быстрая сборка отчёта из готового шаблона раскладки. Позволяет посмотреть список шаблонов, предпросмотреть структуру конкретного шаблона и одним вызовом создать (или дополнить) отчёт набором компонентов с заранее заданными позициями. Применяйте, когда нужно стартовать с типового дашборда, а не собирать раскладку компонент за компонентом вручную.

**Режим:** В `readonly` доступны `list` и `preview` (только чтение, портал не изменяется). Требует `--readwrite`: `scaffold` (проверка `create`) — он создаёт или дополняет реальный отчёт. Действия `help` у этого инструмента нет.

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
|---|---|---|
| `list` | Перечисляет все доступные шаблоны: описание, число и типы компонентов, ASCII-превью раскладки. | — |
| `preview` | Подробная раскладка одного шаблона: ASCII-схема + покомпонентный разбор (тип, заголовок, позиция x/y/w/h, нужны ли данные). | `template` |
| `scaffold` | Создаёт отчёт (или дополняет существующий) компонентами шаблона за один проход (1 чтение + 1 запись); опционально сразу привязывает поля датасета. | `template`; опц. `dataset_id`, `report_id`, `name`, `group_id`, `category_field`, `value_field` |

**Ключевые параметры:**
- `template` (`str`) — имя шаблона; одно из: `kpi_dashboard`, `ranking`, `comparison`, `factor_analysis`, `geo_analytics`, `simple`.
- `dataset_id` (`int`) — датасет для компонентов с данными; обязателен для `scaffold`, если в шаблоне есть хоть один компонент, работающий с данными (то есть для всех штатных шаблонов).
- `report_id` (`int`) — если передан, `scaffold` **дополняет** этот отчёт компонентами шаблона; если не передан — создаётся новый отчёт.
- `name` (`str`) — имя нового отчёта при `scaffold` (когда `report_id` не задан); по умолчанию берётся название шаблона.
- `category_field` (`str`) — поле-измерение, привязываемое в слотах категории (фильтры, ось X графиков, первый столбец таблицы); работает только вместе с `value_field`.
- `value_field` (`str`) — список метрик через запятую: KPI-слоты перебирают их по кругу, графики берут первую, таблицы получают категорию + все метрики. Без него `scaffold` создаёт каркас с подстановочным полем `value`, поля привязываются вручную.

**Пример:**
```
report_template(
    action="scaffold",
    template="kpi_dashboard",       # шаблон: 3 фильтра + 4 KPI + график + treemap + таблица
    dataset_id=10,                  # датасет для компонентов с данными
    name="Дашборд продаж",          # имя нового отчёта
    group_id=20,                    # группа размещения (опц., по умолчанию 1)
    category_field="region",        # измерение для фильтров/оси X/первого столбца
    value_field="amount,qty,profit" # метрики: KPI по кругу, график — amount, таблица — region+все
)
```

**Подсказки/типичные ошибки:**
- `scaffold` нельзя автоматически откатить: добавленные компоненты сохраняются в отчёте, при ненужности их удаляют через `component_crud(action="delete")`, а целый отчёт — через `report_operations(action="delete")`.
- Если у компонента с данными не передать `dataset_id`, `scaffold` вернёт ошибку с подсказкой и примером — заполните `dataset_id` и повторите вызов.
- `category_field` без `value_field` игнорируется (привязка категории требует метрик); в ответе об этом приходит предупреждение в `next_steps`.
- После `scaffold` карты (`HsMapLeafletChart`, шаблон `geo_analytics`) требуют отдельной гео-привязки, а на компоненты-данные нужно добавить поля фильтрации через `component_filters(action="filter_field_add")` — иначе фильтры показывают значения, но данные не фильтруются; соответствующие шаги перечислены в `next_steps` ответа.
- Действия `help` нет — список шаблонов берите через `action="list"`, а при неизвестном имени шаблона `preview`/`scaffold` вернут перечень допустимых значений в поле `hint`.

## `dataset_operations`

**Назначение:** CRUD-операции над датасетами — семантическим слоем поверх источника данных (как правило, сохранённый SQL-запрос с описанием полей). Применяйте, чтобы посмотреть список датасетов, прочитать метаданные и поля, создать/изменить/удалить датасет, а также задать человекочитаемые имена полей (`field_aliases`).

**Режим:** действия `create`, `update`, `delete` требуют запуска сервера с `--readwrite`. В режиме `readonly` доступны `list`, `get`, `fields_list` и самосправка `help`.

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
| --- | --- | --- |
| `help` | Возвращает обзор инструмента и справку по конкретному действию. Без аргумента — общий обзор; с `name="<action>"` — детали и примеры. | `name` (имя действия) |
| `list` | Перечисляет все датасеты с постраничной навигацией. По каждому отдаёт `id`, `name`, `caption`, `datasource_id`, `driver_id`, число полей. | `limit` (по умолчанию 50), `offset` |
| `get` | Возвращает полные метаданные одного датасета: имя, источник, SQL-запрос, список полей с типами и алиасами. `total_rows=null` означает «не подсчитано» (портал считает количество лениво — для свежих датасетов всегда 0). | `dataset_id` (обязателен) |
| `fields_list` | Отдаёт только список полей датасета: имя, алиас, тип, тип поля. Компактнее, чем `get`. | `dataset_id` (обязателен) |
| `create` | Создаёт датасет. Без `sql` — пустой датасет на источнике; с `sql` запрос автоматически маршрутизируется в `dataset_create_from_sql` (SQL проверяется, поля выводятся). | `name`, `datasource_id` (обязательны); `caption`, `sql` (опционально) |
| `update` | Изменяет указанные поля датасета: имя, подпись, источник, SQL-запрос, RLS, человекочитаемые имена полей. При смене `sql` запрос автоматически валидируется и поля пересобираются. Перезаписывает только переданные значения. | `dataset_id` (обязателен); `name`, `caption`, `datasource_id`, `sql`, `rls`, `sql_rls`, `field_aliases` |
| `delete` | Безвозвратно удаляет датасет. Перед удалением проверяет существование, чтобы фантомный id давал честный отказ. | `dataset_id` (обязателен) |

**Ключевые параметры:**
- `dataset_id` (int) — числовой идентификатор датасета; узнать через `action="list"`. Обязателен для `get`, `fields_list`, `update`, `delete`.
- `name` (str) — короткое техническое имя (латиница, lower_snake_case), используется как внутренний идентификатор.
- `datasource_id` (int) — идентификатор подключения к источнику (НЕ тип драйвера). Список — через `datasource_operations(action="list")`.
- `sql` (str) — SQL-запрос семантического слоя. В `create` запускает валидацию; в `update` при изменении запроса вызывает повторную валидацию и пересборку полей.
- `field_aliases` (dict) — карта `имя_поля → {"alias": "...", "description": "..."}` для подписи полей на русском. Задавать **до** привязки датасета к компонентам.
- `rls` / `sql_rls` — включение Row-Level Security и SQL-фильтр RLS (с плейсхолдером `:current_user_id`).

**Пример:**
```text
dataset_operations(
    action="update",
    dataset_id=5,
    field_aliases={                       # подписи полей до привязки к компонентам
        "region": {"alias": "Регион"},
        "amount": {"alias": "Сумма", "description": "Сумма продаж"}
    }
)
```

**Подсказки/типичные ошибки:**
- `field_aliases` нужно задавать **до** привязки датасета к компонентам: после привязки портал блокирует изменение алиасов уже используемых полей (датасет вернёт ошибку, инструмент сообщит об этом в `field_aliases_not_applied`). Рабочий порядок: создать датасет → задать алиасы → затем добавлять компоненты.
- `delete` необратим и ломает все отчёты и компоненты, которые ссылаются на датасет, — они перестанут загружаться, пока их не пересоберут или не перенаправят на другой датасет.
- Для создания датасета из SQL предпочтительнее `dataset_create_from_sql`, а `create` с параметром `sql` всего лишь маршрутизирует туда. При смене `sql` на привязанном датасете изменение может молча не примениться — инструмент это распознаёт и возвращает `query_not_applied` с подсказкой пересоздать датасет.
- Список действий и примеры — `dataset_operations(action="help")`, по конкретному действию — `dataset_operations(action="help", name="update")`.

## `dataset_create_from_sql`

**Назначение:** Создаёт датасет из SQL-запроса за один вызов: проверяет запрос на источнике, выводит структуру и типы полей и собирает семантический слой. Рекомендуемый способ создания SQL-датасета (в отличие от `dataset_operations(action="create")`, который без `sql` валидацию не делает).

**Режим:** требует запуска сервера с `--readwrite` (создание данных).

**Действия (action):** инструмент без параметра `action` — выполняет ровно одну операцию (создание датасета из SQL). Внутренне проходит шаги: получение драйвера источника → валидация SQL через выполнение на источнике → создание датасета → запись запроса и полей.

**Ключевые параметры:**
- `sql_query` (str, обязателен) — SQL-запрос датасета. Пишите ORIGINAL (латинские) имена колонок через `AS` — именно это имя становится ключом поля и используется в `field_aliases`. Включайте `ORDER BY` для сортировки на графиках (порядок сохраняется), при необходимости `WHERE`.
- `datasource_id` (int, обязателен) — идентификатор подключения к источнику (НЕ тип драйвера — драйвер выводится автоматически). Список — через `datasource_operations(action="list")`.
- `name` (str, обязателен) — техническое имя датасета (латиница). Пустое/пробельное имя отклоняется до обращения к порталу.
- `caption` (str, опционально) — человекочитаемая подпись; по умолчанию равна `name`.

**Пример:**
```text
dataset_create_from_sql(
    sql_query="SELECT region, SUM(amount)::INTEGER AS total "
              "FROM sales WHERE status = 'active' "
              "GROUP BY region ORDER BY total DESC",   # ORDER BY сохраняется
    datasource_id=1,        # ID подключения, не тип драйвера
    name="sales_by_region",
    caption="Продажи по регионам"
)
```

**Подсказки/типичные ошибки:**
- После создания задайте русские подписи полей через `dataset_operations(action="update", field_aliases={...})` — **до** привязки датасета к компонентам.
- Передавайте именно `datasource_id` подключения, а не тип драйвера. Системный источник «Метаданные» не поддерживает произвольные SQL-датасеты — инструмент отклонит его заранее с понятным сообщением; выберите реальное подключение к БД (PostgreSQL/ClickHouse и т.п.).
- Запрос реально выполняется на источнике при валидации (это не песочница): допускается единственный оператор `SELECT` (или `WITH ... SELECT`); DML/DDL и несколько операторов отклоняются. При ошибке инструмент возвращает текст ответа портала в `details` и стадию (`step`) — по ней видно, на каком шаге упало.

## `dataset_query`

**Назначение:** Основной способ получить данные из датасета — запрос к семантическому слою в упрощённом «SQL-подобном» виде (выборка полей, фильтры, группировка, сортировка, лимит). Сырой SQL прямо к источнику данных API не выполняет — данные читаются только через датасет.

**Режим:** только чтение — доступен в `readonly`. Запись не выполняет.

**Действия (action):** инструмент без параметра `action`; первый параметр — `dataset_id`, далее условия выборки.

**Ключевые параметры:**
- `dataset_id` (int, обязателен) — идентификатор датасета (НЕ источника данных).
- `select` (list) — поля выборки, каждое как `{"name": "field", "aggr": "sum|avg|min|max|count"}`. Без `aggr` поле берётся как есть.
- `where` (list) — условия фильтра, каждое как `{"name": "field", "op": ..., "value": ...}`. Рабочие операторы: `=`, `!=`, `<`, `>`, `<=`, `>=`, `like`, `is`, `is not`. `is`/`is not` без `value` дают `IS [NOT] NULL`.
- `group` (list) — поля группировки, каждое как `{"name": "field"}`.
- `order` (list) — сортировка, каждое как `{"name": "field", "dir": "asc|desc"}`.
- `limit` (int, по умолчанию 1000) — максимум строк. `limit=0` вернёт 0 строк (только метаданные полей); отрицательное значение отклоняется.
- `variables` (dict) — значения SQL-переменных для подстановки `:variable_name` в запросе датасета, формат `{"region": ["Москва"], "year": [2024]}`.

**Пример:**
```text
dataset_query(
    dataset_id=5,
    select=[{"name": "region"}, {"name": "amount", "aggr": "sum"}],
    where=[{"name": "status", "op": "=", "value": "completed"}],
    group=[{"name": "region"}],
    order=[{"name": "amount", "dir": "desc"}],   # топ-регионы сверху
    limit=10
)
```

**Подсказки/типичные ошибки:**
- Передавайте `dataset_id`, а не `datasource_id` — это разные сущности (датасет привязан к источнику, но запрос идёт к датасету).
- Оператор `in` порталом не поддерживается (даёт ошибку) — используйте несколько условий `=` с `logicOr: 1` вместо него.
- `is`/`is not` — это проверка на NULL; их нельзя сочетать с непустым `value` (инструмент отклонит такое условие). Для сравнения со значением используйте `=`/`!=`.
- При ошибке выполнения (HTTP 500) проверьте доступность источника через `preflight_check_datasource` или `datasource_operations(action="check_connection")`. `truncated: true` в ответе означает, что строк больше, чем `limit`.

## `query_batch`

**Назначение:** Выполняет несколько запросов к одному датасету за один вызов — эффективнее серии отдельных `dataset_query`, когда для одного дашборда нужно несколько срезов данных.

**Режим:** только чтение — доступен в `readonly`.

**Действия (action):** инструмент без параметра `action`; принимает `dataset_id` и список запросов `queries`.

**Ключевые параметры:**
- `dataset_id` (int, обязателен) — идентификатор датасета, к которому применяются все запросы.
- `queries` (list, обязателен) — список запросов, каждый как `{"id": "уникальный_ключ", "params": {select/where/group/order/limit/...}}`. Поле `id` обязательно у каждого запроса — по нему результаты возвращаются и сопоставляются. `params` — те же условия, что у `dataset_query`.

Ограничение по количеству запросов в пакете: до 10 (в демо-режиме — до 5).

**Пример:**
```text
query_batch(
    dataset_id=5,
    queries=[
        {"id": "total",     "params": {"select": [{"name": "amount", "aggr": "sum"}]}},
        {"id": "by_region", "params": {"select": [{"name": "region"},
                                                  {"name": "amount", "aggr": "sum"}],
                                       "group":  [{"name": "region"}]}}
    ]
)
```

**Подсказки/типичные ошибки:**
- У каждого элемента `queries` обязателен непустой `id`; иначе вызов завершится ошибкой. В ответе результаты сопоставляются по этому `id`.
- Пакетный путь портала может вернуть HTTP 200 с пустыми данными на корректном по контракту запросе — инструмент это распознаёт и отдаёт `success: false` с предупреждением. Обходной путь: вызвать `dataset_query` по одному запросу за раз (одиночный путь работает надёжно).
- Если упали отдельные под-запросы, общий ответ остаётся `success: true` с предупреждением — разбирайтесь по `results[].error`; если упали все — `success: false`.

## `sql_query_validate`

**Назначение:** Проверяет SQL-запрос и возвращает структуру результирующих полей (имена и типы) без сохранения датасета. Применяйте перед созданием датасета, чтобы проверить синтаксис, узнать типы и имена колонок и предпросмотреть структуру.

**Режим:** только чтение со стороны MCP — доступен в `readonly`. Важно: на стороне портала проверка выполняется **выполнением** запроса на живом источнике (это не песочница).

**Действия (action):** инструмент без параметра `action`; принимает SQL и идентификатор источника.

**Ключевые параметры:**
- `sql_query` (str, обязателен) — проверяемый SQL-запрос. Допускается ровно один оператор `SELECT` (или `WITH ... SELECT`).
- `datasource_id` (int, по умолчанию 1) — идентификатор подключения к источнику; на нём запрос и выполняется при проверке.

**Пример:**
```text
sql_query_validate(
    sql_query="SELECT id, name, created_at FROM users LIMIT 10",
    datasource_id=1
)
# Вернёт: {success: True, valid: True, fields: [{name: "id", type: "number"}, ...]}
```

**Подсказки/типичные ошибки:**
- Это не песочница: запрос реально выполняется на источнике. Поэтому MCP заранее отклоняет DML/DDL и несколько операторов — разрешён только один `SELECT`/`WITH ... SELECT` (ответ `only single SELECT allowed`).
- Если имя колонки совпадает с ключевым словом SQL (например, `update`), заключите его в двойные кавычки — иначе сработает защитный фильтр.
- При ошибке инструмент возвращает реальную причину из тела ответа портала в `details` (синтаксис, отсутствие таблиц/колонок, недоступность источника) — это точнее, чем голый код HTTP. Если источник недоступен, диагностируйте через `preflight_check_datasource`.

## `datasource_operations`

**Назначение:** Операции только для чтения над источниками данных (подключениями к БД): список подключений, метаданные одного источника, список таблиц, поля таблицы, проверка соединения. Применяйте, чтобы найти `datasource_id` и изучить структуру БД перед написанием SQL.

**Режим:** инструмент только для чтения — все доступные действия работают и в `readonly`. Действия `create`, `update`, `delete` намеренно не реализованы через MCP (они безвозвратно сломали бы все датасеты и отчёты на подключении) — управление подключениями выполняется через веб-портал или прямой HTTP-API; вызов вернёт сообщение `not supported`.

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
| --- | --- | --- |
| `list` | Перечисляет все источники данных с постраничной навигацией: `id`, `name`, `caption`, `parent_id` (тип драйвера). Хост/БД/учётные данные в списке не возвращаются. | `limit` (по умолчанию 50), `offset` |
| `get` | Возвращает публичные метаданные одного источника: имя, подпись, тип драйвера (`parent_id`) и его подсказку (`driver_hint`), описание. Внутренние реквизиты подключения (хост, порт, БД, пользователь) намеренно не выдаются. | `datasource_id` (обязателен) |
| `tables_list` | Перечисляет таблицы базы данных выбранного источника (имя, схема, тип). | `datasource_id` (обязателен) |
| `table_fields` | Возвращает колонки таблицы: имя, тип, длину/точность, обязательность, признак первичного ключа. | `datasource_id`, `table_name` (обязательны); `schema` (по умолчанию `public`) |
| `check_connection` | Проверяет статус соединения с источником и возвращает `connected` и сообщение. | `datasource_id` (обязателен) |
| `create` / `update` / `delete` | Не поддерживаются через MCP — возвращают сообщение о необходимости использовать веб-портал или прямой HTTP-API. | — |

**Ключевые параметры:**
- `datasource_id` (int) — идентификатор подключения к источнику; обязателен для `get`, `tables_list`, `table_fields`, `check_connection`. Список — через `action="list"`.
- `table_name` (str) — имя таблицы (без префикса схемы); обязательно для `table_fields`.
- `schema` (str, по умолчанию `public`) — имя схемы БД (актуально для PostgreSQL).
- `limit` / `offset` — постраничная навигация для `list`.

**Пример:**
```text
datasource_operations(
    action="table_fields",
    datasource_id=1,
    table_name="users",
    schema="public"      # схема PostgreSQL
)
```

**Подсказки/типичные ошибки:**
- Создание/изменение/удаление источников через MCP недоступно по умыслу — выполняйте их в веб-портале; вызов `create`/`update`/`delete` вернёт `not supported`.
- `parent_id` в ответах `list`/`get` — это **тип драйвера** (например, 20 = PostgreSQL, 50 = ClickHouse), а не идентификатор подключения; при создании датасета передавайте `datasource_id` (id подключения), а не этот тип.
- Если таблицы или поля не читаются, начните с `check_connection` (или более глубокого `preflight_check_datasource`) — источник может быть недоступен. Реквизиты подключения (хост/БД/пользователь) инструмент не выдаёт намеренно.

## `preflight_check_datasource`

**Назначение:** Предполётная проверка источника данных: подтверждает, что подключение не только устанавливается, но и реально исполняет запросы. Идёт дальше `check_connection`, выполняя пробный запрос. Применяйте перед затратными операциями, чтобы быстро упасть с понятной диагностикой, и при разборе ошибок выполнения (HTTP 500).

**Режим:** только чтение — доступен в `readonly`.

**Действия (action):** инструмент без параметра `action`; выполняет два шага — базовую проверку соединения (как `check_connection`) и пробное выполнение простого запроса (`SELECT 1`).

**Ключевые параметры:**
- `datasource_id` (int, обязателен) — идентификатор проверяемого подключения к источнику.

**Пример:**
```text
preflight_check_datasource(datasource_id=1)
# Вернёт: {success, datasource_id, connected: bool, can_query: bool, message?/error?/hint?}
```

**Подсказки/типичные ошибки:**
- Различайте поля ответа: `connected` — устанавливается ли соединение, `can_query` — реально ли выполняется SQL. Источник может быть `connected: true`, но `can_query: false` (БД недоступна, неверные реквизиты или нет прав на таблицы).
- Запускайте перед `dataset_query` на новом датасете и при диагностике ошибок выполнения с HTTP 500 — это отделяет проблему источника от проблемы самого запроса.
- При таймауте пробного запроса инструмент сообщит, что БД медленная или недоступна; конкретику смотрите в `error`/`details`/`hint` ответа.

## `component_crud`

**Назначение:** Управляет жизненным циклом компонентов отчёта (виджетов) — добавление, чтение, обновление, удаление, копирование и раскладка (позиция/размеры), а также справочные действия по типам компонентов, слагам настроек и пресетам. Применяйте при сборке дашборда «с нуля» и при любой правке отдельного компонента.

**Режим:** В `readonly` доступны `help`, `types_list`, `get`, `data`, `layout_get_breakpoints`, `list_slugs`, `list_presets`. Требуют запуска с `--readwrite`: `add`, `add_text_block`, `add_chart_with_conclusion`, `update`, `delete`, `copy`, `layout_update`, `layout_update_breakpoint`, `swap`.

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
|---|---|---|
| `help` | Возвращает список действий или справку по одному действию с примерами. Не меняет данные. | `value_field` или `slug_category` = имя действия |
| `types_list` | Перечисляет все доступные типы компонентов (около 30: графики, таблицы, KPI, карты, фильтры, текст и др.). | — |
| `get` | Отдаёт конфигурацию компонента по индексу. С `slug_category='raw'` включает полный сырой config. | `report_id`, `component_idx`, опц. `slug_category='raw'` |
| `add` | Добавляет компонент в отчёт, привязывая его к датасету и полям. Для таблиц обязательно `aggregation='none'`. | `report_id`, `component_type`, `title`, `dataset_id`/`dataset_name`, `value_field`, `category_field`, `aggregation` |
| `add_text_block` | Добавляет текстовый блок `HsTextBlock` с HTML-содержимым (HTML очищается: теги `<script>`/обработчики `on*` вырезаются). | `report_id`, `title`, `text_content`, опц. `position` |
| `add_chart_with_conclusion` | Создаёт пару «график + текстовый блок-вывод» с автопозиционированием внизу отчёта. | `report_id`, `component_type`, `title`, `dataset_id`, `value_field`, `text_content` |
| `update` | Переписывает указанные поля компонента: заголовок, датасет, оси, агрегацию и визуальные параметры. Незаданные поля сохраняются, заданные — перезаписываются. | `report_id`, `component_idx`, плюс изменяемые поля / `config_overrides` / `preset` |
| `delete` | Безвозвратно удаляет компонент вместе с его раскладкой, привязками фильтров, правилами форматирования и вычисляемыми полями. Отмены нет. | `report_id`, `component_idx` |
| `data` | Возвращает строки данных, которые сейчас отрисовываются компонентом. Только чтение. | `report_id`, `component_idx`, опц. `limit` |
| `copy` | Делает глубокую копию компонента в этом же или другом отчёте. | `report_id`, `component_idx`, опц. `target_report_id`, `title` |
| `layout_update` | Меняет позицию/размер компонента сразу для всех breakpoints. | `report_id`, `component_idx`, `x`/`y`/`w`/`h` или `position`, опц. `z_index` |
| `layout_get_breakpoints` | Отдаёт позиции компонента по каждому breakpoint (hd/lg/md/sm/xs/xxs). Только чтение. | `report_id`, `component_idx` |
| `layout_update_breakpoint` | Меняет раскладку только для одного указанного breakpoint. | `report_id`, `component_idx`, `breakpoint`, `x`/`y`/`w`/`h` |
| `swap` | Меняет местами два компонента отчёта. | `report_id`, `component_idx`, `component_idx_2` |
| `list_slugs` | Перечисляет слаги настроек. Поддерживает префиксы в `slug_category`: `search:<строка>` (поиск по подстроке), `ui:<категория>`/`ui:` (добавить названия элементов панели — дороже по токенам). | опц. `component_type`, `slug_category` |
| `list_presets` | Перечисляет визуальные пресеты (minimal, presentation, dashboard, dark, print, kpi). | — |

**Ключевые параметры:**
- `component_type` — класс компонента, например `HsBarAMchartsChart` (столбцы), `HsTableReactabularChart` (таблица), `HsTotalsPanelV2` (KPI), `HsTextBlock` (текст). Полный список — `types_list`.
- `value_field` — поле(я) датасета со значением/метрикой; для таблиц перечисляются через запятую (например `object_name,command_name`).
- `category_field` — поле-измерение (категория/ось), например `region`.
- `aggregation` — способ свёртки: `sum`/`avg`/`min`/`max`/`count`; для таблиц всегда `none`. Пустая строка = «не менять при update».
- `config_overrides` — словарь `{слаг: значение}` для точечного переопределения настроек (Уровень 2); ключи смотрите через `list_slugs`.
- `preset` — имя готового набора оформления (Уровень 3).
- `field_titles` — карта «техническое имя поля → русская подпись», например `{'region':'Регион'}`.

**Пример:**
```text
component_crud(
  action="add",
  report_id=35,
  component_type="HsTableReactabularChart",   # таблица
  title="Команды объектов",
  dataset_id=5,
  value_field="object_name,command_name,title",
  value_fields_type="string",
  aggregation="none",                          # таблицы всегда none
  field_titles={"object_name":"Объект", "command_name":"Команда", "title":"Заголовок"}
)
```

**Подсказки/типичные ошибки:**
- Таблицы (`HsTable...`) всегда добавляются с `aggregation="none"`, иначе данные свернутся неверно.
- `delete` необратимо и каскадно: вместе с компонентом удаляются его фильтры, правила форматирования и вычисляемые поля.
- Если не помните параметры действия — вызовите `component_crud(action="help", slug_category="add")`; список действий — `component_crud(action="help")`.

## `component_filters`

**Назначение:** Управляет осью фильтрации компонентов и глобальными фильтрами отчёта: привязка/снятие полей фильтрации, каскадные зависимости между фильтрами, выставление/сброс значений глобальных фильтров и равномерная раскладка фильтров в сетке. Применяйте при настройке интерактивной фильтрации дашборда.

**Режим:** В `readonly` доступны `help` и `filter_fields_list`. Требуют `--readwrite`: `set_global_filter`, `reset_global_filters`, `filter_field_add`, `filter_field_remove`, `filter_set_cascade`, `filters_grid_layout`.

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
|---|---|---|
| `help` | Список действий или справка по одному действию с примерами. | `value_field` = имя действия |
| `set_global_filter` | Выставляет значение на компоненте-фильтре `FilterControlPanel`. Без `alias` пишется только локальный выбор; для настоящего глобального фильтра `alias` обязателен. | `report_id`, `component_idx`, опц. `value_field` (значения через запятую; пусто = сброс), `alias` |
| `reset_global_filters` | Сбрасывает все выбранные значения глобальных фильтров отчёта. Из MCP необратимо — пользователи выбирают заново. | `report_id` |
| `filter_fields_list` | Перечисляет поля на оси фильтрации компонента. Только чтение. | `report_id`, `component_idx` |
| `filter_field_add` | Привязывает поле к оси фильтрации. Нужно вызвать на `FilterControlPanel` И на каждом фильтруемом компоненте. Опционально задаёт каскад через `depends_on`. | `report_id`, `component_idx`, `value_field`, `alias`, `field_type`, `dataset_id`, опц. `depends_on` |
| `filter_field_remove` | Снимает поле с оси фильтрации компонента. Повторная привязка — через `filter_field_add` со всеми параметрами. | `report_id`, `component_idx`, `value_field` |
| `filter_set_cascade` | Создаёт или снимает каскадную зависимость между фильтрами. Без `depends_on` каскад снимается с фильтра `alias`. | `report_id`, `alias`, опц. `depends_on`, `reset_mode`, `reset_type` |
| `filters_grid_layout` | Равномерно распределяет N компонентов-фильтров по сетке `cols×rows` сразу для всех breakpoints. Удобная надстройка над ручным расчётом ширины. | `report_id`, `config_overrides={component_indices, cols, ...}` |

**Ключевые параметры:**
- `value_field` — имя поля датасета для фильтрации; в `set_global_filter` — выбранные значения через запятую (пусто = сброс).
- `alias` — человекочитаемая подпись фильтра (поддерживает кириллицу, например `Регион`); для глобального фильтра обязателен.
- `field_type` — тип поля для привязки: `string`, `number`, `date`, `datetime` или `boolean`.
- `dataset_id` — датасет поля; обязателен при `filter_field_add`.
- `depends_on` — alias родительского фильтра (для каскада: значения дочернего фильтра ограничиваются выбором родителя).
- `config_overrides` (для `filters_grid_layout`) — `component_indices` (список индексов), `cols` (колонок), опц. `rows` (по умолчанию 1), `y_start` (по умолчанию 0), `h` (по умолчанию 3).

**Пример:**
```text
component_filters(
  action="filter_field_add",
  report_id=35,
  component_idx=3,
  value_field="region",
  alias="Район",
  field_type="string",
  dataset_id=5,
  depends_on="Город"     # каскад: район зависит от выбранного города
)
```

**Подсказки/типичные ошибки:**
- Критично: `filter_field_add` нужно вызывать не только на самом `FilterControlPanel`, но и на каждом фильтруемом компоненте (график/таблица/KPI/карта). Иначе выпадающий список покажет значения, но данные не отфильтруются.
- `dataset_id`, `alias` и `field_type` при `filter_field_add` обязательны.
- Справка по действию — `component_filters(action="help", value_field="filter_field_add")`.

## `component_axes`

**Назначение:** Настраивает поля и связи компонента: вычисляемые поля, страницы контейнеров (`PageContainer`), переходы между отчётами на сводных таблицах (pivot links), иерархию детализации (drill-down), кнопки навигации в `TabsPanel`, условное форматирование и гео-привязку карты. Применяйте для расширенной настройки компонента после его создания.

**Режим:** В `readonly` доступны `help`, `calc_fields_list`, `page_list`, `drill_get`, `conditional_rule_list`, `geodata_list`, `map_get_geokeys`, `tabs_button_list`. Требуют `--readwrite`: `calc_field_add`/`update`/`remove`, `page_add`/`remove`/`rename`, `pivot_link_set`/`remove`, `drill_add_level`/`delete_level`/`change_level`/`toggle_date_range`/`set_field`, `conditional_rule_add`/`delete`, `map_set_geokeys`, `tabs_button_add`/`delete`.

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
|---|---|---|
| `help` | Список действий или справка по действию. | `value_field` = имя действия |
| `calc_fields_list` | Перечисляет вычисляемые поля компонента. | `report_id`, `component_idx` |
| `calc_field_add` | Добавляет вычисляемое поле на указанную ось из SQL-подобного выражения. | `report_id`, `component_idx`, `calc_expression`, опц. `target_axis` (по умолчанию `values`) |
| `calc_field_update` | Меняет выражение существующего вычисляемого поля. | `report_id`, `component_idx`, `value_field`, `calc_expression` |
| `calc_field_remove` | Безвозвратно удаляет вычисляемое поле (выражение теряется). | `report_id`, `component_idx`, `value_field` |
| `page_list` | Перечисляет страницы контейнера. | `report_id`, `component_idx` |
| `page_add` | Добавляет страницу в контейнер. | `report_id`, `component_idx`, `title` |
| `page_remove` | Удаляет страницу и все привязанные к ней компоненты. Необратимо. | `report_id`, `component_idx`, `page_id` |
| `page_rename` | Переименовывает страницу. | `report_id`, `component_idx`, `page_id`, `title` |
| `pivot_link_set` | Задаёт переход (drill-through) по полю сводной таблицы на внешний URL. | `report_id`, `component_idx`, `field_id`, `target_url`, `title`, опц. `link_target` (по умолчанию `_blank`) |
| `pivot_link_remove` | Удаляет настроенный переход с поля. | `report_id`, `component_idx`, `field_id` |
| `drill_get` | Читает конфигурацию детализации (drill-down). | `report_id`, `component_idx` |
| `drill_add_level` | Добавляет уровень в иерархию детализации. | `report_id`, `component_idx` |
| `drill_delete_level` | Удаляет последний уровень иерархии. Необратимо. | `report_id`, `component_idx` |
| `drill_change_level` | Задаёт поле на конкретном уровне детализации (перезаписывает). | `report_id`, `component_idx`, `field_index`, `field_id` |
| `drill_toggle_date_range` | Переключает режим детализации по диапазону дат. | `report_id`, `component_idx` |
| `drill_set_field` | Задаёт сопоставление поля детализации (только для таблиц). | `report_id`, `component_idx`, `drill_category_id`, `drill_direction`, `drill_selected` |
| `conditional_rule_add` | Добавляет правило условного форматирования (только для таблиц/сводных). | `report_id`, `component_idx`, `config_overrides={field, operator, value, color, background, whole_row, bold}` |
| `conditional_rule_list` | Перечисляет правила форматирования. | `report_id`, `component_idx` |
| `conditional_rule_delete` | Удаляет правило по индексу. Необратимо. | `report_id`, `component_idx`, `field_index` |
| `geodata_list` | Перечисляет загруженные на портале файлы GeoJSON (для choropleth-карт). | — |
| `map_set_geokeys` | Гео-привязка карты в одном из режимов: bubble (`latfield`/`lonfield`), choropleth (`geo_type`/`geofield`) или мультислой. Перезаписывает прежнюю привязку. | `report_id`, `component_idx`, `config_overrides` |
| `map_get_geokeys` | Читает текущую гео-привязку карты. | `report_id`, `component_idx` |
| `tabs_button_list` | Перечисляет кнопки навигации в `TabsPanel`. | `report_id`, `component_idx` |
| `tabs_button_add` | Добавляет кнопку навигации в `TabsPanel`. | `report_id`, `component_idx`, `title`, опц. `config_overrides={link, fill_color, text_color, link_target}` |
| `tabs_button_delete` | Удаляет кнопку по индексу. Необратимо. | `report_id`, `component_idx`, `field_index` |

**Ключевые параметры:**
- `calc_expression` — выражение вычисляемого поля по полям датасета, например `amount * 1.2` или `SUM(amount) / COUNT(id)`.
- `target_axis` — ось для добавляемого поля: `values`, `categories`, `rows` или `columns` (по умолчанию `values`).
- `field_id` — строковый идентификатор поля внутри компонента (присваивается при добавлении поля).
- `field_index` — отсчитываемый с нуля индекс элемента (правила/кнопки/уровня) в его списке.
- `config_overrides` для `conditional_rule_add` — `field`, `operator` (`>`, `>=`, `<`, `<=`, `=`; алиасы `gt`/`gte`/`lt`/`lte`/`eq`), `value`, плюс опц. `color`, `background`, `whole_row`, `bold`, `indicator`.
- `config_overrides` для `map_set_geokeys` — набор зависит от режима: bubble (`latfield`, `lonfield`); choropleth (`geo_type` из `geodata_list`, `geofield`); мультислой (`geo_type`, `geofield`, `point_id_field`, `latfield`, `lonfield`, опц. `tooltip_field`).

**Пример:**
```text
component_axes(
  action="conditional_rule_add",
  report_id=35,
  component_idx=0,
  config_overrides={
    "field": "amount",
    "operator": ">",       # > >= < <= = (или gt/gte/lt/lte/eq)
    "value": 1000,
    "background": "#f44336",
    "whole_row": True       # подсветить всю строку
  }
)
```

**Подсказки/типичные ошибки:**
- Условное форматирование работает только на таблицах и сводных таблицах; на других типах вернётся ошибка с указанием поддерживаемых типов. Операторы `!=`, `in`, `starts_with`, `regex` не поддерживаются.
- `page_remove`, `drill_delete_level`, `conditional_rule_delete`, `tabs_button_delete`, `calc_field_remove` необратимы; `page_remove` дополнительно удаляет все компоненты страницы.
- Для choropleth-карты `geo_type` берётся строго из `geodata_list` (загрузка своего GeoJSON через MCP не поддерживается); для произвольных координат используйте режим bubble.

## `component_styling`

**Назначение:** Визуальное оформление компонента — условное форматирование таблиц/сводных, надёжная сортировка по полю и гео-привязка карты. Это подмножество действий `component_axes`, выделенное для частых задач оформления. Применяйте для подсветки значений, фиксации порядка категорий и привязки карты к данным.

**Режим:** В `readonly` доступны `help`, `conditional_rule_list`, `geodata_list`, `map_get_geokeys`. Требуют `--readwrite`: `conditional_rule_add`, `conditional_rule_delete`, `field_sort_set`, `map_set_geokeys`.

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
|---|---|---|
| `help` | Список действий или справка по действию. | `value_field` = имя действия |
| `conditional_rule_add` | Добавляет правило условного форматирования (только таблицы/сводные): цвет текста/фона, подсветка строки, жирность по условию на поле. | `report_id`, `component_idx`, `config_overrides={field, operator, value, color, background, whole_row, bold}` |
| `conditional_rule_list` | Перечисляет правила форматирования компонента. | `report_id`, `component_idx` |
| `conditional_rule_delete` | Удаляет правило по индексу. Необратимо. | `report_id`, `component_idx`, `field_index` |
| `field_sort_set` | Задаёт порядок сортировки по полю компонента (перезаписывает прежний). Это надёжный способ упорядочить категории графика. | `report_id`, `component_idx`, `value_field`, опц. `config_overrides={'order':'asc'\|'desc'}` |
| `geodata_list` | Перечисляет доступные на портале файлы GeoJSON. | — |
| `map_set_geokeys` | Гео-привязка карты: режимы bubble (`latfield`/`lonfield`), choropleth (`geo_type`/`geofield`) или мультислой. Перезаписывает прежнюю привязку. | `report_id`, `component_idx`, `config_overrides` |
| `map_get_geokeys` | Читает текущую гео-привязку карты. | `report_id`, `component_idx` |

**Ключевые параметры:**
- `value_field` — имя поля компонента, к которому применяется сортировка или которое участвует в форматировании.
- `config_overrides` для `field_sort_set` — `{'order':'asc'}` или `{'order':'desc'}`; передача `order=null` снимает сортировку.
- `config_overrides` для `conditional_rule_add` — `field`, `operator` (`>`, `>=`, `<`, `<=`, `=`), `value`, плюс опц. `color`, `background`, `whole_row`, `bold`.
- `field_index` — отсчитываемый с нуля индекс правила в списке (для удаления).
- `config_overrides` для `map_set_geokeys` — зависит от режима: bubble (`latfield`, `lonfield`); choropleth (`geo_type`, `geofield`); мультислой (`geo_type`, `geofield`, `point_id_field`, `latfield`, `lonfield`, опц. `tooltip_field`).

**Пример:**
```text
component_styling(
  action="field_sort_set",
  report_id=35,
  component_idx=23,
  value_field="year",
  config_overrides={"order": "asc"}   # категории по возрастанию года
)
```

**Подсказки/типичные ошибки:**
- Сортировка корректна на числовых полях; строковые поля упорядочиваются лексикографически — для правильного порядка категорий используйте числовое поле. `field_sort_set` — надёжный способ задать порядок (в отличие от попыток сортировать через SQL `ORDER BY` или слаг `sort`, которые могут не примениться).
- `conditional_rule_delete` и `map_set_geokeys` перезаписывают/удаляют конфигурацию без возможности отмены.
- Эти же действия доступны и в `component_axes` — выбирайте инструмент по контексту задачи. Справка — `component_styling(action="help", value_field="field_sort_set")`.

## `style_operations`

**Назначение:** Управляет CSS отчёта на уровне всего отчёта (поле `options.CSStext`): получение, проверка, обновление и применение готовой темы из 5 цветов. Применяйте, когда нужно оформить отчёт целиком — шапку, таблицы, графики, фильтры, скроллбар — а не отдельный компонент.

**Режим:** В readonly доступны `get`, `classes_list`, `examples_list`, `validate`. Режим readwrite требуется для `update` и `apply_theme` (оба проходят `check_action("update")`).

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
| --- | --- | --- |
| `get` | Возвращает текущий CSS отчёта (`current_css`), имя и ID. Главный способ сделать бэкап перед записью. | `report_id` |
| `update` | Перезаписывает весь CSS отчёта переданной строкой. Полная замена: прежний CSS теряется. | `report_id`, `css` |
| `validate` | Проверяет синтаксис CSS-строки без обращения к отчёту. Помогает поймать ошибки до записи. | `css` |
| `classes_list` | Список доступных CSS-классов ModusBI с описанием — какие селекторы можно стилизовать. | `category` |
| `examples_list` | Готовые примеры/паттерны CSS по категории (шапка, таблицы, графики и т. д.). | `category` |
| `apply_theme` | Генерирует brand-pack CSS (~150 строк: шапка, графики, фильтры, таблицы, кнопки, скроллбар) из 5-цветной темы и применяет его. По умолчанию дописывает к существующему CSS. | `report_id`, `theme`, `mode`, `kpi_icons` |

**Ключевые параметры:**
- `report_id` (int) — ID отчёта; обязателен для `get`, `update`, `apply_theme`.
- `css` (str) — текст CSS. Для `update` это полная замена всего CSS отчёта (не добавление).
- `category` (str, по умолчанию `"all"`) — фильтр категории для `classes_list`/`examples_list`. Наборы категорий у этих двух действий различаются (например, у примеров `headers`, `colors`, `animations`); передайте `"all"`, чтобы увидеть допустимые ключи.
- `theme` (dict) — для `apply_theme`: `{primary, secondary, bg, accent, text}` (HEX-цвета). Можно частично — недостающие берутся из дефолтной темы.
- `mode` (str: `"merge"` | `"replace"`, по умолчанию `"merge"`) — для `apply_theme`: дописать к текущему CSS или затереть его целиком.
- `kpi_icons` (dict) — для `apply_theme`: `{component_idx: url}` или `{component_idx: {url, size, position}}` — добавляет `background-image` к KPI-компонентам (нативного слота под иконку у них нет).

**Пример:**
```text
style_operations(action="apply_theme", report_id=35,
                 theme={"primary": "#1B7B45", "secondary": "#E8F5E9",
                        "bg": "#FFFFFF", "accent": "#FF6B35", "text": "#1A1A1A"},
                 mode="merge")  # дописать тему к уже имеющемуся CSS, не затирая правки
```

**Подсказки/типичные ошибки:**
- `update` необратим и заменяет весь CSS целиком. Рабочий порядок: `classes_list` → `examples_list` → `get` (это и есть бэкап) → слить старый CSS с новым → `update`.
- Для безопасного добавления темы используйте `apply_theme` с `mode="merge"` — он сам читает текущий CSS и дописывает к нему; `mode="replace"` затирает.
- Ошибка `требует режим: readwrite` означает, что сервер запущен в readonly; `get`/`validate`/списки при этом остаются доступны.

## `batch_operations`

**Назначение:** Пакетные операции над несколькими объектами за один вызов: добавление/удаление компонентов отчёта, массовое обновление layout, применение CSS к нескольким отчётам и экспорт нескольких отчётов в файлы. Применяйте, чтобы не делать десятки одиночных вызовов при сборке или оформлении дашбордов.

**Режим:** Режим readwrite требуется для `components_add`, `components_delete`, `layouts_update`, `styles_apply`. Действие `reports_export` вызывает `check_action("reports_export")`, но это действие отнесено к разрешённым в readonly — экспорт не меняет состояние портала и доступен в любом режиме.

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
| --- | --- | --- |
| `components_add` | Добавляет в отчёт сразу несколько компонентов; каждый собирается через тот же конструктор, что и одиночный `add` (поддерживает позицию, визуальные параметры, `config_overrides`). Частичный успех: удачные попадают в `added`, проблемные — в `errors`. | `report_id`, `components` |
| `components_delete` | Удаляет из отчёта несколько компонентов по индексам; чистит их записи в layout всех брейкпоинтов. Необратимо. | `report_id`, `indices` |
| `layouts_update` | Массово меняет позицию/размер/`zIndex` компонентов; перезаписывает заданные поля layout на всех брейкпоинтах. | `report_id`, `layouts` |
| `styles_apply` | Записывает один и тот же CSS в несколько отчётов; CSS каждого отчёта перезаписывается целиком. | `report_ids`, `css` |
| `reports_export` | Рендерит несколько отчётов в файлы (по умолчанию PDF) и сохраняет на диск; состояние портала не меняется. | `report_ids`, `format`, `output_dir` |

**Ключевые параметры:**
- `report_id` (int) — целевой отчёт для действий над компонентами/layout.
- `components` (list[dict]) — для `components_add`: каждый элемент повторяет сигнатуру `component_crud(add)` — минимум `component_type` и `title`, а для data-компонентов ещё `value_field` и `dataset_id` (иначе элемент уходит в `errors`). Поддерживаются `position` либо атомарные `x/y/w/h`, `aggregation`, `field_titles`, `where_filter`, визуальные параметры и `config_overrides`.
- `indices` (list[int]) — для `components_delete`: 0-based индексы компонентов (НЕ их id).
- `layouts` (list[dict]) — для `layouts_update`: каждый элемент `{component_idx, x, y, w, h}` (плюс необязательный `z_index`); запись без `component_idx` считается промахом и попадает в `not_found`.
- `report_ids` (list[int]) — для `styles_apply` и `reports_export`.
- `format` (по умолчанию `"pdf"`) и `output_dir` — для `reports_export`; без `output_dir` файлы пишутся в каталог экспорта по умолчанию.

**Пример:**
```text
batch_operations(action="components_add", report_id=35, components=[
    {"component_type": "HsBarAMchartsChart", "title": "Продажи",
     "dataset_id": 5, "value_field": "amount", "category_field": "region",
     "aggregation": "sum"},
    {"component_type": "HsTableReactabularChart", "title": "Детализация",
     "dataset_id": 5, "value_field": "amount", "aggregation": "none"},
])
```

**Подсказки/типичные ошибки:**
- Для data-компонентов (графики, таблицы, KPI) в каждом элементе `components` обязательны `value_field` и `dataset_id`; utility-типы без датасета — исключение.
- В `layouts_update` распространённая ошибка — передать ключ `idx` вместо `component_idx`: такая запись молча не применится и попадёт в `not_found`.
- `components_delete` и `styles_apply` необратимы (удаление компонентов в массовом порядке и полная перезапись CSS целевых отчётов). Перед `styles_apply` имеет смысл забэкапить CSS через `style_operations(action="get")`.
- Ответ содержит `success`, `added`/`deleted`/`updated`/`success_reports`/`exports`, а также `errors[]` и `warnings[]` — при частичном успехе разбирайте именно их.

## `data_export_operations`

**Назначение:** Выгружает данные отдельного компонента отчёта в файл — CSV (локально, без зависимостей) или Excel (серверный рендер через API), а также показывает текущую конфигурацию каталога экспорта. Применяйте, когда нужны сырые данные конкретного виджета в виде файла.

**Режим:** Все действия (`component_csv`, `component_xlsx`, `info`) доступны в readonly — портал не мутируется, `check_action` не вызывается.

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
| --- | --- | --- |
| `component_csv` | Берёт датасет компонента, тянет recordset и сохраняет строки в CSV (UTF-8 с BOM для совместимости с Excel). Колонки — по фактическим ключам строк. | `report_id`, `component_idx`, `output_dir`, `filename`, `limit` |
| `component_xlsx` | Серверный экспорт в Excel через API: учитывает оси/поля компонента, поддерживает промежуточные и общий итоги, форматирование и шаблоны. | `report_id`, `component_idx`, `output_dir`, `filename`, `limit`, `include_subtotals`, `include_totals` |
| `info` | Возвращает каталог экспорта по умолчанию, имя и значение переменной окружения `MODUSBI_EXPORT_DIR`, список поддерживаемых форматов. | — |

**Ключевые параметры:**
- `report_id` (int) и `component_idx` (int, 0-based) — какой компонент какого отчёта выгружать; обязательны для обоих экспортов. Если компонент не привязан к датасету, экспорт вернёт ошибку.
- `output_dir` (str) — каталог для файла. Приоритет источника: параметр `output_dir` → переменная `MODUSBI_EXPORT_DIR` → `~/Downloads/modusbi_exports`.
- `filename` (str) — имя файла без расширения (расширение добавляется по формату).
- `limit` (int, по умолчанию 10000) — максимум выгружаемых строк; в CSV при срезе возвращается флаг `was_limited`.
- `include_subtotals` / `include_totals` (bool, по умолчанию false) — только для `component_xlsx`: добавить промежуточные итоги и строку общего итога.

**Пример:**
```text
data_export_operations(action="component_xlsx", report_id=35, component_idx=0,
                       include_totals=True, filename="sales_data")
# Excel-файл попадёт в каталог экспорта; в нём будет строка общего итога
```

**Подсказки/типичные ошибки:**
- Компонент должен быть привязан к датасету: dataset_id ищется в `config` и в полях осей; если его нет — вернётся `Component not linked to dataset`.
- Формат определяется самим действием (`component_csv` / `component_xlsx`), а не параметром `format` отчётного экспорта; для выгрузки целого отчёта в PDF/PPTX используйте `report_operations(action="export")` или `batch_operations(action="reports_export")`.
- Если CSV/XLSX не сохраняется, проверьте доступность источника данных датасета — типичная причина в недоступности recordset.

## `security_operations`

**Назначение:** Управляет построчной безопасностью (Row Level Security, RLS) на уровне датасета через поля `rls` и `query_rls`. RLS добавляет фильтр, который автоматически применяется ко всем запросам данных и может использовать плейсхолдер `:current_user_id`. Применяйте, когда разным пользователям нужно видеть только свой срез строк.

**Режим:** В readonly доступны `status`, `list_enabled`, `test` (они не вызывают `check_action`). Режим readwrite требуется для `enable`, `disable`, `update_filter` (каждое проходит `check_action("update")`).

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
| --- | --- | --- |
| `status` | Возвращает текущее состояние RLS датасета: включён ли флаг, текст фильтра, есть ли он. Используйте как бэкап перед записью. | `dataset_id` |
| `enable` | Включает флаг RLS у датасета, сохраняя текущий `query_rls`. Сам по себе данные не отфильтрует без заданного фильтра. | `dataset_id` |
| `disable` | Снимает флаг RLS и очищает фильтр. Эффект немедленный: все строки снова видны всем, у кого есть доступ. | `dataset_id` |
| `update_filter` | Перезаписывает текст RLS-фильтра и одновременно включает флаг. Прежний `query_rls` теряется. | `dataset_id`, `rls_query` |
| `list_enabled` | Перечисляет все датасеты, у которых включён RLS, с их фильтрами. | — |
| `test` | Проверяет фильтр: если RLS включён, выполняет пробную выборку (несколько строк) и сообщает результат. | `dataset_id` |

**Ключевые параметры:**
- `dataset_id` (int) — ID датасета; обязателен для `status`, `enable`, `disable`, `update_filter`, `test`.
- `rls_query` (str) — для `update_filter`: SQL-фрагмент условия `WHERE`, например `user_id = :current_user_id`; плейсхолдер `:current_user_id` подставляется на стороне портала.
- `enabled` (bool) — параметр сигнатуры для совместимости; включение/выключение делается отдельными действиями `enable`/`disable`.

**Пример:**
```text
security_operations(action="update_filter", dataset_id=5,
                    rls_query="user_id = :current_user_id")
# Включает RLS и задаёт фильтр: каждый пользователь видит только свои строки
```

**Подсказки/типичные ошибки:**
- `disable` и `update_filter` необратимы и сразу влияют на безопасность: `disable` открывает все строки, ошибочный `update_filter` может либо раскрыть лишние данные, либо заблокировать пользователей. Перед записью снимите бэкап через `action="status"` (он возвращает текущий `rls_query`).
- HTTP 400 при записи часто означает, что драйвер источника не поддерживает RLS: `query_rls` работает на SQL-драйверах (например, PostgreSQL); часть драйверов (например, ClickHouse) его отклоняет. Проверьте источник датасета через `datasource_operations(action="list")`.
- Сохранение флага и фильтра через MCP не гарантирует применение RLS к данным: для реального эффекта может потребоваться установка RLS на самом источнике (включается в веб-портале, вне MCP).

## `instance_operations`

**Назначение:** Возвращает сведения о настроенном экземпляре портала, с которым работает сервер. Модель — один экземпляр на процесс: портал задаётся переменными окружения в конфигурации MCP. Применяйте, чтобы проверить, к какому порталу подключён сервер и валиден ли токен.

**Режим:** Оба действия (`list`, `get_active`) только для чтения и доступны в любом режиме, включая readonly.

**Действия (action):**

| Действие | Что делает | Ключевые параметры |
| --- | --- | --- |
| `list` | Перечисляет настроенный экземпляр (в этой модели всегда один — сохранено для совместимости): имя, базовый URL, признак активности, описание. | — |
| `get_active` | Возвращает данные текущего активного экземпляра: URL, имя, состояние токена и прочие поля. | — |

**Ключевые параметры:** Действия не принимают дополнительных параметров — только `action`.

**Пример:**
```text
instance_operations(action="get_active")
# Вернёт {instance: {name, base_url, token_valid, ...}} текущего портала
```

**Подсказки/типичные ошибки:**
- Один процесс обслуживает один портал. Чтобы работать с несколькими порталами, добавьте несколько записей `mcpServers` в конфигурацию MCP — по экземпляру на запись.
- Если `get_active` показывает невалидный токен, проблема в переменных окружения подключения, а не в самом инструменте — он только читает текущую конфигурацию.

Исходные файлы: `app/server.py` (докстринги и сигнатуры инструментов), `app/tools/action_types.py` (полные перечни `action`), `app/tools/style_operations.py`, `app/tools/batch_operations.py`, `app/tools/export_data.py`, `app/tools/security_operations.py`, `app/core/security.py` (разбиение действий на readonly/readwrite), `app/tools/param_docs.py` (канонические описания параметров).
