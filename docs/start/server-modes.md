# Режимы работы сервера

По умолчанию сервер запускается в режиме `readonly` — только чтение. Это защита:
ИИ-клиент вызывает инструменты сервера автономно, без подтверждения каждого шага
человеком, поэтому по умолчанию запрещены любые действия, которые что-то меняют
или удаляют. Если нужно, чтобы ИИ строил и менял отчёты, запустите сервер в
режиме `readwrite`. Всего режимов три — выбор зависит от вашего сценария.

| Режим | Что можно | Когда использовать |
|-----------|------------------------------------------|------------------------------------------------|
| `readonly` | только чтение | по умолчанию; просмотр, выгрузка, аналитика, первый запуск |
| `readwrite` | чтение + создание/изменение/удаление | автоматизация: ИИ строит и меняет отчёты, batch-обработка |
| `demo` | только чтение + лимиты нагрузки | публичные стенды и песочницы с ограничениями |

Формальные определения режимов — см. [../GLOSSARY.md](../GLOSSARY.md).

## Зачем нужны режимы

Режим работы задаёт верхнюю границу того, что вообще способен сделать сервер в
текущем запуске, независимо от того, какой инструмент вызвал ИИ. Это первый рубеж
защиты вашего портала: даже если ИИ-клиент попытается что-то удалить или
перезаписать, в режиме только для чтения запрос будет отклонён ещё на стороне
сервера, до обращения к порталу.

Каждое действие относится либо к чтению (например, получить список отчётов), либо
к записи (например, удалить отчёт). Сервер сверяет тип каждого действия с текущим
режимом и пропускает только разрешённые.

## Как выбрать режим

| Я хочу… | Режим |
|-----------------------------------------|-------------------------------|
| только читать и выгружать отчёты | `readonly` |
| чтобы ИИ строил и менял дашборды | `readwrite` |
| дать доступ публике с ограничением нагрузки | `demo` |
| ограничить любой запуск сверху | флаг `--security-ceiling` (см. ниже) |

Если сомневаетесь — начните с `readonly`. Перейти на `readwrite` можно в любой
момент, перезапустив сервер.

## readonly (по умолчанию)

Режим только для чтения. Включён, если при запуске не указан другой режим.
В нём доступны действия, которые не меняют состояние портала:

- получение данных: `list`, `get`, `summary`, `data`;
- перечисление вложенных сущностей: `groups_list`, `components_list`,
  `fields_list`, `tables_list`, `table_fields`, `types_list`, `classes_list`,
  `examples_list`;
- проверки: `validate`, `check_connection`, `get_active`;
- выгрузка отчётов и данных компонентов в файлы: `export`, `export_info`
  (отчёт), `component_csv`, `component_xlsx` (данные компонента), а также
  пакетная выгрузка `reports_export`.

Выгрузка относится к чтению: она рендерит уже существующие отчёты в файлы и не
изменяет данные на портале.

Любое действие, которое создаёт, меняет или удаляет данные, в этом режиме
запрещено.

## readwrite

Режим чтения и записи. В нём доступно всё из `readonly`, и дополнительно —
действия, изменяющие состояние портала:

- создание и удаление: `create`, `delete`, `add`, `remove`;
- изменение: `update`, `move`, `swap`, `layout_update`;
- применение оформления: `apply`;
- пакетные операции: `components_add`, `components_delete`, `layouts_update`,
  `styles_apply`;

Это режим, в котором ИИ может строить дашборды, добавлять компоненты, настраивать
фильтры и стили. Включайте его осознанно — в нём становятся доступны и
необратимые операции, такие как удаление отчётов.

## demo

Демо-режим. По набору разрешённых действий он совпадает с `readonly` — записывать
нельзя. Дополнительно он накладывает ограничения нагрузки для публичных стендов и
песочниц: лимиты на число операций и выгрузок, на размер выборки данных и объём
создаваемых сущностей. Подходит для безопасной демонстрации, где не нужно ничего
менять, но важно ограничить нагрузку на портал.

## Как включить нужный режим

Режим задаётся флагом при запуске сервера:

```bash
python -m app.server              # readonly (по умолчанию)
python -m app.server --readonly   # явно только чтение
python -m app.server --readwrite  # чтение и запись
python -m app.server --demo       # демо-режим
```

### Жёсткая верхняя граница (security ceiling)

Дополнительно можно задать «потолок» — максимально допустимый режим, который
нельзя превысить флагом запуска. Это полезно, когда конфигурацию запуска
формирует не тот человек, который владеет порталом: владелец фиксирует потолок, и
даже если кто-то добавит `--readwrite`, запись останется заблокированной.

```bash
python -m app.server --readwrite --security-ceiling readonly
# итоговый режим: readonly (потолок строже флага)
```

Потолок можно задать и через переменную окружения `MODUSBI_SECURITY_CEILING`.
По умолчанию потолок равен `readwrite` (то есть фактически не ограничивает).
Действует правило «выигрывает более строгий»: итоговый режим — это более строгий
из двух (выбранный флагом режим и потолок).

Порядок строгости (от строгого к мягкому):

```
readonly  ≥  demo  ≥  readwrite
```

- `readonly` полностью блокирует запись;
- `demo` тоже только чтение, но добавляет лимиты нагрузки;
- `readwrite` — полный доступ, самый мягкий режим.

В журнале запуска сервер печатает итоговый режим, например:
`Server started in READONLY mode (use --readwrite to enable writes)`.

## Типовая ошибка: «требует режим: readwrite»

Если ИИ-клиент пытается выполнить операцию записи (создать, изменить, удалить), а
сервер запущен в `readonly` или `demo`, действие отклоняется с ошибкой вида:

```
Действие 'create' требует режим: readwrite
```

Это не сбой и не ошибка в запросе — сервер штатно защитил портал от изменения.
Что делать:

1. Если изменение действительно нужно — перезапустите сервер с флагом
   `--readwrite`.
2. Если после этого ничего не изменилось, проверьте, не задан ли потолок
   (флаг `--security-ceiling readonly` или переменная
   `MODUSBI_SECURITY_CEILING=readonly`). Потолок строже флага и оставит сервер в
   режиме только для чтения. Потолок мог установить администратор портала —
   уточните у него, можно ли его снять.
3. Если запись не предполагалась — оставьте `readonly`: ошибка означает, что
   защита сработала верно, и стоит пересмотреть сам запрос к ИИ.

## Где это реализовано

Проверка режима выполняется на стороне сервера для каждого вызова инструмента, до
обращения к порталу. Запросы к порталу идут не «чистым» REST, а как именованные
действия поверх HTTP (action/command), и режим сверяется с типом действия раньше,
чем такой запрос будет отправлен. Подробности реализации — разбиение действий на
чтение и запись, механизм потолка и связь с разграничением доступа на уровне
строк (RLS) — описаны в исходном коде модуля безопасности сервера.
