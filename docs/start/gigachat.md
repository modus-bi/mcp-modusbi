# Компактный профиль инструментов GigaChat

Профиль экспериментальный. [Результаты проверок и ограничения](gigachat-validation.md)
отделяют локальные тесты сервера от приёмки реальных генераций модели.

Профиль выбирается явно при запуске сервера из исходников:

```sh
python -m app.server --tool-profile gigachat
```

По умолчанию сохраняется режим readonly. Для разрешённых изменений тестового
отчёта используйте `--readwrite`; `--security-ceiling readonly` продолжает
блокировать запись. Переменная `MODUSBI_TOOL_PROFILE=gigachat` равнозначна
параметру профиля. Без этого параметра работает прежний каталог инструментов.
Готовый бинарник старого релиза новый профиль не содержит.

Подключение к порталу использует существующие `MODUSBI_URL`,
`MODUSBI_USERNAME`, `MODUSBI_PASSWORD`. GigaChat API key нужен клиенту модели,
а не этому MCP-серверу. Сервер не обращается к API модели и не хранит её ключ.

## Рабочая последовательность

1. `giga_find_datasets` — найти источники: передайте массив `names`.
2. `giga_read_dataset` — прочитать все поля и ограниченный образец строк.
   Возвращает типы, подписи, описания и статистику **выборки**. Уникальность
   в образце не означает уникальность во всём источнике.
3. `giga_query_dataset` — независимо от отчёта проверить исходные суммы,
   отношения сумм, группировку и отобранный срез. Принимает поля и типизированные
   метрики, не принимает SQL. Процент возвращается исходной долей.
4. `giga_list_report_groups` и `giga_create_report` — получить ID нового отчёта.
5. `giga_set_kpi` или `giga_upsert_components` — записать полную спецификацию
   KPI/графика/статического текста. Для таблицы вызывайте `giga_set_table`,
   для HTML из данных — `giga_set_rich_text`, для заголовка и периода —
   `giga_set_header`.
6. `giga_bind_report_filter` — сопоставить поле общего фильтра каждому датасету.
7. `giga_select_filter` — проверить выбранный срез; `values: []` сбрасывает выбор.
8. `giga_arrange_report` — расположить компоненты по логическим рядам.
9. `giga_inspect_report` — проверить сохранённую структуру и фактические строки.
10. Для оформления прочитайте `giga_inspect_report(include_style=true)` и вызовите
   `giga_apply_dashboard_preset`. Это применяет компактную структуру и светлые
   стили. Сам вызов не означает приёмку отчёта.

Для точечных изменений предпочтительны `giga_set_bar_options` (ориентация и
накопление) и `giga_set_table_rules` (подсветка одного существующего столбца).
Они сохраняют остальные метрики, поля, цвета и привязки. Не пересылайте весь
отчёт, чтобы изменить одну настройку.

`metrics` заменяет **весь** список показателей графика. `columns` таблицы по
умолчанию объединяется по точному `field`: пропущенные столбцы, порядок,
ширины и локальные фильтры сохраняются, новые столбцы добавляются в конец.
Пропущенные свойства существующего столбца (например подсветка) сохраняются;
явные свойства обновляются. Для намеренного удаления столбцов передайте
`columns_mode="replace"` и полный новый список. Дубли `field` запрещены.
`key` идентифицирует
компонент внутри конкретного отчёта, а не во всём портале.
Вид визуализации можно изменить с сохранением ключа и привязки фильтра.
`giga_remove_components` удаляет лишние компоненты профиля по ключам; общие
фильтры и компоненты без метаданных профиля этот инструмент не удаляет.
В `giga_arrange_report` отсутствующие `width`/`height` сохраняют текущие размеры.

## Другие визуализации

`giga_list_visualizations` возвращает полный каталог 28 native-типов исходного
builder, фактическую доступность на портале, оси и ограничения. Наличие типа в
каталоге не означает подтверждённую отрисовку. Количественные графики/таблицы,
фильтры и контентные компоненты учитываются отдельно.

`giga_set_visualization` использует исходные Modus builders и явные оси:
размерности передаются в `fields`, расчёты — в `metrics`. Например, Bubble
имеет `xvalues`, `yvalues`, `values`; Pivot — `rows`, `columns`, `values`;
Comparison — `objects`, `indicators`, `values` и два `compare_values`.
Comparison поддерживает одну текстовую размерность объектов, одну текстовую
размерность показателей и одну числовую метрику. Если `indicator_values` не
заданы, сервер читает distinct значения источника; больше 100 требует явного
выбора подмножества. Дополнительная серия пока отклоняется. Для установленного
renderer используется повтор размерности объекта на неактивной оси series:
он обходит ошибку проверки пустой оси и не добавляет зерно в preview.
Для дерева нужны ровно один числовой `identity`, один числовой `linkage` и
неагрегированные значения. Stock требует поле даты. Leaflet требует
числовые координаты с агрегацией max/min/avg и явной геопривязкой.
`component_type` ограничен enum исходных типов. `axes` обязателен; для каждой
native-метрики обязателен `kind`, включая явный `raw` для дерева и параллельных
координат. minimum/maximum проверяются только у спидометра.

Для обычной таблицы, KPI и простого общего фильтра используйте отдельные
короткие инструменты; native-вызов не позволяет обойти защиту таблицы.
Активные иерархические фильтры и переключатели категорий пока не поддерживаются
компактным профилем: каталог обозначает это, запись отклоняется явно.
Для этих двух возможностей доступен стандартный MCP.

## Самопроверка модели

### Деревья, карты и общий фильтр

Предпочтительные короткие инструменты: `giga_set_tree`, `giga_set_map`,
`giga_set_tilemap`. Они принимают роли полей любого изученного источника;
имена полей демонстрационного отчёта на сервере не зашиты.

- Дерево: ID, родитель, подпись, цвет и числовой размер. Тип raw-текста берётся
  из схемы. Проверяются уникальность ID, циклы, родители и безопасный диапазон
  числовых ID для JavaScript. Размер неотрицательный, NULL не подменяется нулём.
- Leaflet: ID точки, широта, долгота и показатель. Координаты указываются один
  раз: MCP сам добавляет их в native-данные. Одна категория — одна пара координат;
  несколько строк одного ID с той же парой допустимы. Проверяются диапазоны.
- Tilemap использует полный словарь90названий установленного renderer, а не
  ручной словарь отчёта. Различия `г.`/`город` и скобочные официальные уточнения
  нормализуются в вычисляемой категории; исходный датасет не изменяется.
  Нераспознанный регион отклоняется до сохранения и не исчезает молча.
- `giga_set_visualization(..., fields_mode="merge")` сохраняет пропущенные
  значения/оси существующего дерева или карты. Удаление полей и смена источника
  требуют явного `fields_mode="replace"`.
- `giga_bind_report_filter` связывает общий срез со всеми источниками отчёта;
  новые и обновлённые компоненты подхватывают его. Инспектор проверяет текущие
  и исходные привязки. Выбор и сброс выполняются `giga_select_filter`.

Проверка геометрии ограничена10000строками (для Tilemap — distinct-регионами),
превышение означает отказ полной проверки. Дерево в выбранном срезе должно
содержать родителей видимых узлов: MCP не достраивает контекст из других групп
и явно отклоняет такой выбор. Это ограничение также следует учитывать при
проектировании исходных витрин и при выборе фильтра непосредственно в UI.

### Оформление

`giga_list_report_styles` показывает четыре BI-адаптации: `corporate_clean`,
`clean_minimalism`, `swiss`, `warm_minimalism`. Применение:
`giga_apply_dashboard_preset(report_id=..., style="swiss")`.
Поля, формулы, общие фильтры и смысловые цвета данных сохраняются. Стили scoped
по ID управляемых панелей; пользовательский CSS вне блока профиля сохраняется.
Проверка оформления — отдельный браузерный этап, не следствие CSS/API PASS.

Ручной контракт на каждый отчёт не требуется. Модель выбирает поля по задаче,
метаданным и данным, проверяет зерно и исходные вычисления через
`giga_query_dataset`, затем сопоставляет их с сохранённым отчётом через
`giga_inspect_report`, включая выбранный срез и сброс. Поля/формулы конкретных
демонстрационных задач в сервере не зашиты.

`giga_inspect_report` сверяет фактические native-формулы, тип renderer,
подписи, значимые настройки осей и столбцов с сохранённой спецификацией.
`checks_passed` означает техническую согласованность и выполнение запросов;
это не гарантия правильного бизнес-смысла. При недостаточных описаниях и данных
модель должна обозначить неопределённость. Проверка отображения остаётся
отдельным этапом. Тестовый эталон хранится снаружи MCP и не передаётся модели.
В generic upsert поле `category` обязательно: для KPI/статического текста
передайте `""`, для графика — имя поля группировки. Кольцо и график с `series`
имеют один числовой показатель; линия без `series` может содержать факт и план.

Пример KPI после получения собственных `report_id` и `dataset_id`:

```json
{
  "report_id": 1,
  "key": "completion",
  "title": "Выполнение плана",
  "dataset_id": 1,
  "metric": {
    "label": "Выполнение плана",
    "kind": "ratio_of_sums",
    "numerator": "completed_amount",
    "denominator": "plan_amount",
    "format": "percent",
    "decimals": 1
  }
}
```

Доля 0.75 выводится как 75%. Расчёт отношения использует отношение сумм, а не
среднее процентов строк. Нулевой знаменатель даёт «н/д». В `giga_set_table`
указываются готовые поля строк: `field`, `label`, `format`; выбора агрегации нет.

Табличная подсветка задаётся `cell_rules` числового показателя. Пороги сравниваются
с исходным числом: для процентов `value: 1` означает 100%. Применяется первое
подходящее правило. Допустимы `gt`, `gte`, `lt`, `lte`, `eq` и цвет `#RRGGBB`.
HTML динамического текста берётся из `field` выбранного датасета через
`giga_set_rich_text`. Он связывается с общим фильтром автоматически.

## Проверка и ограничения

TreeMap с двумя уровнями задаётся двумя полями `categories`; профиль переводит
их в native category+series, чтобы frontend сохранил оба уровня. Для более двух
уровней используйте Sunburst: TreeMap не обрезает лишние уровни молча.
Pivot сортирует размерности через native `pivotOrder` и передаёт агрегацию в
`pivotAgg`, включая min/max/avg/count. Выражения с агрегатами внутри расчётного
поля Pivot пока отклоняются; прямые числовые агрегации поддерживаются.
Длинная обычная таблица получает прокрутку внутри своего блока. Короткая таблица
сохраняет естественную высоту строк; нижние записи не обрезаются скрытым overflow.
Comparison не принимает повторяющиеся выбранные показатели.
Если исходное поле используется сразу в нескольких ролях (например, группировка
и COUNT либо MIN и SUM), результат запроса получает разные имена колонок.
`preview_bindings` и `field_outputs` связывают каждое имя с native-полем, осью
и агрегацией. Это исключает перезапись одного результата другим.

Названия компонентов данных меняйте через `giga_rename_component`: он сохраняет
оси, роли полей, формулы, фильтры, размер и оформление. Неявная замена вида или
источника по прежнему ключу отклоняется. Для намеренной замены у
`giga_upsert_components` есть `replace_kind=true`, у native-инструмента —
`fields_mode=replace`, у таблицы — явный `replace`.

В compact-профиле минимальная высота дерева — 26 строк сетки, Tilemap — 30,
Leaflet — 24: это запас для читаемых подписей, легенд и элементов управления. Короткие
инструменты задают его автоматически; слишком плотная компоновка отклоняется
до записи. Это правило renderer, без отдельного контракта на каждый отчёт.
При native merge пропущенные размеры и логический ряд сохраняются.

`giga_query_dataset` выводит тип raw-полей из схемы источника, включая текст и
даты. Не требуется повторять `format=text` для независимого чтения этих полей.
Клиенту GigaChat рекомендуется ограничивать фазы чтения фактическими результатами:
после получения схем/каталогов/исходных запросов запросить один текстовый итог
с `function_call=none`, затем перейти к построению. Финальная проверка — отдельная
фаза со свежим inspect выбранного среза и сброса, `checks_passed=true` и независимыми
запросами полных источников и срезов. Это логика клиента API; сервер MCP сам не
управляет режимом генерации модели. Ограничение цикла не подтверждает правильность
бизнес-смысла или отображения.

- Предварительная проверка полей, запросов и сетки выполняется до записи.
  Затем сервер перечитывает конфигурацию и сверяет её с отправленной.
- Повтор неизменённой операции возвращает `changed: false` без нового PUT.
  Это относится к управляемым компонентам, а не к произвольным параллельным
  изменениям других клиентов. Блокировки действуют внутри одного процесса.
- При неизвестном результате записи возвращается `WRITE_NOT_VERIFIED`.
  Сначала перечитайте отчёт; не повторяйте запись вслепую.
- `checks_passed` означает проверку структуры и запросов. Он **не** подтверждает
  бизнес-правильность, отображение, скриншоты или принятие отчёта пользователем.
  `browser_verified` сервер самостоятельно не устанавливает.
- Форматирование чисел KPI и таблиц использует PostgreSQL `TO_CHAR`.
  Шаблоны используют литеральные разделители, чтобы результат не зависел от
  `lc_numeric` ([правила PostgreSQL](https://www.postgresql.org/docs/current/functions-formatting.html)).
  Поддержка других SQL-диалектов не заявлена; несовместимый запрос отклоняется
  на предварительной проверке. Графики сохраняют числовые значения.
- Выбор фильтра проверяется по ограниченному набору до 1000 значений.
- Пользовательские CSS-правила вне блока `modus-gigachat` сохраняются.
  Правила профиля ограничены ID управляемых панелей.
- Один пользователь портала поддерживает один сеанс. Для работы MCP и
  одновременной проверки в браузере нужны разные учётные записи.

Локальная проверка:

```sh
python -m pytest app/tests/test_gigachat_profile.py -q
python -m pytest -q
```

Схемы функций передаются с явными типами и описаниями, без `$ref` и nullable
union. Реальная валидация Pydantic и ограничения режима безопасности сохранены.

### Самопроверка и читаемость

`giga_inspect_report` возвращает `verification_plan`: независимые запросы,
полученные из сохранённых полей, зерна и формул, с группировкой одинаковых
расчётов. Ручной контракт для каждого отчёта не нужен. Выполните запросы
через `giga_query_dataset`, сравните возвращённые значения с данными отчёта,
затем отдельно проверьте каждый общий фильтр и сброс. Ограниченный
(`truncated=true`) запрос остаётся неполным доказательством.

План не подтверждает бизнес-смысл выбранных полей. `checks_passed` и факт
вызовов функций также не заменяют независимую проверку чисел и браузер.
Код, написанный в текстовом ответе модели, не выполняется.

В API-клиенте при незавершённой проверке можно запросить конкретную функцию
через `function_call={"name":"giga_query_dataset"}`: аргументы генерирует
модель. Такой режим описан в [документации GigaChat](https://developers.sber.ru/docs/ru/gigachat/guides/functions/function-calling-modes).
Храните журнал реальных вызовов и ограничивайте отсутствие прогресса двумя
повторами; не исполняйте код, извлечённый из текста ответа.

Для native-размерностей и raw-осей доступен `field_labels=[{field,label}]`:
меняется подпись, исходное поле сохраняется. Плотные сводные, Parallel и
Tilemap автоматически получают отдельный ряд; фильтры отделяются от
диаграмм. Sunburst переносит длинные названия, Tilemap использует крупные
контрастные значения и поясняет серые регионы. Для столбцов и области
шкала включает ноль, сохраняя возможность отрицательных значений.

В `giga_query_dataset` каждый элемент `metrics` требует явного `kind`:
`raw` для чтения строк, `sum`/`count` и другие агрегаты для расчётов.
Текст, даты и время при raw-чтении получают текстовый формат автоматически.
При `truncated=true` возвращается `query_complete=false`: увеличьте лимит
того же запроса до 1000, сохранив поля и зерно. Если результат по-прежнему
усечён, полная проверка не выполнена; такой запрос нельзя считать доказательством.

Для новых текстовых столбцов таблицы с пропущенным `format` выбирается
текстовый формат. При merge существующие форматы и отсутствующие в запросе
столбцы сохраняются. Явный числовой формат текстового поля отклоняется.

В Comparison `indicator_mode=all` по умолчанию при сохранении получает все
фактические показатели источника, максимум 100. Для намеренного подмножества
используйте `indicator_mode=selected` и непустой `indicator_values`.
Состав списка фиксируется при upsert: появление новых значений в источнике
потребует повторного сохранения компонента.

`kind=count` с пустым или отсутствующим `field` считает все строки (`COUNT(*)`).
С указанным точным полем считает только значения, отличные от NULL.
Звёздочку и SQL в `field` передавать нельзя. Правило одинаково для запросов
источника, KPI и native-диаграмм.

Числовые оси `values/xvalues/yvalues` обычных диаграмм принимают `metrics`
с явным `kind`, а не неявные raw `fields`. Ошибка `AXIS_METRICS_REQUIRED`
поясняет, как перенести поле в метрику; агрегацию выбирает модель по задаче.
Для Tree и Parallel сохраняются raw-поля. Явные raw-координаты Bubble
допускаются; если другой показатель агрегирован, план проверки включает
raw-координаты в зерно группировки. Bubble получает отступы шкал 20%,
чтобы большие маркеры не обрезались в узких компонентах.

Если source-запрос содержит агрегаты и raw-поля вне `group_by`, MCP выполняет
два независимых чтения: `rows/columns` сохраняют заданные агрегаты и зерно,
`diagnostic_detail.rows/columns` возвращают raw-детали с ключами групп.
Признак `grain_split=true` явно обозначает разделение; формулы не меняются,
поля не теряются. Нельзя связывать строки разных блоков по позиции,
общего транзакционного snapshot нет. Ошибка или усечение детали не дают
полной проверки. Для деталей с ключами действует лимит 24 столбца.
Pure-raw запрос с несовместимой группировкой остаётся ошибкой.
