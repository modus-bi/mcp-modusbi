# Типовые проблемы и их решения

Этот справочник собирает повторяющиеся ситуации, на которые натыкаются при сборке
отчётов и дашбордов через MCP-сервер ModusBI: что вы видите (симптом), почему так
устроено (причина) и что сделать (решение). Цель — чтобы человек, впервые работающий
с проектом, мог быстро понять, в чём дело, и не тратить время на одни и те же грабли.

Аудитория: разработчики интеграций, аналитики данных, инженеры по качеству.

Базовые термины (`отчёт`, `компонент`, `датасет`, `config`, `слаг`,
`config_overrides`, `рендер`, `фильтр`, `alias`, режимы `readonly`/`readwrite`)
определены в [словаре терминов](../../GLOSSARY.md).

Сервер использует протокол **JSON-RPC 2.0** поверх stdio для общения с
клиентом-ассистентом — инструменты вызываются как RPC-методы, это не REST. К самому
порталу сервер обращается уже по HTTP (POST-запросы с командой/действием в теле). Эта
многоуровневость и порождает часть проблем ниже: между записью настройки и её
отображением на экране стоит несколько слоёв.

## 1. Слаг применился, но рендер не изменился

**Симптом.** Вызов изменения компонента вернул успех, слаг попал в очищенный набор
записанных настроек — но на экране ничего не поменялось.

**Причина.** Запись настройки в `config` и её отрисовка на экране — два независимых
шага. Сервер отвечает за то, что значение корректно лежит в `config` по правильному
адресу. А рисует компонент фронтенд портала: он читает `config` из браузера и
превращает его в картинку. Не каждая настройка имеет видимый эффект для каждого типа
компонента — фронтенд при отрисовке может просто не обращаться к этому ключу, либо
эффект проявляется только в паре с другой настройкой, либо элемент рисуется одинаково
независимо от значения. Это нейтральное свойство конкретной пары «настройка + тип
компонента», а не ошибка вызова — его описывает принцип, называемый
**рендер-контрактом** (см. [концепция «корректный конфиг ещё не картинка»](../../architecture/concepts/render-contract.md)).

**Решение.**

- Финальную проверку делайте в браузере: откройте отчёт, сравните «до» и «после» на
  заметно разных значениях (контрастная пара) — так разница очевиднее.
- Читайте предупреждения в ответе. Сервер возвращает не только записанные настройки,
  но и список предупреждений. Различайте два разных исхода:
  - предупреждение про «не применимо к данному типу» (`not applicable`) или
    «устаревший слаг» (`deprecated`) означает, что слаг **не записан** вовсе — выберите
    подходящий компоненту слаг или другой приём оформления;
  - предупреждение о «немой» настройке означает, что слаг **записан, но на экране его
    может быть не видно**; при необходимости задайте сопутствующую настройку.
- Если нужного эффекта нет через слаг, попробуйте CSS отчёта (см.
  [стилизацию](../../architecture/components/styling.md)).

## 2. Истёк доступ к порталу / ошибка авторизации

**Симптом.** Вызов, который раньше работал, вдруг падает с ошибкой доступа; похоже,
что сеанс с порталом «протух».

**Причина.** Сервер авторизуется на портале и получает токен с ограниченным временем
жизни. Когда токен истекает, портал отвечает отказом в доступе.

**Решение.** В штатном режиме сервер обрабатывает это сам: при получении отказа по
истёкшему токену он молча переавторизуется и повторяет запрос (есть защита от
одновременной повторной авторизации при параллельных вызовах). Поэтому чаще всего
достаточно повторить операцию.

Если ошибка доступа повторяется устойчиво:

- проверьте состояние подключения: `instance_operations(action="get_active")` вернёт
  объект `instance` со сведениями о текущем портале и флагом валидности токена
  (`token_valid` внутри этого объекта);
- убедитесь, что для операций записи сервер запущен в режиме `readwrite` (см.
  [словарь терминов](../../GLOSSARY.md), «Режимы readonly / readwrite»): отказ с текстом
  про «требует режим readwrite» — это не про авторизацию, а про то, что сервер
  поднят в режиме только чтения;
- проверьте корректность учётных данных подключения (URL портала, логин/пароль
  задаются конфигурацией сервера, не в самом вызове).

## 3. Выпадающие списки фильтров перекрываются

**Симптом.** Список значений фильтра, который должен раскрываться поверх соседних
виджетов, оказывается обрезанным нижестоящим компонентом или спрятанным под ним.

**Причина.** Раскладка дашборда помещает каждый компонент в свою ячейку сетки, и эта
ячейка визуально изолирована от соседних (браузер создаёт для неё отдельный контекст
наложения слоёв из-за CSS-трансформаций раскладки). Попытка поднять слой через
позицию компонента (`zIndex`) не помогает: эта настройка не превращается в нужное
CSS-правило.

**Решение.** Поднять слой именно у ячеек сетки с контейнером фильтров, добавив отчёту
CSS-правило через `style_operations`:

```python
style_operations(
  action="update",
  report_id=<id отчёта>,
  css=".react-grid-item:has(.hsFilterControlPanel) { z-index: 100 !important; }"
)
```

Селектор использует CSS-псевдокласс `:has()` (поддерживается актуальными браузерами) —
он выбирает ячейки сетки, внутри которых лежит контейнер фильтров. Рекомендуется
добавлять это правило в каждый отчёт с фильтрами.

Важно: действие `update` у `style_operations` **заменяет весь CSS отчёта целиком**.
Если у отчёта уже есть свой CSS (например, оформление темы), сначала получите его
действием `get`, объедините с правилом z-index и отправьте объединённый текст одним
вызовом `update` — иначе ранее заданное оформление будет затёрто.

Подробнее — [паттерны фильтров](../../architecture/components/filter-patterns.md) и
[стилизация](../../architecture/components/styling.md).

## 4. Столбцы графика «схлопнулись»

**Симптом.** После настройки ширины столбцов столбчатая диаграмма рисует их как
тонкие нитки или они почти исчезают.

**Причина.** Ширина столбца на этих диаграммах задаётся **процентом** в диапазоне
`10–100` (где `100` — максимально широкий столбец). Внутри сервер сам преобразует это
число в долю, понятную фронтенду. Если передать значение вне допустимого диапазона
(например, очень большое), оно либо не применится при валидации, либо приведёт к
схлопыванию столбцов.

**Решение.** Передавайте целое число в диапазоне `10–100` (процент от шага сетки
столбцов):

- `40` — столбцы шириной примерно 40 % шага;
- `80` — широкие столбцы;
- значения вне `10–100` могут не примениться или вызвать ошибку валидации.

Сервер сам переводит процент в нужную фронтенду долю — отдельно конвертировать его не
нужно. Если столбцы уже испорчены прежней настройкой ширины, задайте корректное
значение `10–100` заново; в крайнем случае компонент можно пересоздать. Сортировка
столбцов на ширину не влияет и безопасна.

## 5. Ошибка при смене alias на полях привязанного датасета

**Симптом.** Попытка изменить человекочитаемые имена полей (`alias`) на датасете
завершается ошибкой со стороны портала, хотя сам датасет существует.

**Причина.** Портал блокирует переименование полей датасета, которые уже используются
в компонентах какого-либо отчёта. Менять `alias` поля, на которое уже завязаны оси
графиков/таблиц, нельзя — это защита от рассинхронизации привязок.

**Решение.** Соблюдайте правильный порядок при создании отчёта:

1. создать датасет;
2. **задать все нужные `alias` полей**;
3. **только после этого** добавлять компоненты, которые привязываются к этим полям.

Если `alias` всё же надо поправить на уже привязанном датасете: создайте новый датасет
с нужными `alias`, перепривяжите компоненты на него, затем удалите старый. (Это правило
не касается некоторых служебных привязок, не создающих стандартных полей — например
карты, где привязка устроена иначе.)

См. также [рецепты данных](../../architecture/components/data-recipes.md) и
[руководство аналитика](../analyst.md).

## 6. Пустая строка `""` вместо «не задано» в опциональных параметрах

**Симптом.** Необязательный строковый параметр (заголовок, имя поля, цвет, выражение
и т. п.) ведёт себя не так, как ожидалось: настройка будто бы не сбрасывается или,
наоборот, что-то перезаписывает.

**Причина.** У многих инструментов опциональные строковые параметры означают «не
менять это» только когда они **не переданы** (`None`). Если же в такой параметр
приходит **пустая строка** `""`, это уже значение, а не «оставить как есть». Сервер
содержит защиту от этой неоднозначности: для ключевых полей он трактует `""` так же,
как «не задано», то есть **не применяет** пустую строку (проверки вида «значение
задано И не пустое»). Это сделано, чтобы случайно пришедшая `""` не затирала
существующие данные.

**Решение.**

- Если параметр менять не нужно — **не передавайте его вообще** (вместо пустой строки
  `""`).
- Если нужно действительно очистить значение — это отдельная операция; пустая строка
  для этого не предназначена и для защищённых полей будет проигнорирована.
- При неожиданном поведении проверьте, не уходит ли в вызов `""` там, где вы имели в
  виду «не трогать».

## 7. Формат ручного сохранения отчёта (массив-обёртка)

**Симптом.** При прямом (ручном) сохранении отчёта в портал приходит ошибка вида
«отчёт с таким наименованием уже существует», хотя отчёт ровно один.

**Причина.** Тело запроса на сохранение ждёт отчёт, **обёрнутый в массив** (список из
одного отчёта), а не «голый» объект отчёта. Если передать одиночный объект, портал
интерпретирует это как попытку создать дубликат.

**Решение.** Передавайте отчёт массивом из одного элемента — `[отчёт]`, а не `отчёт`.
Это касается ручной работы с API сохранения; штатные инструменты MCP
(`report_operations`, `component_crud` и др.) формируют корректное тело сами, и при
работе через них об этом думать не нужно.

## 8. Сравнительная диаграмма требует данных в формате UNPIVOT

**Симптом.** Сравнительная диаграмма (компонент «Сравнительная диаграмма») остаётся
пустой, хотя данные в датасете есть и привязка выполнена.

**Причина.** Этот компонент ожидает данные в «длинном» формате (UNPIVOT): **одна
строка = один объект + название одного показателя + его значение**. Обычная «широкая»
таблица, где показатели лежат в отдельных колонках, ему не подходит — он перебирает
пары «объект × показатель» и не находит их.

**Решение.** Разверните широкую таблицу в длинную через `UNION ALL`:

| объект | показатель | значение |
|---|---|---|
| Регион A | Количество | 1200 |
| Регион A | Сумма | 340 |
| Регион B | Количество | 870 |
| Регион B | Сумма | 510 |

Привязка: поле объекта — в категорию (`category_field`); поле с названиями показателей
(одно строковое поле, значения которого — «Количество», «Сумма» и т. п.) — в показатели
(`column_fields`); числовое поле — в значения (`value_field`). Два сравниваемых объекта
выбираются как два значения поля объекта.

Полный рецепт с примером SQL — [форматы данных для компонентов](../../architecture/components/data-recipes.md).

## 9. Древовидный граф требует числового идентификатора

**Симптом.** Дерево связей (компонент «Древовидный граф») не строит граф или приводит
к сбою отрисовки.

**Причина.** Компонент обрабатывает идентификатор узла как **число** — и ссылку на
родителя тоже. Строковый идентификатор приводит к ошибке преобразования, после чего
граф не строится.

**Решение.** Генерируйте идентификаторы числами, а корень помечайте фиксированным
числом с пустым родителем. Удобный приём — нумерация строк:

```sql
SELECT 0 AS id, NULL::int AS parent_id, 'Все регионы' AS name, SUM(value) AS metric
FROM source_table
UNION ALL
SELECT ROW_NUMBER() OVER (ORDER BY region) AS id,  -- числовой идентификатор узла
       0 AS parent_id,                              -- числовая ссылка на корень
       region AS name,
       SUM(value) AS metric
FROM source_table
GROUP BY region;
```

Привязка: идентификатор узла — в категорию (`category_field`); ссылка на родителя и
числовой показатель — в значения (`value_field`, где первое поле — `parent_id`,
остальные — показатели); агрегация — `none`.

Подробнее — [форматы данных для компонентов](../../architecture/components/data-recipes.md).
