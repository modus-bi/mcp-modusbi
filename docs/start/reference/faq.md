[словаре терминов](../../GLOSSARY.md).

## Почему сервер по умолчанию работает только на чтение и как разрешить запись

При запуске без флага сервер стартует в режиме `readonly` — только чтение. Так
сделано потому, что ИИ-ассистент вызывает инструменты сервера сам, без
подтверждения каждого шага человеком: пока режим только для чтения, ни один вызов
не может создать, изменить или удалить что-либо на портале — даже ошибочный.

Чтобы ассистент мог строить и менять отчёты, запустите сервер с флагом
`--readwrite`:

```bash
python -m app.server              # readonly (по умолчанию)
python -m app.server --readwrite  # чтение и запись
```

Если ассистент пытается выполнить операцию записи в режиме `readonly`, сервер
штатно отклоняет её с сообщением вида «Действие 'create' требует режим:
readwrite». Это не сбой, а сработавшая защита. Подробно про режимы (включая `demo`
и «потолок» `--security-ceiling`) — в
[../server-modes.md](../server-modes.md).

## Как переключиться на другой портал

Один процесс сервера обслуживает ровно один портал. Адрес портала и учётные данные
сервер берёт из переменных окружения при запуске (`MODUSBI_URL`,
`MODUSBI_USERNAME`, `MODUSBI_PASSWORD`). Сменить портал «на лету» внутри запущенного
процесса нельзя.

Чтобы работать с несколькими порталами, заведите **несколько записей в конфигурации
MCP-клиента** — по одной на портал, у каждой свой блок переменных окружения:

```json
{
  "mcpServers": {
    "modusbi-prod": {
      "command": "python",
      "args": ["-m", "app.server"],
      "env": { "MODUSBI_URL": "https://prod.example.com", "MODUSBI_USERNAME": "...", "MODUSBI_PASSWORD": "..." }
    },
    "modusbi-test": {
      "command": "python",
      "args": ["-m", "app.server"],
      "env": { "MODUSBI_URL": "https://test.example.com", "MODUSBI_USERNAME": "...", "MODUSBI_PASSWORD": "..." }
    }
  }
}
```

Каждая запись — отдельный процесс сервера; они не делят между собой подключение и
состояние. Какой именно портал подключён в текущем процессе, можно посмотреть
инструментом `instance_operations` (только чтение).

## Настройка применилась без ошибки, но на экране ничего не изменилось

Это ожидаемая ситуация, а не сбой. Сервер отвечает за то, чтобы записать значение
по правильному адресу внутри `config` компонента. А рисует компонент на экране не
сервер, а фронтенд портала — он читает `config` из браузера и превращает его в
картинку. Поэтому успешный ответ инструмента подтверждает только, что значение
**записано**, но не то, что оно **повлияло на изображение**. Этот принцип называется
рендер-контрактом.

Что делать:

- **Прочитайте предупреждения в ответе.** Сервер возвращает не только записанные
  настройки, но и список предупреждений. Если слаг помечен как «not applicable» или
  «deprecated» — значение вообще не записано, нужен другой слаг. Если есть
  предупреждение, что слаг записан, но рендер его не показывает, — значение в
  `config` лежит, но на картинке его может быть не видно.
- **Проверьте, нет ли парной настройки.** Некоторые значения проявляются только
  вместе с другой настройкой (например, размер подписи имеет смысл лишь при
  включённых подписях).
- **Сверьте в браузере.** Откройте отчёт и сравните «до» и «после» на заметно разных
  значениях. Видимый результат в браузере важнее любых ожиданий.

Полный разбор принципа рендер-контракта —
[../../architecture/concepts/render-contract.md](../../architecture/concepts/render-contract.md). Пошаговый порядок
проверки эффекта в браузере описан в
[../tester.md](../tester.md).

## Чем инструмент (tool) отличается от промпта (prompt)

Это две разные вещи в одном сервере:

- **Инструмент (tool)** — одиночная функция, которую ассистент вызывает напрямую,
  чтобы выполнить конкретную операцию: создать отчёт, добавить компонент, выполнить
  запрос к данным. Один вызов — одно действие.
- **Промпт (prompt)** — готовый многошаговый сценарий, который разворачивается в
  последовательность вызовов инструментов. Например, «создай дашборд из шаблона»:
  промпт описывает, какие инструменты и в каком порядке вызвать, чтобы получить
  результат.

Грубо: инструмент — это отдельный шаг, промпт — заранее собранный маршрут из таких
шагов. И инструменты, и промпты поставляются вместе с сервером и перечисляются
встроенными механизмами MCP. Карта инструментов — [../../architecture/tools/README.md](../../architecture/tools/README.md);
встроенные промпты — [../../prompts/README.md](../../prompts/README.md).

## Почему наружу JSON-RPC, а не REST

Интерфейс между ассистентом и сервером — это **JSON-RPC 2.0** поверх транспорта
stdio. Здесь нет URL-путей и HTTP-глаголов `GET`/`POST`/`PUT`/`DELETE`: ассистент не
обращается к ресурсу по адресу, а отправляет именованный удалённый вызов процедуры.
Все инструменты вызываются через один RPC-метод `tools/call`, а конкретный
инструмент выбирается по имени внутри параметров. Список инструментов и их схемы
параметров клиент получает от сервера встроенным методом `tools/list` — отдельная
спецификация для этого не нужна.

«Этажом ниже» сервер обращается к HTTP-API портала, но и это **не чистый ресурсный
REST**: операция кодируется в теле запроса (поле `command`), почти всё идёт через
`POST /v1/api/...`, а сам объект указывается полем в теле, а не URL-путём. Эта
деталь скрыта от ассистента и полезна в основном при отладке.

Полный разбор всех трёх слоёв (MCP → JSON-RPC → stdio, и HTTP-команды к порталу) —
[../../architecture/concepts/protocol-and-rpc.md](../../architecture/concepts/protocol-and-rpc.md).

## Где взять справку по инструменту

У мультидейственных инструментов есть встроенная самосправка. Вызов с
`action="help"` возвращает список доступных действий, а вызов с указанием
конкретного действия — его описание и пример:

```text
component_crud(action="help")                          # список действий инструмента
component_crud(action="help", slug_category="add")     # справка по действию add
report_operations(action="help", name="clone")         # справка по действию clone
```

Это самый надёжный источник: справка формируется из самого кода сервера и не
расходится с реализацией. Имя параметра, в котором передаётся интересующее действие,
у разных инструментов отличается:

- `report_operations`, `dataset_operations` и им подобные ждут его в параметре `name`;
- `component_crud` ждёт его в параметре `slug_category` (рекомендуемый), но принимает
  и `value_field` как запасной вариант;
- остальные инструменты управления компонентами (`component_filters`, `component_axes`,
  `component_styling`) ждут его в параметре `value_field`.

Если сомневаетесь, сначала вызовите `action="help"` без аргументов и посмотрите
подсказку. Если вызвать инструмент с неизвестным действием, сервер вернёт ответ вида
`{error: "Unknown action: X"}` — это сигнал свериться со списком действий через
самосправку. Карта всех инструментов — [../../architecture/tools/README.md](../../architecture/tools/README.md).

## Как узнать список типов компонентов и слагов настроек

Оба перечня отдаёт сам сервер — это служебные действия инструмента
`component_crud`:

```text
component_crud(action="types_list")   # список доступных типов компонентов
component_crud(action="list_slugs")   # список слагов настроек (config_overrides)
```

`types_list` показывает, какие типы компонентов можно добавить (графики, таблицы,
карты, KPI-блоки и прочее). `list_slugs` показывает слаги — короткие имена настроек,
которые передаются в `config_overrides` при добавлении или обновлении компонента.

Помните про рендер-контракт: то, что слаг есть в списке и записывается без ошибки,
ещё не гарантирует видимого эффекта на конкретном типе компонента — финальную
проверку даёт браузер (см. выше). Подробнее про слаги и три уровня визуальной
настройки — [../../architecture/concepts/components-json-slugs.md](../../architecture/concepts/components-json-slugs.md)
и [../../architecture/components/styling.md](../../architecture/components/styling.md).
