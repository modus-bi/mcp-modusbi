# Проверка экспериментального профиля GigaChat

Состояние на 18 ноября 2026 года: профиль пригоден для дальнейшего тестирования,
но стабильность автоматического построения ещё не подтверждена. Это отдельная
ветка разработки, а не стабильный релиз. Включение и контракты инструментов
описаны в [руководстве профиля](gigachat.md).

## Что проверено

| Уровень | Подтверждённый результат | Границы |
| --- | --- | --- |
| Локальные тесты MCP | 393 теста пройдены | Тесты исходников и имитаций API, без генераций модели и браузерной приёмки |
| Один полный прогон модели | Отчёт с 18 количественными типами компонентов, заголовком и общим фильтром; 350 из 350 проверок данных и конфигурации пройдены | Один управляемый сценарий на синтетических источниках; ручных исправлений конфигурации отчёта после генерации не было |
| Отрисовка этого отчёта | Проверка Chromium при размере окна 1422 × 1000; независимо просмотрен 21 снимок | Проверены также нижняя часть таблицы и выбор среза дерева; мобильный интерфейс и все интерактивные действия не приняты |
| Оформление | Четыре стиля отдельно проверены на инженерных контрольных отчётах | Это проверки оформления, а не четыре дополнительных успешных генерации модели |

Внешний испытательный стенд дополнительно прошёл 89 тестов контроллера/клиента
модели и 49 тестов проверяющих артефакты. Эти инструменты и их приватные журналы
не входят в данный репозиторий; запуск `pytest` здесь не воспроизводит эти
138 проверок или браузерную приёмку.

## Что ещё не подтверждено

Критерий устойчивости — три последовательных полных построения на одной версии
MCP, клиента, модели и сценария, без ручной правки отчётов. Такой серии пока нет.
Во втором прогоне последней серии API модели вернул HTTP 502, затем HTTP 429;
прогон прерван и успешным не считается. Подготовка следующей версии клиента
повторных попыток сама по себе новым успешным прогоном не является.

Пройденный сценарий содержит заданные роли полей. Он проверяет сохранение полей,
формул, зерна группировки, привязок общего фильтра и результата в интерфейсе,
но не доказывает самостоятельное понимание произвольной новой бизнес-витрины.
Следующий этап — незнакомые источники и задачи с неоднозначными метаданными.

В каталоге объявлены 28 native-типов, а полная приёмка охватывает 18
количественных типов плюс простой общий фильтр и заголовок. Вне этой приёмки
остаются два специализированных элемента управления, четыре медиа/контентных
типа и два типа, отсутствовавших на тестовом портале. Список каталога не означает
проверку всех renderer. Не приняты мобильная компоновка, полный набор hover,
выделения, масштабирования и экспорт. Четыре проверенных стиля не означают
проверку всех возможных стилей.

## Как проверять следующие изменения

Локальные проверки из корня репозитория:

```sh
python -m pip install -e ".[dev]"
python -m pytest -q
git diff --check
```

Для испытаний с моделью фиксируйте commit MCP, версию клиента, идентификатор
модели, сценарий и версии источников. Для каждого нового отчёта требуются:

1. Схема и образец исходных данных, явные роли полей и типы метрик.
2. Чтение сохранённой конфигурации и `verification_plan` через инспектор.
3. Независимые запросы источников с теми же формулами, зерном и срезом, сравнение
   с фактическими данными компонентов. Preview инспектора ограничен образцом
   строк и не заменяет полную проверку источника. Усечённые или ошибочные
   результаты нельзя считать доказательством полноты.
4. Выбор и сброс общего фильтра с повторной проверкой данных и привязок.
5. Проверка в браузере: подписи, легенды, отсутствие обрезания, последняя строка
   таблицы, геометрия дерева и карт, доступность фильтра.

Модель выбирает поля по задаче и метаданным. Сервер формирует план проверки из
фактически сохранённого отчёта; отдельный ручной контракт на каждый отчёт ему
не нужен. Управление фазами модели, обязательный вызов функции самопроверки,
учёт токенов и обработка лимитов API выполняются клиентом модели. MCP-сервер
не вызывает GigaChat API, не хранит его ключ и не гарантирует, что произвольный
клиент исполнит этот цикл. Режим readonly и существующий security ceiling
сохраняются независимо от выбранного профиля.

Стоимость нужно считать отдельно от качества: нулевая дополнительная покупка
не означает нулевое потребление квоты. Сохраняйте возвращённый API usage для
успешных ответов; отсутствие usage у оборванного запроса не доказывает нулевого
списания.
