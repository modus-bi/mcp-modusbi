# Руководство разработчика

> ⚠️ **Перед практической работой** прочитайте [../../DISCLAIMER.md](../../DISCLAIMER.md): изменения на портале необратимы (нет отмены/истории), безопасность доступов при работе с LLM — на стороне пользователя.

Этот документ — маршрут разработчика, который впервые открывает исходный код
ModusBI MCP Server и собирается вносить изменения. Он отвечает на три вопроса:
как устроен код, по какому циклу его менять и где добавлять новое.

ModusBI MCP Server — это сервер на Python (на фреймворке FastMCP), который даёт
ИИ-ассистенту набор инструментов для работы с BI-отчётами портала ModusBI.
Ассистент вызывает инструменты по протоколу MCP (формат сообщений — JSON-RPC 2.0,
транспорт — стандартный ввод/вывод процесса, stdio). Инструмент внутри обращается
к HTTP-API портала, где операция кодируется в теле запроса (например, полем
`command`), а не выражается ресурсным URL. Эта рамка важна и при чтении кода:
наружу — RPC-методы, внутрь — действия поверх HTTP.

Начать вносить изменения можно, не разобравшись сразу во всех слоях. Достаточно
понять путь одного вызова от инструмента до портала — а его легко проследить по
карте кода ниже. Остальное подтянется по мере работы над конкретной задачей.

---

## С чего начать

Пройдите три шага по порядку — каждый следующий опирается на предыдущий.

1. **Разверните сервер локально.** Установка из исходников, переменные окружения
   и режимы запуска — [руководство по установке и эксплуатации](for-devops.md).
   Дополнительный ориентир — раздел «Быстрый старт (запуск из исходников)» в
   [обзорном README документации](../README.md).
2. **Разберитесь в концепциях.** Прочитайте
   [Что такое MCP](../architecture/concepts/what-is-mcp.md) — модель «ИИ → сервер → портал» и
   доменные сущности, затем
   [Протокол: JSON-RPC, а не REST](../architecture/concepts/protocol-and-rpc.md) — как устроен
   обмен сообщениями наружу к ассистенту и действия поверх HTTP к порталу. Если
   встретится незнакомое слово — [словарь терминов](../GLOSSARY.md).
3. **Вернитесь к этому руководству.** Дальше — карта кода, рабочий цикл и места,
   куда добавлять новое.

## Карта кода

Пути указаны относительно корня репозитория.

### Точка входа и регистрация инструментов

| Файл | Роль |
|---|---|
| `app/server.py` | **Главный файл.** Здесь объявлены публичные инструменты (декоратор `@mcp.tool`) и промпты (`@mcp.prompt`), задан жизненный цикл сервера, разбор флагов режима (`readonly` / `readwrite` / `demo`) и единый формат конверта ошибок. |
| `app/__main__.py` | Точка входа `python -m app`: импортирует и вызывает `main` из `app/server.py`. |
| `app/prompts.py` | Генераторы промптов (готовых многошаговых сценариев) и диспетчер `get_prompt`, который `app/server.py` подключает через `@mcp.prompt`. |

Каждый инструмент в `app/server.py` — это Python-функция, помеченная декоратором.
FastMCP сам строит из её сигнатуры JSON Schema параметров, из имени функции —
имя инструмента, из docstring — его описание. Сами функции в `server.py`
тонкие: они проверяют режим и передают работу в диспетчеры из `app/tools/`.

### `app/tools/*` — диспетчеры и доменная логика

Большинство инструментов мультидейственные: первый аргумент `action`
(`create`, `update`, `delete`, `list`, `get`, `add`, …) выбирает операцию, а
внутри файла-диспетчера стоит разветвление по этому значению. У многих
диспетчеров есть `action="help"`, который возвращает список поддерживаемых
действий и примеры.

| Файл | Роль |
|---|---|
| `report_operations.py` | Отчёты: создание, чтение, обновление, удаление, клонирование. |
| `reportgroup_operations.py` | Группы отчётов. |
| `component_crud.py` | Добавление, обновление, удаление компонентов и работа с раскладкой. Здесь же `_apply_visual_overrides` и список типов без датасета. |
| `component_filters.py` | Фильтры компонентов и каскад фильтрации. |
| `component_axes.py` | Оси, вычисляемые поля, drill-down, pivot-связи, табы. |
| `component_operations.py` | Стилизация компонентов (условное форматирование, сортировка полей, настройка геокарт). Реализует инструмент `component_styling`; логика разнесена по нескольким диспетчерам (`component_crud`, `component_filters`, `component_axes`) для читаемости. |
| `dataset_operations.py` | Датасеты: CRUD и создание из SQL (инструмент `dataset_create_from_sql` реализован здесь же). |
| `datasource_operations.py` | Источники данных и предварительная проверка соединения. |
| `query_execute.py` | Выполнение запросов к семантическому слою (`dataset_query`, `query_batch`). |
| `style_operations.py` | CSS уровня отчёта (действие `update` замещает весь CSS целиком). |
| `report_template.py` | Шаблоны отчётов (список, предпросмотр, scaffold). |
| `batch_operations.py` | Пакетные операции над компонентами и отчётами. |
| `export_data.py` | Выгрузка данных и отчётов в файлы. |
| `security_operations.py` | Разграничение доступа на уровне строк (RLS). |

Имя инструмента в `app/server.py` не всегда совпадает с именем модуля: например,
инструмент `component_styling` реализован внутри `component_operations.py`, а
`data_export_operations` — внутри `export_data.py`. Ориентируйтесь на роль файла,
а не на буквальное совпадение имён.

Вспомогательные модули там же: `builders.py` (сборка стартового `config`
компонента), `config_presets.py` (именованные наборы слагов), `layout_helper.py`
(сборка раскладки x/y/w/h), `text_block_helper.py` (текстовые блоки),
`help_texts.py` и `param_docs.py` (тексты для `action="help"` и описания
параметров).

### `app/core/*` — инстансы, безопасность, HTTP-клиент

Слой между диспетчерами и порталом: подключение к порталу, проверка прав и
валидация входа.

| Файл | Роль |
|---|---|
| `instances.py` | Подключение к порталу и HTTP-клиент. Классы `Instance` (адрес портала, токен, сборка URL) и `InstanceManager` (аутентификация, общий пул соединений `httpx.AsyncClient`, повторная авторизация при истёкшем токене). Через этот слой инструменты обращаются к порталу действиями поверх HTTP. |
| `security.py` | Режимы запуска (`readonly` / `readwrite` / `demo`), верхняя граница (security ceiling) и разбиение действий на чтение и запись. Проверка выполняется до обращения к порталу. |
| `validation.py` | Проверка и нормализация входных параметров инструментов. |
| `exceptions.py` | Доменные исключения, на основе которых собирается конверт ошибки для ассистента. |

### `app/tools/config_schema.py` — слаги

Сердце настройки компонентов. Слаг (см. [словарь терминов](../GLOSSARY.md)) —
это короткое плоское имя одной настройки (например, `legend.position`), которое
сервер раскладывает в нужный адрес внутри вложенного `config` компонента. Так
ассистенту не нужно писать сырой JSON-путь.

| Что внутри | Назначение |
|---|---|
| `SLUG_SCHEMA` | Реестр всех слагов: для каждого — тип значения, ограничения, фактический JSON-путь записи, к каким типам компонентов применим. |
| `apply_slug_overrides` | Принимает словарь `{слаг: значение}` (`config_overrides`), проверяет значения и записывает каждое в нужное место `config`. |
| `CHART_TYPE_MAP` | Сопоставление типов компонентов и их вариантов для валидации слагов. |

Поток внутри добавления компонента: диспетчер `component_crud` вызывает билдер из
`builders.py`, который собирает «скелет» `config` (оси, привязка полей, дефолты
типа), затем `apply_slug_overrides` накладывает точечные настройки из
`config_overrides`, и результат записывается в портал.

## Рабочий цикл

Изменения вносите небольшими проверяемыми шагами: правка — перезапуск сервера —
проверка тестом, и только потом следующий шаг.

### 1. Правка

Внесите минимальное изменение в нужный файл (см. карту кода). Держите
правки маленькими: один слаг, один билдер или одно действие за раз — так проще
локализовать проблему, если что-то пошло не так.

### 2. Перезапуск сервера

ИИ-клиент запускает MCP-сервер как дочерний процесс по конфигурации (например, из
записи `mcpServers`). Старый процесс держит уже загруженный код, поэтому после
правки сервер нужно перезапустить, чтобы изменения вступили в силу — обычно это
делается перезапуском MCP-клиента или соответствующего подключения.

Запустить сервер вручную (например, чтобы проверить, что он стартует, и увидеть
итоговый режим в журнале запуска) можно так:

```bash
python -m app.server              # readonly (по умолчанию)
python -m app.server --readwrite  # чтение и запись
```

Подробнее о режимах и верхней границе — [Режимы работы сервера](server-modes.md).

### 3. Проверка (pytest)

Прогоните тесты. Они лежат в `app/tests/`:

```bash
pytest -q                         # весь набор
pytest app/tests/test_config_schema.py -q   # один файл
```

Для изменений в слагах полезно дополнительно проверить, что значение
действительно ложится в ожидаемый JSON-путь. Это можно сделать прямым вызовом
`apply_slug_overrides` из `app/tools/config_schema.py` в коротком тесте: подать
пустой `config` и словарь `{слаг: значение}`, затем убедиться, что значение
оказалось по нужному адресу.

Учтите, что запись настройки в `config` и её видимость на экране — разные факты.
Сервер заканчивает работу на записи корректного JSON; рисует отчёт фронтенд
портала. Поэтому для визуальных слагов одной проверки записи недостаточно —
нужна и проверка в браузере, что настройка действительно отрисовалась. Этот
принцип («источник истины — то, что отрисовано») в словаре терминов называется
рендер-контрактом (см. [../GLOSSARY.md](../GLOSSARY.md), разделы «Рендер» и
«Рендер-контракт»).

## Где добавлять новое

Короткие ориентиры, в какие файлы смотреть под типовую задачу. Подробные
пошаговые рецепты — [руководство по расширению сервера](../architecture/extending.md).

| Задача | Куда смотреть |
|---|---|
| Новая настройка компонента (слаг) | `app/tools/config_schema.py` — добавить запись в `SLUG_SCHEMA` с типом, ограничениями и фактическим JSON-путём; для визуального слага — проверить отрисовку в браузере. |
| Новый тип компонента (билдер) | `app/tools/builders.py` — функция-билдер стартового `config`; зарегистрировать тип в диспетчере добавления `app/tools/component_crud.py`. |
| Новый инструмент или действие | `app/server.py` — объявить функцию с `@mcp.tool` и проверкой режима; логику вынести в соответствующий `app/tools/*_operations.py`; для мультидейственного инструмента — диспетчер по `action` и ветка `action="help"`. |
| Новый промпт (сценарий) | `app/prompts.py` — генератор промпта; подключение через `@mcp.prompt` в `app/server.py`. |

При добавлении инструмента или действия придерживайтесь общего контракта ошибок:
неуспешный результат возвращается единым конвертом (поля вида `success`, `error`,
перечень недостающих параметров, подсказка и пример) — по нему ассистент
понимает, как исправить свой вызов и повторить его.
