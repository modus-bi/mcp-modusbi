# Установка и запуск из исходников (DevOps)

Этот документ описывает полный путь от клонирования репозитория до работающего
MCP-сервера: подготовка окружения, конфигурация подключения к порталу, запуск,
выбор режима доступа и базовая эксплуатация.

Что такое сам сервер и как он встроен в связку «ИИ — сервер — портал», описано в
[обзорном README документации](../README.md) и
[словаре терминов](../GLOSSARY.md). Здесь — практика развёртывания.

Коротко о месте сервера в схеме:

- наружу, к ИИ-клиенту, сервер говорит по протоколу **MCP поверх JSON-RPC 2.0**
  (не REST); транспорт — стандартный поток ввода-вывода (stdio). Каждый
  инструмент сервера — это RPC-метод;
- внутрь, к **порталу** ModusBI, сервер обращается по его HTTP-API: запросы идут
  методом POST, а конкретная операция кодируется в теле запроса (команда/действие),
  а не маршрутом ресурса.

Сервер запускает не человек напрямую, а MCP-клиент (например, Claude Desktop или
Claude Code): клиент читает конфигурацию, поднимает процесс сервера и общается с
ним по stdio. Поэтому «запуск» на практике сводится к двум вещам: подготовить
окружение и описать сервер в конфигурации клиента.

---

## Предусловия

- **Python 3.10 или новее** — обязателен; на нём работает и сервер, и тесты.
- **git** — для клонирования репозитория.
- Доступ к **порталу** ModusBI: URL, логин и пароль API-пользователя.
- Около 500 МБ свободного места, если планируется опциональная сборка бинарника.

## Шаг 1. Клонирование

Склонируйте репозиторий и перейдите в его каталог. Дальнейшие команды
выполняются из корня репозитория.

```bash
git clone <адрес-репозитория> modusbi-mcp
cd modusbi-mcp
```

## Шаг 2. Виртуальное окружение

Создайте изолированное окружение Python и активируйте его.

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
```

## Шаг 3. Установка зависимостей

Сервер опирается на три прямые зависимости (плюс их транзитивные), перечисленные
в `requirements.txt`:

| Пакет | Версия | Назначение |
|-------|--------|------------|
| `mcp` | `>=1.22.0` | SDK для реализации MCP-сервера (FastMCP) |
| `httpx` | `>=0.27.0` | Асинхронный HTTP-клиент для обращения к порталу |
| `pydantic` | `>=2.0.0` | Валидация входных данных инструментов |

```bash
pip install -r requirements.txt

# дополнительно — только если будете запускать тесты и дорабатывать сервер:
pip install -r requirements-dev.txt
```

## Шаг 4. Параметры подключения к порталу (`.env`)

Параметры портала и секреты сервер читает из переменных окружения. Их удобно
хранить в файле `.env` (шаблон — `.env.example`). Этот файл содержит пароль,
поэтому он внесён в `.gitignore` и **не должен попадать в репозиторий**.

Минимально необходимый набор:

| Переменная | Назначение |
|---|---|
| `MODUSBI_URL` | URL портала, например `https://your-portal.example.com` |
| `MODUSBI_USERNAME` | логин API-пользователя |
| `MODUSBI_PASSWORD` | пароль API-пользователя |

Дополнительные (необязательные) переменные:

| Переменная | Назначение |
|---|---|
| `MODUSBI_INSTANCE_NAME` | имя инстанса портала |
| `MODUSBI_SECURITY_CEILING` | жёсткая верхняя граница режима доступа (см. ниже) |
| `MODUSBI_EXPORT_DIR` | каталог для выгружаемых файлов отчётов |
| `MODUSBI_LOG_FORMAT` | формат логов (например, `json` для машинной обработки) |

Пример `.env` (значения — плейсхолдеры, подставьте свои):

```bash
MODUSBI_URL=https://your-portal.example.com
MODUSBI_USERNAME=<логин>
MODUSBI_PASSWORD=<пароль>
```

Пароль нигде не печатается в выводе инструментов и в логах. Не коммитьте `.env`
и `.mcp.json` — оба файла исключены из git.

## Шаг 5. Описание сервера в MCP-клиенте (`.mcp.json`)

MCP-клиент сам запускает сервер по записи в своём конфигурационном файле
(`.mcp.json` или `claude_desktop_config.json`). Готовый шаблон со всеми полями —
[.mcp.example.json](../../.mcp.example.json) в корне репозитория; справка по
серверам — [../../MCP_SERVERS.md](../../MCP_SERVERS.md), тоже в корне.

Минимальная запись для нашего сервера:

```jsonc
{
  "mcpServers": {
    "modusbi": {
      "command": "/абсолютный/путь/modusbi-mcp/.venv/bin/python",
      "args": ["-m", "app.server", "--readonly"],
      "cwd": "/абсолютный/путь/modusbi-mcp",
      "env": {
        "PYTHONPATH": "/абсолютный/путь/modusbi-mcp",
        "MODUSBI_URL": "https://your-portal.example.com",
        "MODUSBI_USERNAME": "<логин>",
        "MODUSBI_PASSWORD": "<пароль>"
      }
    }
  }
}
```

Замечания:

- `command` указывает на интерпретатор из созданного `.venv`, чтобы клиент
  поднимал сервер именно с установленными зависимостями;
- `args` задаёт точку входа `app.server` и режим доступа (здесь `--readonly`;
  для записи — `--readwrite`, см. ниже);
- один процесс сервера обслуживает **один портал**. Чтобы подключить несколько
  порталов, добавьте несколько записей в `mcpServers` — у каждой свой набор
  переменных `MODUSBI_*` (например, `modusbi-prod` и `modusbi-stage`).

### Мультипортал

Так как процесс single-instance (один портал на процесс), мультипортальная
конфигурация — это просто несколько именованных записей в `mcpServers`:

```jsonc
{
  "mcpServers": {
    "modusbi-prod":  { "command": "…", "args": ["-m", "app.server", "--readonly"],  "env": { "MODUSBI_URL": "https://portal-a.example.com", "…": "…" } },
    "modusbi-stage": { "command": "…", "args": ["-m", "app.server", "--readwrite"], "env": { "MODUSBI_URL": "https://portal-b.example.com", "…": "…" } }
  }
}
```

## Шаг 6. Запуск

Обычно сервер поднимает MCP-клиент по записи из `.mcp.json`. Запустить процесс
вручную (для проверки) можно как модуль — он общается по stdio:

```bash
python -m app.server              # readonly (по умолчанию)
python -m app.server --readonly   # явно только чтение
python -m app.server --readwrite  # чтение и запись
python -m app.server --demo       # демо-режим (только чтение + лимиты нагрузки)
```

Корректная точка входа — `python -m app.server`. При успешном старте в `stderr`
появляется строка вида `Server started in READONLY mode`. Для остановки ручного
запуска — `Ctrl-C`.

## Режимы доступа: readonly / readwrite

Режим запуска задаёт верхнюю границу того, что сервер вообще способен сделать,
независимо от вызванного инструмента. Это первый рубеж защиты портала: ИИ-клиент
вызывает инструменты автономно, поэтому по умолчанию запрещены любые изменяющие
действия.

- **`readonly`** (по умолчанию) — только чтение: `list`, `get`, `summary`,
  `validate`, выгрузка готовых отчётов в файлы. Безопасный режим для первого
  запуска, просмотра и аналитики.
- **`readwrite`** — дополнительно разрешает создание, изменение и удаление
  (`create`, `update`, `delete`, `add`). Включайте осознанно: в нём становятся
  доступны и необратимые операции.
- **`demo`** — по набору действий совпадает с `readonly`, но добавляет лимиты
  нагрузки; для публичных стендов.

Если ИИ-клиент пробует операцию записи, а сервер в `readonly`, действие штатно
отклоняется ошибкой вида `Действие 'create' требует режим: readwrite` — это не
сбой, а сработавшая защита. Чтобы разрешить запись, перезапустите сервер с
`--readwrite`.

Дополнительно можно зафиксировать **жёсткую верхнюю границу** режима флагом
`--security-ceiling` или переменной `MODUSBI_SECURITY_CEILING`: даже если кто-то
добавит `--readwrite`, потолок строже флага оставит запись заблокированной.

Полный разбор режимов, набор разрешённых действий каждого режима и механика
потолка — в [Режимы работы сервера](server-modes.md).

## Smoke-проверка и тесты

После установки убедитесь, что сервер собирается и точечная логика работает.

**Быстрая проверка слаг-логики без портала** (не требует подключения к порталу;
проверяет, что слаг раскладывается в нужный ключ конфигурации):

```python
import sys; sys.path.insert(0, "app")
from tools.config_schema import apply_slug_overrides

cfg = apply_slug_overrides({}, {"visuals.markerSize": 12}, "lineChart")
assert cfg["styleCommons"]["markerWidth"] == 12
```

**Точечные тесты** (запускаются после `pip install -r requirements-dev.txt`).
Эти файлы используют собственный runner — у них нет функций `def test_*`, поэтому
`pytest` их «не видит» (выдаёт `no tests ran`). Запускайте их как модули:

```bash
python -m app.tests.test_config_schema -q
python -m app.tests.test_security_modes -q
```

При успехе каждый печатает итог вида `Result: N OK, 0 FAIL` и завершается с
кодом `0`.

**Весь набор тестов** удобно прогонять через `pytest`:

```bash
python -m pytest app/tests/ -q
```

Учтите: тестовые файлы с собственным runner (как два выше) при сборе через
`pytest` могут давать `ERROR` на этапе фикстур — это особенность сборки, а не
падение теста. Ориентируйтесь на `FAILED`, а файлы с собственным runner
проверяйте модульным запуском. Действует правило «тесты первыми»: если что-то
падает, не переходите к сборке бинарника, пока не разберётесь.

## Обновление

Чтобы обновить установку до новой версии:

```bash
git pull
source .venv/bin/activate
pip install -r requirements.txt
```

После обновления перезапустите процесс сервера — живой сервер держит код в
памяти, и правки в `app/**` подхватываются только после перезапуска. В этом
проекте перезапуск выполняется вручную (оператором/администратором клиента).

Версия релиза сервера отслеживается переменной `MCP_VERSION` в записи сервера
(`.mcp.json`). О совместимости версий и миграции слагов — в
[../../VERSIONING.md](../../VERSIONING.md) в корне репозитория.

## Логи и диагностика

- Сервер пишет диагностику в **`stderr`** (stdout занят протоколом stdio).
  Где именно осядут эти строки, определяет MCP-клиент, который поднял процесс
  (как правило, в журнал клиента).
- Уровень детализации задаётся флагом `--log-level` (например,
  `--log-level DEBUG` при ручном запуске).
- Формат логов переключается переменной `MODUSBI_LOG_FORMAT` (значение `json`
  даёт структурированный вывод, удобный для систем сбора логов).
- Чувствительные данные (пароль, БД-credentials подключений) в логи и в вывод
  инструментов не попадают.

При ручной диагностике удобно стартовать сервер с подробными логами:

```bash
MODUSBI_URL=https://your-portal.example.com \
MODUSBI_USERNAME=<логин> \
MODUSBI_PASSWORD=<пароль> \
  python -m app.server --readonly --log-level DEBUG
```

## Опционально: сборка одного бинарника

Для распространения без установки Python собирается единый исполняемый файл.
Подробности и платформенные скрипты — в `build/BUILD.md`.

```bash
cd build
python build.py
```

Результат — один файл в папке версии `dist/<version>/<os>-<arch>/`:
`build/dist/1.0.0/linux-x86_64/modusbi-mcp-server` (Linux) или
`build/dist/1.0.0/windows-x86_64/modusbi-mcp-server.exe` (Windows), рядом —
файл `.sha256`. Бинарник собирается под текущую ОС
(Windows — на Windows, Linux — на Linux). Конфигурация в бинарь не упаковывается —
он читает те же переменные окружения (`MODUSBI_URL`, `MODUSBI_USERNAME`,
`MODUSBI_PASSWORD`) при запуске.
