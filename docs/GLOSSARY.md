# Словарь терминов

Единый справочник терминов проекта ModusBI MCP Server. Формулировки нейтральные,
каждый термин — одна-две фразы. Если в других файлах документации встречается понятие,
здесь приведено его краткое определение.

Термины сгруппированы: сначала протокол и сервер, затем сущности портала, затем
понятия конфигурации компонентов. Внутри групп — по алфавиту.

**Новичку достаточно знать восемь терминов:** MCP, MCP-сервер, Tool (инструмент),
Action (действие), Отчёт, Компонент, Датасет, Портал. Остальные термины пригодятся
при углублённом изучении настройки компонентов.

---

## Протокол и сервер

### MCP (Model Context Protocol)
Протокол, по которому ИИ-ассистент вызывает внешние инструменты. Сервер этого проекта
предоставляет ассистенту набор инструментов для работы с BI-отчётами. Подробнее —
[architecture/concepts/what-is-mcp.md](architecture/concepts/what-is-mcp.md).

### MCP-сервер
Процесс, который реализует протокол MCP и отдаёт ассистенту набор инструментов.
Этот проект и есть такой сервер: он принимает вызовы от ассистента и обращается к порталу.

### JSON-RPC
Формат обмена, который MCP использует для общения между ассистентом и сервером:
ассистент отправляет вызов метода с параметрами и получает результат. Транспорт — стандартный
поток ввода-вывода (stdio). Каждый инструмент сервера — это RPC-метод, а не HTTP-эндпоинт.
Подробнее — [architecture/concepts/protocol-and-rpc.md](architecture/concepts/protocol-and-rpc.md).

### Tool (инструмент)
Публичная функция сервера, доступная ассистенту как RPC-метод по протоколу MCP. Примеры:
`report_operations`, `component_crud`, `dataset_operations`. Один инструмент обычно покрывает
целую группу операций над одной сущностью.

### Action (действие)
Большинство инструментов мультидейственные: первый аргумент `action` выбирает конкретную
операцию (`create`, `update`, `delete`, `list`, `get` и т.д.). Например,
`component_crud(action="add", ...)` добавляет компонент. Это означает, что одна функция-инструмент
обслуживает много операций, переключаемых параметром `action`.

### Промпт (prompt)
Готовый многошаговый сценарий, который ассистент может развернуть по запросу — например,
«создай дашборд из шаблона». Промпты описывают последовательность вызовов инструментов
и идут вместе с сервером.

### Портал
Серверное приложение ModusBI, где хранятся отчёты, датасеты и подключения к данным, и которое
отдаёт интерфейс пользователю в браузере. MCP-сервер обращается к порталу по его HTTP-API:
вызовы идут методом POST, а конкретная операция кодируется в теле запроса (например,
полем `command`) либо парой «объект + метод». То есть портальный API устроен в стиле
команд-действий (action/command dispatch) поверх HTTP, а не как чистый ресурсный REST.

### Режимы readonly / readwrite
Режим запуска MCP-сервера. В режиме `readonly` (по умолчанию) доступны только операции чтения
и проверки: `list`, `get`, `summary`, `validate`, экспорт готовых отчётов. Режим `readwrite`
дополнительно разрешает создание, изменение и удаление (`create`, `update`, `delete`). Любая
операция задаётся параметром `action` инструмента; полный список действий для каждого режима —
[start/server-modes.md](start/server-modes.md).

## Сущности портала

### Отчёт (report)
Контейнер компонентов: объединяет виджеты, их раскладку и оформление. То же самое, что
**дашборд** (см. ниже). У отчёта есть числовой идентификатор (`id`), по которому к нему
обращаются инструменты.

### Дашборд (dashboard)
Синоним отчёта. В документации слова «отчёт» и «дашборд» взаимозаменяемы: и то и другое —
страница-контейнер с виджетами. В именах инструментов и параметров используется `report`.

### Компонент (component)
Отдельный виджет внутри отчёта: график, таблица, карта, KPI-блок, фильтр, текстовый блок и т.п.
То же самое, что **виджет** (см. ниже). Многие операции адресуют компонент по его порядковому
индексу в отчёте (`component_idx`), который считается с нуля.

### Виджет (widget)
Синоним компонента — отдельный элемент дашборда (график, таблица, карта, KPI, фильтр, текст).
В именах инструментов и параметров используется `component`.

### Датасет (dataset)
Сохранённый запрос к данным — «семантический слой», который базируется на источнике данных
(как правило SQL-запрос) и отдаёт таблицу строк и столбцов. Компоненты привязываются к
датасету и выбирают его поля для осей, значений и фильтров.

### Фильтр (filter)
Тип компонента, который ограничивает данные дашборда по значениям выбранного поля
(например, по периоду или категории). Чтобы фильтр действительно влиял на данные, его
поле добавляют не только в сам фильтр, но и в каждый компонент, который он должен фильтровать.

## Конфигурация компонентов

### config (конфиг)
JSON-объект внутри компонента, где хранятся все его настройки: цвета, легенда, оси, подписи,
поля данных и прочее. Это «истина» — портал отдаёт config браузеру, и именно по нему рисуется
компонент.

### Слаг (slug)
Короткое плоское имя одной настройки, понятное ассистенту. Сервер сам раскладывает слаг в нужный
адрес внутри `config`. Например, слаг `legend.position` сервер записывает в `config.legend.position`,
а слаг `visuals.columnWidth` — в `config.styleCommons.columnWidth`. Слаг избавляет от
необходимости писать сырой JSON-путь вручную.

### config_overrides
Словарь вида `{слаг: значение}`, который передают в инструменты редактирования компонента, чтобы
точечно переопределить его настройки — например,
`component_crud(action="update", component_idx=0, config_overrides={...})`. Сервер проходит по
словарю, проверяет каждое значение и записывает его в нужное место `config`.

### Рендер (render)
Отрисовка отчёта в браузере: фронтенд портала читает JSON-конфигурацию компонентов и
превращает её в видимое изображение (графики, таблицы, карты). Именно рендер определяет,
как настройки из `config` выглядят на экране.

### Рендер-контракт
Принцип, по которому проверяют, что настройка действительно влияет на изображение: источник
истины — то, что отрисовано в браузере, а не только то, что записано в `config`. Бывает, что
значение корректно сохранено в конфиге, но визуально ничего не меняется (настройка для данного
типа компонента не имеет видимого эффекта либо игнорируется отрисовкой) — такие случаи и выявляет
сверка с рендер-контрактом.

### Агрегация (aggregation)
Способ свёртки нескольких строк датасета в одно значение показателя: сумма (`sum`),
среднее (`avg`), минимум (`min`), максимум (`max`), количество (`count`). Применяется к полям на оси значений графиков
(столбцы, линия, круговая и др.). Значение `none` означает «не агрегировать».

### Иерархический разрез (hierarchy)
Категории, организованные уровнями (например, год → квартал → месяц или
регион → город → магазин). На диаграмме можно интерактивно переходить между
уровнями, сворачивая и разворачивая их.

### Серия (series)
Группа значений одного типа на графике, отличающаяся цветом или стилем. На
столбчатой диаграмме несколько серий показываются как столбцы рядом
(кластеризованные) либо как слои (стек). Серии задаются полем-разрезом
(параметр `series_field`).

## Практический пример

Как термины связаны в типичной работе:

1. **Отчёт** создают инструментом `report_operations(action="create", ...)` — получают пустой дашборд с `id`.
2. **Датасет** готовят инструментом `dataset_operations(action="create", ...)` — он отдаёт таблицу данных.
3. **Компонент** добавляют через `component_crud(action="add", ...)`, привязывая его к датасету и его полям.
4. **Фильтр** настраивают так, чтобы его поле попало и в фильтр, и в фильтруемые компоненты.
5. **Слаги** в `config_overrides` точечно правят `config` компонента; результат проверяют по **рендеру** в браузере.
