# Версионирование MCP-сервера ModusBI

Документ описывает: какие компоненты версионируются, по какой схеме, в каком порядке
ведётся версия и как соблюдаются зависимости между **фронтендом**, **бэкендом портала** и
**MCP-сервером**. Цель — уйти от россыпи inline-упоминаний версий в коде к единому источнику.

---

## 1. Три версионируемых компонента и их зависимости

```
┌─────────────────┐     читает слаги      ┌──────────────────┐
│  Frontend bundle │◄──────────────────────│   MCP slug-схема  │
│ (портал, рендер) │   (render contract)   │ config_schema.py  │
└────────┬─────────┘                       └────────┬─────────┘
         │ вызывает API                              │ вызывает API
         ▼                                           ▼
              ┌──────────────────────────────┐
              │   Backend портала (HTTP API)  │
              └──────────────────────────────┘
```

| Компонент | Что версионирует | Где живёт версия |
|---|---|---|
| **MCP-сервер** | tool-контракт, slug-схема, builders | `app/__init__.py` (`__version__`), см. §4 |
| **Frontend bundle** | что реально рендерится (слаги, geokeys, компоненты) | имя render-contract: `render_contract_<frontver>.json` |
| **Backend портала** | HTTP-эндпоинты (action/command), поля датасетов/отчётов | согласуется с frontend-релизом портала |

**Ключевая зависимость:** MCP пишет JSON-конфиг, но **рисует его фронтенд**. Поэтому slug-схема
MCP действительна только против КОНКРЕТНОЙ версии фронт-бандла (render contract). При смене
бандла часть слагов может стать `render-dead` или поменять json-путь — это надо переснять.

---

## 2. Схема версии MCP-сервера (semver)

`MAJOR.MINOR.PATCH` (например `1.1.0`):

- **MAJOR** — несовместимое изменение tool-контракта (удалён/переименован action или параметр,
  изменён формат ответа). Требует обновления клиентов.
- **MINOR** — обратносовместимое расширение: новые tools/actions/слаги/builders, новый
  render-contract под более новый фронт.
- **PATCH** — багфиксы без изменения контракта (исправление json-пути слага, scale, builder-логики).

Суффикс пред-релиза (`-rcN`) допустим только во внутренних сборках; **в публичный релиз
идёт чистый `MAJOR.MINOR.PATCH`**.

## 3. Матрица совместимости фронт ↔ бэк ↔ MCP

Ведётся таблицей (обновлять при каждом релизе). Источник правды по фронту — файл
`docs/architecture/readiness/audit/render_contract_<frontver>.json` (его имя = проверенная версия бандла).

| MCP-сервер | Frontend bundle (проверенный) | Backend портала | Render contract | Примечание |
|---|---|---|---|---|
| 1.0.x | 3.15.3 | совместимый с фронт 3.15.x | `render_contract_3.15.3.json` | первый публичный релиз, текущая база слаг-схемы |

> При добавлении строки: сначала переснять render-contract на новом фронте (§5), затем фиксировать
> строку матрицы. Не указывать «поддерживается» без проверенного render-contract.

## 4. Единый источник версии (уход от inline-упоминаний)

**Проблема:** версии/числа разбросаны по коду inline и расходятся
(напр. «342 slugs» в `server.py` ×3, но «339 slugs» в `schemas.py`; версии фронта в именах файлов).

**Правила:**

1. **Версия MCP** — каноничный источник один: `app/__init__.py` (`__version__`), он же дублируется
   в `pyproject.toml` (packaging требует статический номер). Бинарник сообщает версию сам.
   Переменная окружения `MCP_VERSION` — необязательный override для рантайма (стейджинг/сборки):
   код читает `os.environ.get("MCP_VERSION") or __version__` (см. `app/tools/token_metrics.py`).
   Не разносить номер по докстрингам/докам — менять только `__version__` (и синхронно `pyproject.toml`).
2. **Число слагов** — НЕ писать числом в тексте. Вычислять из `len(SLUG_SCHEMA)`
   (`app/tools/config_schema.py`). В докстрингах/инструкциях — формулировка «N слагов (см.
   `config_schema.SLUG_SCHEMA`)» без конкретного числа, либо подставлять `len(...)` в рантайме.
3. **Версия фронта** — ТОЛЬКО в имени `render_contract_<ver>.json` и в §3. Не хардкодить номер
   бандла (`3.15.3`) в коде Python.
4. **Версия бэка** — фиксируется только в §3 (матрица), не в коде.

---

## 5. Порядок ведения версии (процесс)

При **изменении фронт-бандла портала**:
1. Прогнать верификацию render-contract (какие слаги реально рендерятся) против нового бандла.
2. Обновить `render_contract_<новый_ver>.json` + slug-вердикты в `config_schema.py`
   (`render-dead` / новые json-пути).
3. Поднять **MINOR** MCP (новый контракт фронта = расширение совместимости) или **PATCH**
   (если только починка путей).
4. Добавить строку в матрицу §3.
5. Поднять `__version__` (`app/__init__.py`) и синхронно `pyproject.toml`.

При **изменении только MCP** (новый tool/slug/builder без смены фронта):
- Новый функционал → **MINOR**; багфикс существующего → **PATCH**. Матрицу §3 не трогать
  (фронт/бэк те же). Поднять `__version__` (и `pyproject.toml`).

При **изменении backend API портала**:
- Сверить затронутые tools (datasource/dataset/report/component) против нового API.
- При несовместимости — **MAJOR**; иначе MINOR/PATCH. Обновить строку §3.

---

## 6. Чек-лист перед релизом
- [ ] `__version__` (`app/__init__.py`) и `version` в `pyproject.toml` совпадают, чистый semver без суффиксов; если задан `MCP_VERSION` — тоже без суффиксов.
- [ ] В коде нет inline-чисел слагов и номеров версий фронт/бэк (см. §4).
- [ ] Матрица §3 отражает реально проверенную связку фронт/бэк/MCP.
- [ ] render-contract соответствует текущему фронт-бандлу.
